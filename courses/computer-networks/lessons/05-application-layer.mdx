      The **application layer** (top of the stack) is where users and apps meet the
      network: HTTP, DNS, SMTP, FTP, SSH, WebSockets. This lesson covers the protocols
      you will actually be quizzed on in interviews.

      ## HTTP vs HTTPS

      - **HTTP** — plaintext request/response (`GET /index.html` → `200 OK`). Anyone on
        the path (rogue WiFi, ISP, a MITM) can read or modify it.
      - **HTTPS** — HTTP wrapped in **TLS**: encrypts the payload, authenticates the
        server (certificate), and detects tampering. Same HTTP semantics, secure pipe.

      ## HTTP methods

      | Method | Job | Idempotent? |
      |--------|-----|-------------|
      | GET | read a resource | yes |
      | POST | create a resource / trigger an action | no |
      | PUT | replace/update a resource | yes |
      | DELETE | remove a resource | yes |

      ## Status codes worth remembering

      | Code | Meaning |
      |------|---------|
      | 200 OK | success |
      | 201 Created | resource created (the REST convention for a successful POST) |
      | 301 / 302 | moved permanently / found — redirects |
      | 400 Bad Request | malformed request |
      | 401 Unauthorized | missing or invalid credentials |
      | 403 Forbidden | authenticated, but not allowed to do this |
      | 404 Not Found | no such resource |
      | 500 Internal Server Error | server-side failure |

      **Use case:** `curl -i https://api.example.com/users` — read the status line
      first: 200 means the body *is* the resource, 201 means it was just created, 401
      means you forgot the token, 404 means the URL is wrong, 500 means the server broke.

      ## HTTP/1.1 vs HTTP/2 vs HTTP/3

      | | HTTP/1.1 | HTTP/2 | HTTP/3 |
      |---|----------|--------|--------|
      | Framing | text | binary | binary |
      | Connections | one request at a time per connection | many streams multiplexed over one TCP connection | many streams over one QUIC connection |
      | Headers | repeated on every request | HPACK compression | QPACK compression |
      | Transport | TCP | TCP | QUIC over **UDP** |
      | Head-of-line blocking | yes (per request) | residual: TCP-level (one lost packet stalls all streams) | no |

      One line each:

      - **HTTP/1.1 (1997)** — the classic; browsers open ~6 parallel connections to
        work around one-request-per-connection.
      - **HTTP/2 (2015)** — binary framing + multiplexing + header compression; but it
        still runs on TCP, so a single lost packet stalls every stream on that
        connection (TCP head-of-line blocking).
      - **HTTP/3 (2022)** — swaps TCP for **QUIC** (built on UDP): streams are
        independent, so a lost packet only affects its own stream; plus a faster 1-RTT
        handshake and connection migration (WiFi → cellular without reconnecting).

      ## DNS — turning names into IPs

      DNS is a distributed database mapping hostnames → IP addresses. Resolution
      sequence (cache at every hop):

      1. **Browser cache** → 2. **OS resolver cache** → 3. **Recursive resolver (ISP)**
         → 4. **Root server** (who handles `.com`?) → 5. **TLD server** (who handles
         `example.com`?) → 6. **Authoritative server** (the A record) → answer flows
         back down and is cached at every level until the TTL expires.

      ### Worked walkthrough: cold-cache resolution of www.example.com

      1. Browser cache miss → OS cache miss → the query goes to the ISP recursive resolver.
      2. Resolver asks a **root server**: "who is authoritative for .com?" → referral.
      3. Resolver asks the **.com TLD server**: "who is authoritative for example.com?"
         → referral to ns1.example.com.
      4. Resolver asks **ns1.example.com** (the authoritative server): "A record for
         www?" → `93.184.216.34`.
      5. The answer flows back; the resolver caches it (TTL, typically 300–86400 s) and
         the browser opens a TCP connection to that IP.

      That is **4 queries for a fully cold cache**, then everything is served from
      caches until the TTL expires.

      ## Record types (one line each)

      | Type | Purpose |
      |------|---------|
      | A | hostname → IPv4 address |
      | AAAA | hostname → IPv6 address |
      | CNAME | alias → canonical name |
      | MX | mail server for a domain (+ priority) |
      | TXT | arbitrary text — SPF/DKIM email verification, domain ownership |

      **Use case:** `dig +trace example.com` replays the root → TLD → authoritative
      walk you just did by hand; `nslookup -type=MX gmail.com` shows the mail servers.

      ## SMTP vs IMAP/POP3, FTP, SSH

      - **SMTP** — *sends* mail (push, port 25; submission on 587).
      - **IMAP / POP3** — *receive* mail (pull). IMAP keeps messages on the server and
        syncs folders across devices; POP3 downloads and typically deletes from the
        server (single-device model).
      - **FTP** — file transfer, ports 20/21, plaintext by default (prefer SFTP).
      - **SSH** — encrypted remote login + secure command execution, port 22.

      ## WebSockets vs HTTP

      | | HTTP | WebSockets |
      |---|------|------------|
      | Model | request → response, then done | full-duplex, persistent connection |
      | Direction | client initiates everything | server can push anytime |
      | Use | pages, REST APIs | chat, live scores, collaborative editors |

      A WebSocket starts as an HTTP `Upgrade` request; after the handshake both sides
      send frames freely over one TCP connection.

      ## REST vs GraphQL

      - **REST** — many endpoints, one per resource (`GET /users/7`); HTTP verbs +
        status codes; easy caching and statelessness; but **over-fetching** (you get
        the whole user object when you need one field) and **under-fetching** (N+1
        round trips) are common.
      - **GraphQL** — one endpoint; the client *declares exactly the fields it needs*
        (`query { user(id: 7) { name } }`); no over-fetching, one round trip; costs:
        more server complexity, no free HTTP caching, and deep nested queries need
        depth/complexity limits.

      **Use case:** a mobile app with a chat + profile feed uses GraphQL to fetch only
      what the small screen needs in one request; a public API for many consumers stays
      REST for its uniform interface and cacheability.

      :::tip
      **Interview question:** What happens when you type `https://www.example.com` and
      press Enter? — (1) **DNS**: browser cache → OS cache → ISP recursive resolver →
      root → .com TLD → authoritative server, getting the IP. (2) **TCP**: 3-way
      handshake (SYN, SYN-ACK, ACK) with the server. (3) **TLS**: handshake — verify the
      certificate, exchange keys, derive the AES session key. (4) **HTTP**: send
      `GET /` with headers (Host, User-Agent, Accept); the server replies 200 + HTML.
      (5) The browser parses, fetches sub-resources, and renders. Answer the layers in
      order — DNS → TCP → TLS → HTTP — and you have the complete walkthrough.
      :::

      :::tip
      **Interview question:** REST or GraphQL — which would you choose and why? — REST:
      uniform interface, simple, cacheable, great for public APIs and CRUD-heavy
      systems; pain points are over-fetching and N+1 requests. GraphQL: single endpoint,
      the client requests exactly the fields it needs — ideal for complex UIs on weak
      networks (mobile) and for aggregating resources in one round trip; costs are
      server complexity, no HTTP-level caching, and query abuse (mitigate with depth
      limits and cost analysis). Give the trade-off, not a favourite.
      :::

      ## WebSockets vs SSE vs long-polling — real-time options

      | | Long-polling | SSE | WebSockets |
      |---|--------------|-----|------------|
      | Direction | client asks, server holds the response until data exists, client re-asks | **one-way**: server → client, over plain HTTP | **full-duplex**: both sides send freely |
      | Transport | HTTP request/response loop | HTTP (EventSource) | HTTP Upgrade → persistent TCP frames |
      | Reconnect | manual (client logic) | **automatic** (EventSource reconnects) | manual (app-level heartbeats) |
      | Use | legacy chat fallback | live scores, notifications, logs | chat, collaborative editing, games |

      - **SSE** is a long-lived HTTP response the server keeps writing to — perfect when
        the server only *pushes* (notifications, tickers), because it rides normal HTTP
        (proxies and LBs handle it) and auto-reconnects.
      - **WebSockets** are needed for true two-way messaging (chat, multiplayer) — at
        the cost of a persistent connection that load balancers must pin to one backend
        (sticky sessions).
      - **gRPC** one-liner: protobuf-encoded messages over HTTP/2 with streaming (unary,
        server-stream, client-stream, bidi) — use it for internal service-to-service
        APIs with strict contracts; REST stays the default for public, cacheable,
        language-neutral APIs.

      :::tip
      **Interview question:** SSE or WebSockets for live notifications? — Notifications
      are one-way (server → client), so SSE fits: it runs over plain HTTP, auto-reconnects,
      and proxies handle it naturally. WebSockets buy full-duplex two-way messaging —
      choose them only when the client must also push (chat, multiplayer). And remember
      the LB implication: a WebSocket is a long-lived connection that must stick to one
      backend.
      :::
