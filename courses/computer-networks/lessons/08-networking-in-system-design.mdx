      System-design interviews test whether you can place the networking components you
      already know (DNS, TCP, TLS) at scale. Three components do most of the work:
      **DNS**, **CDNs** and **load balancers**.

      ## DNS in design — caching, TTL, anycast

      - **Caching + TTL:** every DNS answer is cached (browser, OS, resolver) until the
        **TTL** expires. Low TTL (60–300 s) → clients re-resolve often → fast failover
        when you move a service or switch CDN edges, at the cost of more queries. High
        TTL → fewer queries, but changes propagate slowly. This is the classic TTL
        trade-off.
      - **Anycast:** the same IP is advertised from many locations (BGP); a packet goes
        to the *nearest* location announcing it. Used for DNS root/TLD servers, CDN edge
        selection, and load-balancer VIPs.
      - **DNS role in CDN geo-routing:** the CDN's authoritative DNS answers with the IP
        of the **nearest edge** (based on the resolver's location / latency). One
        hostname, many edge IPs — DNS is the *first* routing decision of every request.

      **Use case:** `dig example.com` from two different resolvers returns two different
      IPs — that is geo-routing working.

      ## CDNs — cache at the edge

      A CDN is a network of **edge nodes** that cache content close to users; the
      **origin** is the source of truth.

      - **Cache hit:** the edge already has the object → served locally (fast, zero
        origin traffic).
      - **Cache miss:** the edge **pulls from the origin**, stores a copy (honoring
        `Cache-Control` / TTL), and serves it; the *next* request for the same object
        hits.
      - **What to cache:** static assets (images, JS/CSS, video). Dynamic, personalized
        pages are usually not cacheable — you need cache invalidation or a CDN that
        supports it.
      - **Payoff:** hits cut origin load dramatically and move content closer to users.

      ### Walkthrough: an image request

      1. Browser asks DNS → CDN geo-routing returns the nearest edge IP.
      2. Browser sends `GET /img/logo.png` to the edge.
      3. Edge cache lookup → **miss** (first request) → the edge requests the origin.
      4. Origin responds; the edge caches the object (TTL from Cache-Control) and serves
         it.
      5. A second user asks for the same image → **hit** — served from the edge; the
         origin never sees it.

      :::tip
      **Interview question:** Where does DNS sit in a CDN request? — DNS is the first
      hop: the browser's recursive resolver asks the CDN's authoritative nameservers,
      which answer with the IP of the *nearest* edge node (geo-routing, often anycast).
      The browser then connects to that edge, which serves the cached object or pulls
      from the origin on a miss. The TTL on that DNS answer decides how long users stay
      pinned to that edge — which is why CDN failover is fundamentally a DNS story.
      :::

      ## Load balancers — L4 vs L7

      | | L4 (transport) | L7 (HTTP/application) |
      |---|----------------|----------------------|
      | Decides on | IP + port only | HTTP: Host header, path, cookies |
      | Speed | very fast, minimal overhead | slower (parses HTTP) |
      | Awareness | none — can't tell /api from /static | full application awareness |
      | Extra duties | — | TLS termination, compression, caching, rewriting |
      | Fits | databases, game servers, raw TCP/UDP, backends that do their own TLS | web APIs, microservice routing, gRPC, sticky sessions |

      - **gRPC needs L7:** its HTTP/2 streams and trailers are opaque to an L4 balancer —
        routing, retries and balancing must understand HTTP/2.
      - **Algorithms:** **round robin** (each backend in turn), **least connections**
        (fewest active connections — good for uneven request durations), **IP hash**
        (same client → same backend, a cheap form of stickiness), **weighted**
        (capacity-aware).
      - **Reverse proxy duties:** an L7 LB is a reverse proxy — it **terminates TLS**
        (certificates live at the LB; backends speak plaintext internally), compresses
        responses, caches static content, and **hides the origin** (backends are not
        publicly reachable).
      - **Health checks:** the LB probes backends (TCP connect, HTTP `/healthz`) and
        stops routing to failed ones — the standard answer to "what happens when a
        backend dies?".
      - **Sticky sessions (session affinity):** pin a client to one backend via cookie
        or IP hash because the backend holds in-memory session state (cart, login).
        Trade-off: stickiness fights **statelessness** — the design goal is stateless
        backends so any instance can serve any request and a dying backend doesn't take
        its sessions with it. Treat sticky sessions as a migration crutch, not a design
        goal.

      :::tip
      **Interview question:** L4 vs L7 — when do you need L7? — Choose L7 whenever the
      routing decision needs HTTP context: path- or host-based routing (/api vs /static),
      TLS termination, cookie-based sticky sessions, compression/caching, and gRPC
      (HTTP/2 awareness). Choose L4 when you only need fast IP+port forwarding —
      databases, game servers, raw TCP/UDP — or when backends terminate TLS themselves
      and you want the balancer to stay out of the way.
      :::
