      Debugging is the interview topic that proves you understand layers: every tool
      targets a specific layer, and reading its output tells you where the stack breaks.

      ## ping — ICMP echo (L3 reachability)

      - Sends an **ICMP echo request**; a reply proves the host is **reachable at the
        network layer** and routers along the path forward ICMP.
      - What it does **NOT** prove: that the app works. A server can answer ping while
        port 443 is closed (firewall) or the web app is crashing (L7).
      - Caveat: many firewalls drop ICMP, so `ping fails` ≠ host down — it only means
        ICMP is unanswered.

      ## traceroute — mapping the path with TTL

      - **Mechanism:** send probes with **TTL = 1, 2, 3, …**. Every router decrements
        the TTL; the router that decrements it to **0 discards the packet** and replies
        **ICMP time-exceeded**, revealing its own IP.
      - The TTL=1 probe dies at the first router, TTL=2 at the second — so each hop
        identifies itself in order.
      - Platforms: Windows `tracert` uses **ICMP echo** probes; Linux/macOS
        `traceroute` uses **UDP** by default (the destination replies ICMP
        port-unreachable when the final probe arrives). `* * *` = a router that does
        not reply (common; firewalls).
      - TTL also explains the default TTL of 64/128 on packets: it bounds routing loops.

      **Use case:** `ping` answers "is it reachable?"; `traceroute` answers "via which
      path, and where does the path break?"

      ## dig / nslookup — DNS at the record level

      - `dig example.com` → the A record; `dig example.com AAAA` → IPv6; `dig -t MX
        gmail.com` → mail servers; `dig -t TXT example.com` → SPF/DKIM text records.
      - `dig +trace example.com` replays the full chain: root → .com TLD → authoritative
        server (the exact walk from the DNS lesson).
      - `nslookup` is the older, simpler tool; `dig` is the debugging-grade one.

      ## curl -v — see the actual conversation

      `curl -v https://api.example.com/users` prints, with `*` (events), `>` (request
      lines) and `<` (response lines):

      - `* Trying 93.184.216.34:443...` → TCP connect (L4).
      - `* Connected to ...` → the 3-way handshake completed.
      - `* TLS handshake completed` → TLS negotiated.
      - `> GET /users HTTP/1.1` and `< HTTP/1.1 200 OK` → the HTTP exchange (L7).

      Stops after `Trying...` → packets dropped (firewall/blackhole). Says `Connection
      refused` → host is up but the port is closed. Fails on the certificate → TLS-layer
      problem. The verbose output *is* a layer-by-layer progress report.

      ## tcpdump / Wireshark — read the flags

      `tcpdump -i eth0 host 93.184.216.34 and tcp port 443` shows segments with flags:

      - **SYN → SYN-ACK → ACK** = successful 3-way handshake.
      - **FIN / ACK, FIN / ACK** = graceful teardown (4-way).
      - **RST** = abrupt reset — e.g. nothing listening (connection refused).
      - Repeated **SYN** with no SYN-ACK = packets dropped or a SYN flood.

      Wireshark is tcpdump with a GUI; filter `tcp.flags.syn==1` to isolate handshakes.

      ## The layered troubleshooting ladder — ping works but HTTPS fails?

      Work the layers bottom-up; each tool answers exactly one layer:

      | Step | Layer | Tool / check |
      |------|-------|--------------|
      | L1 | Physical | cable/WiFi link, link lights |
      | L2 | Data link | switch ports, VLAN, MAC |
      | L3 | Network | `ping` (ICMP), `ip addr`, routing |
      | L4 | Transport | `nc -vz host 443`, `curl -v` (SYN-ACK?) |
      | L5–6 | Session/Presentation (TLS) | certificate valid? handshake completes? |
      | L7 | Application | DNS (`dig`), HTTP status, app logs |

      **Walkthrough: ping works, HTTPS fails.**

      1. ping OK → L3 and below are fine (ICMP reached the host).
      2. `dig example.com` → does DNS resolve? (**NXDOMAIN** = no record; **timeout** =
         resolver problem).
      3. `curl -v https://example.com` → does TCP connect? (`Connection refused` = port
         closed; hang after `Trying` = firewall dropping).
      4. TLS: expired or invalid certificate? Then HTTP: 4xx/5xx status?

      The failure is almost never the physical layer when ping works — it is DNS, a
      closed port, TLS, or the app.

      ## Common failures — read the error, not the vibes

      - **DNS NXDOMAIN** — the name does not exist (no record). Check spelling, the
        record, or the zone. Fast failure, definitive answer.
      - **DNS timeout** — no server answered. Different problem: resolver unreachable,
        firewall, or the DNS server is down.
      - **Connection refused** — the TCP handshake *reached* the host but nothing
        listens on that port (the host sent **RST**). The port is closed or the service
        is down.
      - **Timeout** — no response at all. Packets are being **dropped** (firewall,
        blackhole, host down, partition). The host may be up but unreachable.

      :::tip
      **Interview question:** How does traceroute use TTL to map a path? — Traceroute
      sends probes with TTL 1, 2, 3, … . Each router decrements the TTL; the router that
      reaches 0 discards the packet and replies ICMP time-exceeded with its own address.
      So TTL=1 names the first router, TTL=2 the second, and so on — each hop
      identifies itself in order. Windows `tracert` uses ICMP echo probes; Linux
      `traceroute` uses UDP by default.
      :::

      :::tip
      **Interview question:** ping works but the browser fails — walk me through the
      layers. — Ping proving reachability only clears L3 and below; the browser also
      needs DNS (L7), a TCP connection (L4), a TLS handshake (L5/6) and an HTTP response
      (L7). I would check, in order: `dig` for the A record; `nc -vz host 443` for the
      port; `curl -v` to watch TCP/TLS/HTTP progress; then the app logs. The insight
      they want: each tool targets one layer, and the failure is where the stack stops
      progressing.
      :::
