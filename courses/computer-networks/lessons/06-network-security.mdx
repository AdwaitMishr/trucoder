    content: |
      Security provides **confidentiality** (nobody reads it), **integrity** (nobody
      changes it) and **authentication** (it really is the server). Two kinds of
      encryption do the heavy lifting.

      ## Symmetric vs asymmetric encryption

      | | Symmetric (AES) | Asymmetric (RSA / ECC) |
      |---|-----------------|------------------------|
      | Keys | one shared key | key pair: public + private |
      | Speed | very fast (hardware-accelerated) | slow (modular exponentiation) |
      | Problem | key distribution — how do both sides share the key secretly? | solves distribution, but too slow for bulk data |
      | Uses | encrypting the actual data | key exchange, digital signatures |

      ## Hybrid encryption — how TLS combines them

      The handshake uses **asymmetric** crypto (RSA, or ECDHE key exchange) to agree on
      a **session key**; all application data is then encrypted with **symmetric AES**
      using that key. Best of both: secure distribution (asymmetric) + speed (symmetric).

      **Use case:** every `https://` connection. You never encrypt a whole download with
      RSA — you use RSA to ship the AES key, and AES to ship the bytes.

      ## SSL/TLS handshake (5 steps)

      1. **Client hello** — TLS version, cipher suites, client random.
      2. **Server hello** — chosen cipher, server random, and the server's **certificate**.
      3. **Certificate check** — the client verifies the certificate against trusted CAs
         (chain of trust), confirming the public key really belongs to the server.
      4. **Key exchange** — the client sends the **premaster secret** (encrypted with the
         server's public key) — or ECDHE parameters; both sides compute the **same AES
         session key** from the premaster + the two randoms.
      5. **Encrypted session** — `Finished` messages, then AES-encrypted application
         data. (TLS 1.3: 1-RTT, fewer round trips, forward-secret ciphers only.)

      ## Certificates & CAs — why we trust the server

      A certificate binds a **public key to an identity** and is digitally signed by a
      **CA**. Your browser ships the public keys of root CAs and verifies server certs by
      following the **chain of trust**: server ← intermediate ← root CA. You trust the
      CA, not the server directly — that is exactly what stops a stranger's key from
      passing itself off as example.com's.

      ## Firewalls

      - **Packet-filtering** — stateless; checks header fields (IP, port, protocol)
        against rules. Fast, but blind to context.
      - **Stateful** — tracks connection state (e.g. saw SYN, so allow the return
        traffic). The default for most office/home firewalls.
      - **Application proxy / gateway** — inspects the payload (HTTP, SQL…), terminates
        and re-originates connections. Deepest inspection, highest cost.

      ## VPNs

      A VPN creates an **encrypted tunnel** between two endpoints over the public
      internet (IPsec or TLS-based). A remote laptop ↔ corporate gateway: traffic is
      encrypted so the ISP or rogue WiFi cannot read it, and the remote host appears to
      be inside the office network.

      **Use case:** the layered answer — "stateful firewall at the perimeter, an
      application proxy for sensitive services, and a VPN for remote workers."

      ## Common attacks

      - **DoS vs DDoS** — one attacker overwhelms a server vs a **botnet** of many
        machines (much harder to block by IP). **SYN flood**: send many SYN segments and
        never finish the handshake → the server's half-open connection table fills →
        legitimate clients cannot connect. Defenses: SYN cookies, short timeouts.
      - **Amplification** — the attacker sends a small query with a *spoofed victim IP*
        to an open server (DNS/NTP); the big reply floods the victim.

      ### Worked numerical: DNS amplification

      Query = 60 bytes, response = 3000 bytes. Amplification factor = 3000 / 60 =
      **50×**. An attacker spoofing the victim's IP in 1000 queries makes the victim
      absorb 1000 × 3000 = **3,000,000 bytes ≈ 3.0 MB (2.9 MiB)** of traffic it never asked for.

      - **MITM (man-in-the-middle)** — the attacker sits between Alice and Bob, reading
        and altering traffic while impersonating each side to the other. Defense: TLS
        with proper certificate verification (PKI), mutual TLS for APIs.
      - **SQL injection** — user input is concatenated into a SQL query, changing its
        structure: `WHERE user = '$input'` with `input = ' OR '1'='1` logs you in as
        anyone (or dumps the table). Defense: **parameterized queries** (structure and
        data stay separate), input validation, least-privilege DB accounts.
      - **XSS** — the attacker injects client-side script into a page that *other* users
        view; the script steals cookies/sessions. Defense: escape output, sanitize
        input, Content-Security-Policy.

      **HTTPS vs plaintext:** over HTTP, anyone on the path — rogue WiFi, ISP, a MITM —
      can read and modify everything. HTTPS encrypts the whole payload, so eavesdroppers
      see only ciphertext.

      :::tip
      **Interview question:** Explain the TLS handshake. — Client hello (version,
      ciphers, random) → server hello with its certificate → client verifies the
      certificate against trusted CAs → key exchange (premaster secret encrypted with
      the server's public key, or ECDHE) → both sides derive the same AES session key →
      encrypted data flows. One-line summary: "asymmetric crypto to agree on a key,
      symmetric crypto to use it."
      :::

      :::tip
      **Interview question:** How does SQL injection work, and how do you prevent it? —
      If user input is concatenated into a query string, a crafted value like
      `' OR '1'='1` changes the query's structure and can bypass authentication or
      exfiltrate data. Prevention: **parameterized queries / prepared statements** (the
      database treats input as data, never as SQL), input validation/whitelisting,
      escaping, and least-privilege database accounts. Never build SQL by string
      concatenation.
      :::

      ## TLS 1.3 — the modern handshake

      - **1-RTT handshake:** the client hello carries an ECDHE **key share**; the server
        replies with its certificate and Finished — the full handshake takes **one round
        trip** instead of TLS 1.2's two, and both sides derive the session key
        immediately.
      - **0-RTT resumption:** with a previously shared PSK, the client sends
        **application data in its very first flight** (e.g. a GET) — zero added round
        trips on repeat visits. Trade-off: **replay risk** — a captured 0-RTT message
        can be replayed. Mitigations: idempotent requests only, anti-replay windows,
        never 0-RTT for state-changing requests.
      - **Forward secrecy is mandatory:** only ephemeral key exchange (**ECDHE**) is
        allowed, so a stolen long-term private key cannot decrypt past sessions.
        **RSA key exchange was removed** — with static RSA, the server's private key
        decrypts *every* recorded session, so one compromise exposed the whole history.
      - Legacy leftovers removed too: CBC ciphers, renegotiation, compression — fewer
        options, fewer attacks.

      ## Web security in one screen

      - **CORS preflight:** before a non-simple cross-origin request (custom headers,
        PUT/DELETE), the browser sends an **OPTIONS** preflight asking the server which
        origins/methods are allowed; the real request proceeds only if the server
        approves. The server's `Access-Control-Allow-Origin` header is the policy; the
        browser enforces it.
      - **CSRF + SameSite cookies:** CSRF = a malicious site triggers state-changing
        requests using the victim's cookies. Defenses: **SameSite** cookies (Lax/Strict
        stop cross-site sends), CSRF tokens, Origin/Referer checks.
      - **SSRF:** the server is tricked into fetching an attacker-chosen URL (e.g. the
        cloud metadata endpoint `http://169.254.169.254/`). Defenses: allowlist
        destinations, block link-local/metadata IPs, never trust raw user-supplied URLs.
      - **Cookie flags:** **HttpOnly** (JavaScript can't read it — defeats XSS cookie
        theft) and **Secure** (only sent over HTTPS).
      - **DNS over HTTPS (DoH):** DNS queries travel inside HTTPS to a DoH resolver, so
        ISPs and on-path attackers can't see or tamper with them — DNS privacy.
