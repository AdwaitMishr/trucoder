      The transport layer provides **end-to-end** delivery between processes (identified
      by **ports**) on two hosts. Two protocols dominate: **TCP** and **UDP**.

      ## TCP vs UDP

      | Feature | TCP | UDP |
      |---------|-----|-----|
      | Connection | connection-oriented (handshake) | connectionless |
      | Reliability | reliable, in-order (ACKs + retransmission) | best-effort, may lose/reorder |
      | Header | 20 bytes min | 8 bytes |
      | Flow/congestion control | yes (windows, AIMD) | no |
      | Use cases | HTTP, email, file transfer | DNS, VoIP, live gaming, video calls |

      ## TCP connection lifecycle

      **3-way handshake** (client → server):

      1. Client → Server: **SYN**, seq = x
      2. Server → Client: **SYN-ACK**, seq = y, ack = x+1
      3. Client → Server: **ACK**, ack = y+1 → connection established

      It proves *both* directions work and synchronizes both sequence numbers.

      **4-way termination:**

      1. A → B: **FIN**; 2. B → A: **ACK**; 3. B → A: **FIN**; 4. A → B: **ACK**.
      The side that initiates close enters **TIME_WAIT** (2 × MSL) so late packets die
      before the port is reused.

      ## Flow control vs congestion control

      - **Flow control** — receiver-driven: the receiver advertises a **receive window
        (rwnd)**; the sender never sends more than rwnd bytes in flight (sliding window).
      - **Congestion control** — network-driven: the sender keeps a **congestion window
        (cwnd)** and probes the network:
        - **Slow start:** cwnd doubles every RTT — 1, 2, 4, 8, 16 … until it hits
          **ssthresh** (slow-start threshold).
        - **Congestion avoidance (AIMD):** after ssthresh, cwnd grows *linearly*
          (+1 MSS per RTT); on loss, cwnd is halved (multiplicative decrease).
        - **Fast retransmit:** 3 duplicate ACKs → resend the missing segment immediately
          (don't wait for timeout). **Fast recovery:** halve cwnd, skip slow start,
          resume AIMD.

      ## Throughput formula

      Max throughput ≈ **window size / RTT** (bits per second). Bigger window or smaller
      RTT → more bandwidth. This is the classic "bandwidth-delay product" intuition.

      ## Ports & sockets

      A **socket** = (IP, port) pair. **Well-known ports:** HTTP 80, HTTPS 443, SSH 22,
      DNS 53, SMTP 25, MySQL 3306. Clients use **ephemeral ports** (49152–65535 by
      default) for the source side of a connection.

      **Use case:** choose UDP when a stale frame beats a late frame (gaming, voice,
      live video); choose TCP when correctness beats speed (web, files, email).

      :::tip
      **Interview question:** Why a 3-way handshake and not a 2-way one? — Both sides
      must synchronize their **sequence numbers**: SYN proves the server is reachable,
      SYN-ACK proves the client's SYN arrived, and the final ACK proves the server's
      SYN-ACK arrived. With 2 steps the client could never confirm the server's ISN, and
      the server would keep half-open connections — the setup that SYN-flood attacks
      exploit. (SYN cookies mitigate that.)
      :::

      :::tip
      **Interview question:** TCP or UDP for streaming vs gaming? — Video streaming can
      buffer, so it uses TCP (or QUIC, which is TCP-like over UDP) for reliable ordered
      delivery. Fast-action gaming and VoIP **cannot wait** for retransmission — a lost
      frame is better than a delayed one — so they use UDP for low latency, accepting
      loss. The answer hinges on: *can the app tolerate loss or latency?*
      :::

      ## RTT estimation — the EWMA formula

      TCP estimates the round-trip time to size its retransmission timeout.
      **Exponential Weighted Moving Average (EWMA, RFC 6298):**

      SRTT_new = (1 − α) × SRTT_old + α × Sample, with α = 0.125.

      ### Worked example

      Convention: initial SRTT = 28 ms; samples arrive in order 26, 32, 24 ms.

      - Sample 26: SRTT = 0.875 × 28 + 0.125 × 26 = 24.5 + 3.25 = **27.75 ms**
      - Sample 32: SRTT = 0.875 × 27.75 + 0.125 × 32 = 24.28125 + 4 = **28.28125 ≈ 28.28 ms**
      - Sample 24: SRTT = 0.875 × 28.28125 + 0.125 × 24 = 24.74609 + 3 = **27.74609 ≈ 27.75 ms**

      The newest sample moves SRTT by only α × (sample − SRTT) — that is the smoothing.
      α close to 1 chases every sample; α close to 0 is sluggish. (Single-step check
      from the initial value: 0.875 × 28 + 0.125 × 24 = 24.5 + 3 = **27.5 ms**.)

      ## Nagle's algorithm & silly window syndrome — two anti-tiny-packet fixes

      - **Nagle's algorithm (sender side):** while an unacknowledged segment is in
        flight, buffer small writes until a full MSS accumulates or the ACK arrives —
        stops a stream of 1-byte packets crossing the network. Disabled
        (`TCP_NODELAY`) when latency matters more than packet count.
      - **Silly window syndrome (receiver side):** the receiver advertises a tiny window
        (1 byte), forcing the sender to emit tiny segments. Fix: the receiver waits
        until the window is at least half an MSS before advertising it (Clark's
        solution).
