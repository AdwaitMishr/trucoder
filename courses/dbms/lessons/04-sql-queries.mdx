      ## DDL and DML basics

      Base data used by every example in this lesson:

      ```sql
      CREATE TABLE Department (
        dept_id   INT PRIMARY KEY,
        dept_name VARCHAR(50)
      );

      CREATE TABLE Employee (
        emp_id  INT PRIMARY KEY,
        name    VARCHAR(50),
        dept_id INT,
        salary  INT
      );

      INSERT INTO Department VALUES (10, 'Engineering'), (20, 'Sales'), (40, 'Legal');
      INSERT INTO Employee VALUES
        (1, 'Alice', 10, 60000),
        (2, 'Bob',   20, 50000),
        (3, 'Carol', 10, 80000),
        (4, 'Dave',  30, 40000);
      ```

      DML one-liners (shown separately — each acts on the base data):

      ```sql
      UPDATE Employee SET salary = salary * 1.1 WHERE dept_id = 20;  -- modify rows
      DELETE FROM Employee WHERE emp_id = 4;                          -- remove rows
      TRUNCATE TABLE Employee;   -- delete ALL rows, keep the schema
      DROP TABLE Employee;       -- delete table AND schema
      ```

      **SELECT** with filtering, sorting, limiting:

      ```sql
      SELECT name, salary
      FROM Employee
      WHERE dept_id = 10
      ORDER BY salary DESC
      LIMIT 2;
      -- Carol 80000, Alice 60000  → 2 rows
      ```

      ## Joins — same two tables, different row counts

      Employee has 4 rows (dept_ids 10, 20, 10, 30); Department has 3 rows
      (10, 20, 40). Only dept 10 and 20 match.

      ```sql
      SELECT e.name, d.dept_name
      FROM Employee e
      INNER JOIN Department d ON e.dept_id = d.dept_id;
      -- Alice/Engineering, Bob/Sales, Carol/Engineering → 3 rows
      -- Dave (dept 30) and Legal (dept 40) have no partner and are dropped

      SELECT e.name, d.dept_name
      FROM Employee e
      LEFT JOIN Department d ON e.dept_id = d.dept_id;
      -- 4 rows: all employees kept; Dave gets a NULL dept_name

      SELECT e.name, d.dept_name
      FROM Employee e
      RIGHT JOIN Department d ON e.dept_id = d.dept_id;
      -- 4 rows: all departments kept; Legal gets NULL name

      SELECT e.name, d.dept_name
      FROM Employee e
      FULL OUTER JOIN Department d ON e.dept_id = d.dept_id;
      -- 5 rows: 3 matches + Dave (left-only) + Legal (right-only)

      SELECT e.name, d.dept_name
      FROM Employee e
      CROSS JOIN Department d;
      -- 4 × 3 = 12 rows: every employee paired with every department

      SELECT e1.name AS emp1, e2.name AS emp2
      FROM Employee e1
      JOIN Employee e2 ON e1.dept_id = e2.dept_id AND e1.emp_id < e2.emp_id;
      -- SELF join: employees sharing a department → (Alice, Carol) → 1 row
      ```

      **Use case:** dashboards join fact and dimension tables every query —
      knowing which join keeps unmatched rows (and on which side) is the
      difference between correct and inflated counts.

      ## Subqueries and correlated subqueries

      ```sql
      -- Plain subquery: above the company average (57500)
      SELECT name FROM Employee
      WHERE salary > (SELECT AVG(salary) FROM Employee);
      -- Alice 60000, Carol 80000 → 2 rows

      -- Correlated subquery: above their OWN department's average
      SELECT e.name
      FROM Employee e
      WHERE e.salary > (SELECT AVG(salary) FROM Employee e2
                        WHERE e2.dept_id = e.dept_id);
      -- dept 10 avg = (60000+80000)/2 = 70000 → Carol (80000) qualifies
      -- dept 20 avg = 50000 → Bob (50000) does not
      -- dept 30 avg = 40000 → Dave (40000) does not
      -- → 1 row: Carol
      ```

      A **correlated** subquery references the outer row (`e.dept_id`) and
      re-runs for every outer row; a plain subquery runs once.

      ## CTEs: WITH ... AS (named subqueries)

      A **CTE (common table expression)** gives a subquery a name so
      the main query reads top-down:

      ```sql
      WITH high_earners AS (
        SELECT name, salary FROM Employee WHERE salary > 55000
      )
      SELECT name FROM high_earners ORDER BY salary DESC;
      -- high_earners = {Alice 60000, Carol 80000} → Carol, Alice → 2 rows
      ```

      - Defined once with `WITH name AS (...)`, then referenced like a
        table — even **multiple times** in the same query.
      - Mostly a **readability** tool: simple non-recursive CTEs are
        usually inlined by the optimizer, not a performance shortcut.
      - `WITH RECURSIVE` (lesson 9) turns them into iterative queries
        for hierarchies.

      **Use case:** a multi-step report — compute the eligible set in a
      CTE, then join/filter against it twice in one query instead of
      repeating the subquery.

      ## GROUP BY, HAVING, and aggregates

      `WHERE` filters **rows before grouping**; `HAVING` filters **groups
      after grouping**. Aggregates cannot appear in WHERE — that is the
      classic interview distinction.

      ```sql
      SELECT dept_id, AVG(salary) AS avg_sal
      FROM Employee
      GROUP BY dept_id
      HAVING AVG(salary) > 55000;
      -- dept 10: (60000+80000)/2 = 70000 ✓
      -- dept 20: 50000 ✗   dept 30: 40000 ✗
      -- → 1 row: (10, 70000)

      SELECT COUNT(*), SUM(salary), AVG(salary), MIN(salary), MAX(salary)
      FROM Employee;
      -- 4, 230000, 57500, 40000, 80000
      ```

      ## Window functions

      Window functions compute over a "window" of rows without collapsing
      them. On ties, the three ranking functions differ:

      ```sql
      CREATE TABLE Score (student VARCHAR(20), score INT);
      INSERT INTO Score VALUES ('Ana', 90), ('Ben', 85), ('Cid', 85), ('Dina', 70);

      SELECT student, score,
             ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,
             RANK()       OVER (ORDER BY score DESC) AS rk,
             DENSE_RANK() OVER (ORDER BY score DESC) AS dr
      FROM Score;
      -- Ana  90 → rn 1, rk 1, dr 1
      -- Ben  85 → rn 2, rk 2, dr 2
      -- Cid  85 → rn 3, rk 2, dr 2   (tie: same rank; rn stays unique)
      -- Dina 70 → rn 4, rk 4, dr 3   (RANK skips 3, DENSE_RANK does not)
      ```

      ```sql
      SELECT student, score,
             LAG(score)  OVER (ORDER BY score DESC) AS prev,
             LEAD(score) OVER (ORDER BY score DESC) AS next
      FROM Score;
      -- Ana: prev NULL, next 85   ·   Ben: prev 90, next 85
      -- Cid: prev 85,  next 70    ·   Dina: prev 85, next NULL
      ```

      `LAG` reads the previous row, `LEAD` the next row in the window.

      ## Indexes, views, triggers, procedures

      ```sql
      CREATE INDEX idx_emp_dept ON Employee(dept_id);  -- speed up dept lookups

      CREATE VIEW high_paid AS
      SELECT name, salary FROM Employee WHERE salary > 60000;

      CREATE TRIGGER trg_emp_audit
      AFTER INSERT ON Employee
      FOR EACH ROW
      INSERT INTO AuditLog(emp_id, changed_at) VALUES (NEW.emp_id, NOW());

      CREATE PROCEDURE GiveRaise(IN pct INT)
      BEGIN
        UPDATE Employee SET salary = salary * (1 + pct / 100);
      END;
      ```

      **Use case:** a real app uses all of these together — an index on the
      join key, a view for role-based access, a trigger for auditing, a
      procedure for the payroll raise.

      ## Interview questions

      :::tip
      **Interview question:** What is the difference between WHERE and HAVING?
      — WHERE filters individual rows before grouping; HAVING filters groups
      after GROUP BY. Aggregates are only legal in HAVING: `WHERE AVG(salary) >
      55000` is a syntax error, `HAVING AVG(salary) > 55000` works.
      :::

      :::tip
      **Interview question:** RANK vs DENSE_RANK vs ROW_NUMBER? — On ties,
      RANK and DENSE_RANK give tied rows the same number; ROW_NUMBER always
      assigns unique numbers. After a tie, RANK skips the next number(s)
      (90, 85, 85, 70 → 1, 2, 2, 4) while DENSE_RANK does not (1, 2, 2, 3).
      :::

          counts = Counter(row[rkey] for row in right)
          return sum(counts.get(row[lkey], 0) for row in left)
