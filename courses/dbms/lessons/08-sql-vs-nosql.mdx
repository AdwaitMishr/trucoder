      ## SQL vs NoSQL — the comparison table

      The first question in any data-store interview: what is each family
      good at, and how do you choose?

      | | SQL (relational) | NoSQL |
      |---|---|---|
      | Schema | Fixed, enforced (DDL); migrations required | Flexible / schema-less; fields vary per row |
      | Scaling | Mostly vertical; sharding is hard and manual | Horizontal by design (shard / replicate) |
      | Transactions | ACID, multi-row, multi-table | ACID per document; BASE at cluster scale |
      | Relations | First-class via JOIN | Denormalize or embed; joins are avoided |
      | Best for | Banking, ERP, anything needing strong consistency and joins | Caching, sessions, catalogs, time series, analytics |
      | Examples | PostgreSQL, MySQL, Oracle | Redis, MongoDB, Cassandra, Neo4j |

      **Use case:** interviewers rarely want a winner — they want you to weigh
      consistency, write volume, schema stability, and query shape against
      each other and then commit to an answer.

      ## CAP theorem

      A distributed data store can guarantee at most **two of three**:

      - **Consistency (C)** — every read sees the latest write (replicas agree).
      - **Availability (A)** — every request gets a response, even if stale.
      - **Partition tolerance (P)** — the system keeps working when nodes lose
        contact with each other.

      The catch: **partitions are not optional** — networks drop packets, so a
      distributed system must tolerate them. That makes the real choice **CP
      vs AP**, not "pick any two":

      - **CP** (e.g. a bank ledger, single-leader replication): during a
        partition the system **rejects writes** it cannot confirm, so replicas
        never diverge. Consistency wins, availability dips.
      - **AP** (e.g. a social-media feed, multi-leader): every replica **keeps
        accepting writes** and reconciles later — availability wins, reads may
        be briefly stale (eventual consistency).

      ## ACID vs BASE

      | ACID (SQL) | BASE (NoSQL at scale) |
      |---|---|
      | **A**tomicity — all-or-nothing transactions | **B**asically **A**vailable — system stays up |
      | **C**onsistency — invariants hold after every commit | **S**oft state — replicas may differ briefly |
      | **I**solation — concurrent transactions don't interfere | **E**ventual consistency — replicas converge later |
      | **D**urability — committed data survives crashes | No hard guarantee per write; trade-offs explicit |

      BASE is not "worse ACID" — it is a different contract chosen when
      availability and write throughput matter more than instant agreement.

      ## When to choose NoSQL

      Choose **NoSQL** when:

      - **High write throughput** — logging, events, IoT: millions of writes
        per second shard naturally (Cassandra).
      - **Flexible schema** — product catalogs where attributes change every
        sprint (MongoDB documents).
      - **Caching / hot paths** — sessions, rate-limit counters, leaderboards
        (Redis, in front of your SQL DB).
      - **Analytics over wide data** — columnar/wide-column layouts scan
        billions of rows fast.

      Stay with **SQL** when you need multi-row ACID transactions (money),
      complex joins or ad-hoc reporting, or a stable schema with mature tooling.

      ## NoSQL types and when each shows up

      - **Key-value — Redis.** Caching, session storage, counters (INCR),
        pub/sub, TTLs (`SET key val EX 60`). Why so fast: everything lives
        **in memory** (µs reads, no disk), and a **single-threaded event
        loop** processes commands one at a time — no locking, no context
        switches, and every command is O(1)-ish.
      - **Document — MongoDB.** Flexible JSON-ish documents, embedded
        sub-objects; great for catalogs and content where one entity is
        naturally a whole tree.
      - **Wide-column — Cassandra.** Rows with sparse, dynamic columns;
        designed for **very high write throughput** and time-series data.
      - **Graph — Neo4j.** Nodes + edges queried by traversal; "friends of
        friends", path finding, recommendation hops.

      ## "Design a schema for X" — the e-commerce intro

      Interviewers love an open-ended schema question. Take a mini
      e-commerce: users, orders, products.

      **SQL, normalized:**

      ```sql
      CREATE TABLE Users (id INT PRIMARY KEY, name VARCHAR(50));
      CREATE TABLE Products (id INT PRIMARY KEY, name VARCHAR(50), price INT);
      CREATE TABLE Orders (
        id INT PRIMARY KEY, user_id INT REFERENCES Users(id), placed_at DATE
      );
      CREATE TABLE Order_Items (
        order_id INT REFERENCES Orders(id),
        product_id INT REFERENCES Products(id),
        qty INT,
        PRIMARY KEY (order_id, product_id)
      );
      -- an order is assembled with JOINs; price changes are consistent
      -- everywhere because there is exactly one Products row
      ```

      **NoSQL, document (MongoDB-style):**

      ```js
      {
        _id: 9001,
        user: { id: 7, name: "Ana" },          // denormalized snapshot
        items: [
          { product_id: 12, name: "Keyboard", price: 80, qty: 1 }
        ],
        placed_at: "2024-01-15"
      }
      ```

      Trade-off: one read returns the whole order (no joins), but the
      product name/price are **copied** — if the price changes later, old
      orders keep the old snapshot. That is the classic normalization vs
      read-speed decision, and naming it out loud is the answer.

      ## Interview questions

      :::tip
      **Interview question:** Explain CAP with a real system. — Take a bank
      ledger: it is CP — during a network partition it rejects writes it
      cannot confirm so two ATMs can never disagree about a balance. Take a
      social-media feed: it is AP — it keeps accepting posts everywhere and
      reconciles later; a briefly stale follower count is fine. The trick is
      that partition tolerance is not a choice: networks fail, so you only
      really pick C or A during a partition.
      :::

      :::tip
      **Interview question:** When would you use Redis? — When hot data must
      be served in microseconds and fits in memory: caching (with TTLs so
      keys expire), session storage, rate-limit counters (INCR), pub/sub for
      lightweight fan-out, and sorted sets for leaderboards. It is fast
      because it is in-memory and single-threaded — and that is also its
      limit: no SQL joins, no multi-row transactions, and data is only as
      durable as your persistence config.
      :::

      :::tip
      **Interview question:** SQL or NoSQL for a new product — how do you
      decide? — Start from requirements, not fashion: need ACID across
      multiple rows (money, inventory) or complex joins → SQL. Expecting
      massive write throughput, a schema that changes weekly, or read-heavy
      hot paths → NoSQL. And name the middle ground: a SQL source of truth
      with a Redis cache in front is the most common real architecture.
      :::
