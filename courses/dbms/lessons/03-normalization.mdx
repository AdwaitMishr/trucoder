      ## Functional dependencies

      **X → Y** ("X determines Y") means every value of X maps to exactly one
      value of Y — like a mathematical function. In a student table,
      `StudentID → StudentName` holds because one student has one name.

      A dependency is **trivial** when Y is a subset of X: `{A, B} → A` holds
      in every table and carries no information. The **closure X⁺** is the set
      of all attributes reachable from X by following FDs — you compute it to
      find candidate keys.

      ## The normal forms (short definitions)

      - **1NF** — all values atomic (no lists/arrays), no repeating groups.
      - **2NF** — 1NF + no *partial* dependency: no attribute depends on only
        part of a composite candidate key.
      - **3NF** — 2NF + no *transitive* dependency: no non-prime attribute
        depends on another non-prime attribute (A → B → C, with C non-prime).
      - **BCNF** — every determinant (the left side of every non-trivial FD)
        must be a candidate key. Stronger than 3NF.

      **Use case:** before you write a schema, list the FDs and walk the
      ladder — the interview answer is exactly this checklist, in order.

      ## Worked ladder: Enroll(StudentID, StudentName, CourseID, CourseName, Instructor, InstructorPhone)

      FDs:

      ```sql
      StudentID   → StudentName
      CourseID    → CourseName, Instructor
      Instructor  → InstructorPhone
      ```

      Candidate key: `{StudentID, CourseID}` (composite).

      **Step 1 (1NF):** values are atomic and there are no repeating groups —
      already in 1NF.

      **Step 2 (2NF):** `StudentID → StudentName` is a *partial dependency*
      (StudentName depends on part of the key); same for `CourseID →
      CourseName, Instructor`. Decompose to remove them:

      ```sql
      Student(StudentID PK, StudentName)
      Course(CourseID PK, CourseName, Instructor)
      Enroll(StudentID, CourseID)   -- PK (StudentID, CourseID), both FKs
      ```

      **Step 3 (3NF):** in Course, `CourseID → Instructor → InstructorPhone`
      is transitive, and InstructorPhone is non-prime. Split:

      ```sql
      Course(CourseID PK, CourseName, Instructor)
      InstructorInfo(Instructor PK, InstructorPhone)
      ```

      **Step 4 (BCNF):** every remaining determinant (`StudentID`, `CourseID`,
      `Instructor`) is a primary key of its table — the design is in BCNF and
      all FD-driven redundancy is gone.

      ## Lossless vs lossy decomposition

      A decomposition is **lossless** if the natural join of the fragments
      recovers the original relation exactly — no lost rows, no spurious rows.
      Test: the shared (common) attribute must be a **key of at least one
      fragment**.

      ```sql
      -- Lossy example: Emp(EmpID, Project, Dept)
      -- rows: (E1, P1, D1), (E2, P1, D2)
      -- split into R1(EmpID, Project) and R2(Project, Dept)
      -- joining on Project fabricates (E1, P1, D2) — a row that never existed
      ```

      `Project` is not a key of either fragment (P1 maps to two depts), so the
      join invents tuples — lossy. In the 2NF split above, the shared
      attributes between fragments — `StudentID` between Student↔Enroll and
      `CourseID` between Course↔Enroll — are keys of the Enroll fragment, so
      every split is lossless.

      ## When to denormalize

      Normalization removes redundancy at the cost of joins. In **read-heavy
      analytics** (star schemas, data warehouses) you deliberately denormalize
      — store `dept_name` inside the fact table — to avoid joins over billions
      of rows, accepting update anomalies in exchange for query speed. OLTP
      stays normalized; OLAP often does not.

      **Use case:** a reporting warehouse answers "total sales by region" —
      one wide, denormalized fact table beats a 6-way normalized join.

      ## Interview questions

      :::tip
      **Interview question:** What is the difference between 3NF and BCNF? — A
      relation is 3NF if every non-trivial FD X → A has X as a superkey OR A
      is prime (part of a candidate key). BCNF drops the second clause: every
      non-trivial FD must have a candidate key on its left side. So BCNF is
      strictly stronger — every BCNF relation is 3NF, not vice versa.
      :::

      :::tip
      **Interview question:** Why is BCNF stricter than 3NF? — 3NF tolerates a
      non-key determinant as long as what it determines is a prime attribute;
      BCNF does not. Classic case: R(A, B, C) with FDs {AB → C, C → B}. The
      candidate keys are AB and AC, so B and C are prime and 3NF holds — but
      C → B has a non-key determinant, so BCNF fails. BCNF removes that
      residual redundancy: C's value would otherwise repeat alongside B.
      :::
