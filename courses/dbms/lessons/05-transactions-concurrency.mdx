      ## Transaction states

      A **transaction** is a unit of work executed as a whole (ACID recap:
      **Atomicity** all-or-nothing · **Consistency** valid state to valid
      state · **Isolation** behaves as if serial · **Durability** committed
      work survives crashes — lesson 1). During its life a transaction moves
      through five states:

      - **Active** — executing statements (the normal state).
      - **Partially committed** — the last statement executed, but writes are
        not yet flushed to disk.
      - **Committed** — all writes are durable; the transaction is done.
      - **Failed** — an unrecoverable error (bad statement, constraint
        violation, deadlock victim).
      - **Aborted** — rolled back; all effects undone. It may be restarted.

      **Use case:** a payment gateway tracks every order as a state machine —
      the DB knows whether to redo (partially committed + crash), undo
      (failed → aborted), or report success (committed).

      ## Concurrency anomalies — with concrete examples

      Three problems appear when transactions interleave on the same data.

      **Dirty read** — a transaction reads a value written by another
      transaction that has NOT committed:

      ```sql
      -- T1: UPDATE accounts SET balance = 500 WHERE id = 1;  -- not committed
      -- T2: SELECT balance FROM accounts WHERE id = 1;       -- reads 500
      -- T1: ROLLBACK;                                        -- 500 vanishes
      -- T2 read 500, which never existed in any committed state
      ```

      **Non-repeatable read** — the same row read twice in one transaction
      returns different values because another transaction committed an
      update in between:

      ```sql
      -- T1: SELECT balance FROM accounts WHERE id = 1;  -- 1000
      -- T2: UPDATE accounts SET balance = 900 WHERE id = 1; COMMIT;
      -- T1: SELECT balance FROM accounts WHERE id = 1;  -- 900 (changed!)
      ```

      **Phantom read** — a range query run twice returns different row sets
      because another transaction inserted (or deleted) matching rows:

      ```sql
      -- T1: SELECT COUNT(*) FROM accounts WHERE balance > 500;  -- 2
      -- T2: INSERT INTO accounts VALUES (9, 700); COMMIT;
      -- T1: SELECT COUNT(*) FROM accounts WHERE balance > 500;  -- 3 (phantom)
      ```

      Key difference: non-repeatable read = an **existing row changed**;
      phantom read = **new rows appeared** in the result set of a range query.

      ## Isolation levels

      The SQL standard defines four levels. Each one *allows* some anomalies
      and *prevents* others:

      | Isolation level | Dirty read | Non-repeatable read | Phantom read |
      |---|---|---|---|
      | READ UNCOMMITTED | allowed | allowed | allowed |
      | READ COMMITTED | prevented | allowed | allowed |
      | REPEATABLE READ | prevented | prevented | allowed |
      | SERIALIZABLE | prevented | prevented | prevented |

      - **READ UNCOMMITTED** — reads whatever is in the buffer, committed or
        not. Fast, but every anomaly is possible.
      - **READ COMMITTED** — each statement only sees committed data.
      - **REPEATABLE READ** — a row read twice in one transaction returns the
        same value; new rows (phantoms) can still appear.
      - **SERIALIZABLE** — transactions behave as if executed one after
        another (range locks or snapshot + conflict checks).

      **Use case:** a bank uses SERIALIZABLE (or REPEATABLE READ with range
      locks) for money movements; an analytics dashboard reads a replica at
      READ COMMITTED — stale aggregates are acceptable, corrupt ones are not.

      ## Locking: shared vs exclusive, 2PL, deadlock

      **Shared lock (S)** — for reads; many transactions may hold it on the
      same item at once. **Exclusive lock (X)** — for writes; only one
      holder. Compatibility: S–S compatible; S–X, X–S and X–X conflict.

      **Two-phase locking (2PL):**

      - **Growing phase** — the transaction may only *acquire* locks.
      - **Shrinking phase** — the transaction may only *release* locks; the
        moment it releases one, it can never acquire another.

      2PL guarantees a **serializable (conflict-serializable)** schedule: any
      interleaving is equivalent to some serial order. **Strict 2PL** (used
      in practice) holds every lock until commit/abort, which also prevents
      cascading aborts.

      **Deadlock** — two transactions hold locks the other needs:

      ```sql
      -- T1: UPDATE accounts SET balance = ... WHERE id = 1;  -- T1 holds X(1)
      -- T2: UPDATE accounts SET balance = ... WHERE id = 2;  -- T2 holds X(2)
      -- T1: UPDATE accounts SET balance = ... WHERE id = 2;  -- T1 waits for T2
      -- T2: UPDATE accounts SET balance = ... WHERE id = 1;  -- T2 waits for T1
      ```

      Detection: build the **wait-for graph** — a node per transaction, an
      edge `T1 → T2` when T1 waits for a lock held by T2. A **cycle** means
      deadlock. Resolution: the DB picks a **victim** (the cheapest to roll
      back), rolls it back, releases its locks, and the other transaction
      proceeds.

      ## MVCC: snapshot isolation in PostgreSQL

      MVCC (Multi-Version Concurrency Control) is PostgreSQL's
      alternative to pure locking:

      - Each transaction sees a **snapshot** — the committed state as
        of a point in time (statement start at READ COMMITTED,
        transaction start at REPEATABLE READ).
      - **UPDATE/DELETE never overwrite in place**: the old row version
        stays behind for transactions whose snapshots still need it;
        writers create new versions.
      - **Readers never block writers, writers never block readers** —
        a long-running SELECT and a concurrent UPDATE both proceed.
        This is the big win over 2PL, where a read can wait on a
        writer's lock.
      - Old versions are garbage-collected by **VACUUM** once no
        snapshot can see them anymore.
      - MySQL's InnoDB also uses MVCC (undo-log based), but its default
        REPEATABLE READ still uses next-key locks for range scans.

      **Use case:** a reporting SELECT that runs for minutes no longer
      stalls checkout writes — the report reads its snapshot while
      writes go to new row versions.

      **vs 2PL:** 2PL makes readers and writers *wait* on locks; MVCC
      lets them proceed on different versions.

      ## Interview questions

      :::tip
      **Interview question:** Explain dirty read vs phantom read with
      examples — Dirty read: T1 updates a row but does not commit; T2 reads
      the uncommitted value; T1 rolls back, so T2 used data that never
      existed. Phantom read: T1 runs a range query (`COUNT(*) WHERE balance >
      500`); between two runs, T2 inserts a new matching row and commits, so
      T1 sees a different count. Dirty = reading *uncommitted* data; phantom
      = *new rows* appearing in a range result.
      :::

      :::tip
      **Interview question:** What isolation level do PostgreSQL and MySQL
      default to? — PostgreSQL defaults to READ COMMITTED; MySQL (InnoDB)
      defaults to REPEATABLE READ.
      :::

      :::tip
      **Interview question:** How is a DB deadlock detected and resolved? —
      Transactions wait on locks; the DB builds a wait-for graph and looks
      for a cycle. On a cycle it selects a victim, rolls that transaction
      back, frees its locks, and lets the other proceed.
      :::
