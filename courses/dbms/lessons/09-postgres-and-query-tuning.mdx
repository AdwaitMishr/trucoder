      ## PostgreSQL vs MySQL vs SQLite — one line each

      - **PostgreSQL** — the most SQL-standard-compliant open-source DB;
        MVCC concurrency, rich types (jsonb, arrays, ranges), a heavy
        feature set.
      - **MySQL** — the default in classic web stacks (LAMP, WordPress);
        InnoDB storage engine, fast simple CRUD, easy to run and
        replicate.
      - **SQLite** — an embedded library, not a server: zero-config,
        single-file, runs inside the app (browsers, mobile, CLI tools).

      **Use case:** interviews love the trade-off — PostgreSQL for
      complex queries and data integrity; MySQL when the team already
      runs a LAMP-style stack; SQLite when the database must travel
      with the application.

      ## MVCC: snapshot isolation without blocking

      MVCC = Multi-Version Concurrency Control. Instead of making
      readers wait for locks, the DB keeps **multiple versions of each
      row**:

      - Every transaction reads from a **snapshot** — the committed
        state at a point in time.
      - An UPDATE/DELETE does not overwrite in place: it writes a **new
        version** and leaves the old one for transactions whose
        snapshots still need it.
      - **Readers never block writers and writers never block readers**
        — a long SELECT and a concurrent UPDATE both finish without
        waiting.
      - Old versions are swept up later by **VACUUM** (PostgreSQL) once
        no snapshot can see them.

      MySQL's InnoDB also uses MVCC (undo-log based), so both engines
      give non-blocking reads — the *isolation semantics* differ (next
      block).

      **vs 2PL:** 2PL makes a reader wait on a writer's lock (or vice
      versa); MVCC sidesteps the wait by serving the reader an older
      version. Locking guarantees serializability; MVCC gives snapshot
      isolation.

      ## Practical isolation: PG READ COMMITTED vs MySQL REPEATABLE READ

      - **PostgreSQL defaults to READ COMMITTED.** Each *statement*
        gets a fresh snapshot of committed data. Two statements in one
        transaction can see different rows if another transaction
        commits in between. Good default: current data, short waits.
      - **MySQL (InnoDB) defaults to REPEATABLE READ.** The snapshot is
        fixed at the transaction's first read, so a row read twice
        returns the same value — and InnoDB's next-key (gap) locks also
        block most phantoms, at the price of more lock contention and
        deadlock risk.
      - Both engines **prevent dirty reads** at these defaults.

      **Use case:** "I ran the same report twice and got different
      numbers" is usually READ COMMITTED doing its job — each statement
      sees fresh commits. Use REPEATABLE READ when a report must be
      internally consistent.

      ## EXPLAIN: reading query plans

      `EXPLAIN SELECT ...` shows the **execution plan** the optimizer
      chose, without running the query:

      - **Seq Scan** — read every row of the table (bad on big tables).
      - **Index Scan** — walk the B+ tree to the matching rows.
      - **Index Only Scan** — the index alone answers the query
        (covering index).

      `EXPLAIN ANALYZE` actually **runs** the query and reports real
      time and rows per node. The plan is only as good as the
      **statistics**: the planner estimates row counts from
      `pg_statistic`/`ANALYZE` data. Stale stats (big inserts, no
      ANALYZE) produce bad plans — so tables are re-analyzed as data
      changes.

      ## Sargability: don't wrap indexed columns in functions

      A predicate is **sargable** when the index can be searched
      directly. Putting a function around the indexed column forces
      evaluation on every row — the index is ignored:

      ```sql
      -- NOT sargable: YEAR() runs per row → seq scan despite the index
      SELECT name FROM Employee WHERE YEAR(hire_date) = 2024;

      -- Sargable: a range on the raw column → index range scan
      SELECT name FROM Employee
      WHERE hire_date >= '2024-01-01' AND hire_date < '2025-01-01';
      ```

      Same trap: `UPPER(name) = 'ALICE'`, `salary + 1000 > 50000`,
      `LEFT(code, 2) = 'AB'` — all scan. Rewrite the predicate, don't
      rewrite the column.

      ## Composite indexes and covering indexes

      - **Composite index** `(dept_id, salary)` — one B+ tree ordered
        by dept_id, then salary. **Leftmost prefix rule:** usable for
        queries on `dept_id` and on `dept_id + salary`, but NOT on
        `salary` alone.
      - **Covering index** — contains every column the query touches,
        so the query is answered from the index alone (Index Only
        Scan), with no table lookups.

      ```sql
      CREATE INDEX idx_dept_sal ON Employee(dept_id, salary);

      SELECT dept_id, salary FROM Employee WHERE dept_id = 10;
      -- index-only: both columns are in the index, filter is the prefix

      SELECT salary FROM Employee WHERE salary > 50000;
      -- NOT index-only: salary is not the leftmost column
      ```

    content: |
      ## Query-tuning checklist

      - Avoid `SELECT *` — fetch only needed columns (enables covering
        scans, shrinks transferred data).
      - Use `LIMIT` where the app only needs the top rows.
      - Index the columns in `WHERE` and `JOIN ... ON` — and make sure
        the predicate is sargable.
      - Rewrite correlated subqueries as **JOINs** when the outer table
        is large — a join can be hash-joined, a per-row subquery
        cannot.
      - Don't put functions on indexed columns.
      - Confirm with `EXPLAIN ANALYZE`: the fix worked when Seq Scan
        becomes Index Scan / Index Only Scan.

      ## CTEs: WITH ... AS

      A CTE names a subquery so the main query reads top-down. Using
      lesson 4's Employee (Alice 60000, Bob 50000, Carol 80000, Dave
      40000):

      ```sql
      WITH high_earners AS (
        SELECT name, salary FROM Employee WHERE salary > 55000
      )
      SELECT name FROM high_earners ORDER BY salary DESC;
      -- high_earners = {Alice 60000, Carol 80000} → Carol, Alice → 2 rows
      ```

      - Defined once, referenced like a table — even **multiple times**
        in one query.
      - Mostly a **readability** tool: simple non-recursive CTEs are
        usually inlined by the optimizer, so no magic speedup.
      - Recursive or data-modifying CTEs are materialized (next block).

      ## Recursive CTEs: hierarchies

      `WITH RECURSIVE` = **anchor term** (first rows) `UNION ALL`
      **recursive member** (joins the CTE's own name to produce the
      next level). Hierarchy: Ada is CEO; Ben and Cam report to her;
      Dee, Eve and Fay are level 3.

      ```sql
      CREATE TABLE Emp (
        emp_id     INT PRIMARY KEY,
        name       VARCHAR(50),
        manager_id INT REFERENCES Emp(emp_id)   -- NULL for the CEO
      );

      INSERT INTO Emp VALUES
        (1, 'Ada', NULL), (2, 'Ben', 1), (3, 'Cam', 1),
        (4, 'Dee', 2),    (5, 'Eve', 2), (6, 'Fay', 3);

      WITH RECURSIVE org AS (
        SELECT emp_id, name, manager_id, 1 AS level
        FROM Emp WHERE manager_id IS NULL            -- anchor: Ada, level 1
        UNION ALL
        SELECT e.emp_id, e.name, e.manager_id, org.level + 1
        FROM Emp e JOIN org ON e.manager_id = org.emp_id  -- next level
      )
      SELECT name, level FROM org ORDER BY level, name;
      -- Ada 1 · Ben 2 · Cam 2 · Dee 3 · Eve 3 · Fay 3 → 6 rows
      ```

      Each iteration feeds the previous level's rows back in; when an
      iteration returns no rows, the recursion stops.

      ## JSON / JSONB in PostgreSQL — one line

      `jsonb` stores JSON in binary, indexed form; a **GIN index**
      (`CREATE INDEX ON doc USING gin(body jsonb_path_ops)`) makes
      `@>` (contains) and `?` (key exists) lookups fast instead of
      re-scanning every document.

      ## Interview questions

      :::tip
      **Interview question:** PostgreSQL vs MySQL — which and why? —
      PostgreSQL: closest to the SQL standard, richest types (jsonb,
      arrays, ranges), MVCC with strong consistency, great for complex
      queries and analytics. MySQL (InnoDB): ubiquitous in web stacks,
      fast simple CRUD, easy replication, but weaker on advanced
      features and standard quirks. Pick by workload: complex queries
      and data integrity → PostgreSQL; commodity web CRUD with a team
      that already runs MySQL → MySQL.
      :::

      :::tip
      **Interview question:** What does EXPLAIN tell you? — The
      optimizer's chosen plan: access method per table (Seq Scan vs
      Index Scan vs Index Only Scan), join order and type, and
      estimated row counts and costs. EXPLAIN ANALYZE additionally runs
      the query and reports actual timings and rows — the gap between
      estimated and actual rows is where stale statistics hide.
      :::

      :::tip
      **Interview question:** Why does WHERE YEAR(hire_date) = 2024
      ignore the index? — The predicate is not sargable: the function
      must be evaluated on every row, so the B+ tree on hire_date
      cannot be walked. Rewrite as a range —
      `hire_date >= '2024-01-01' AND hire_date < '2025-01-01'` — and
      the planner can use the index.
      :::
