      ## Entities and attributes

      An **entity** is a real-world object we store data about (Student,
      Course). An **attribute** is a property of an entity:

      - **Simple** — atomic, cannot be split (`age`).
      - **Composite** — made of parts (`Name` = First + Last).
      - **Multivalued** — can hold many values (`Phone` — several numbers).
      - **Derived** — computed from others (`Age` from `DOB`); usually not
        stored.

      A **relationship** is an association between entities (`Enrolls` links
      Student and Course).

      ## Cardinality

      - **1:1** — one entity on each side (one Employee ↔ one ParkingSpot).
      - **1:N** — one on the left, many on the right (one Department → many
        Employees).
      - **M:N** — many on both sides (a Student enrolls in many Courses; a
        Course has many Students).

      ## ER notation

      ER diagrams use shapes: **rectangles** = entities, **ellipses** =
      attributes, **diamonds** = relationships, **lines** = links. Key
      attributes are underlined; multivalued attributes are double ellipses;
      derived attributes are dashed ellipses.

      **Use case:** a university registrar sketches the Student–Course model in
      ER notation first, then converts it to SQL tables.

      ## ER → relational conversion rules

      1. **Entity → table:** each entity becomes a table; its attributes become
         columns; the key attribute becomes the primary key.
      2. **1:N → foreign key on the N side:** put the primary key of the "1"
         side into the "many" side's table as a foreign key.
      3. **M:N → junction table:** create a new table whose primary key is the
         composite of the two entity primary keys, plus any relationship
         attributes.
      4. **1:1 → merge or FK:** merge into one table, or add a foreign key on
         either side.

      ## Worked example: Student–Course (M:N)

      ```sql
      CREATE TABLE Student (
        StudentID INT PRIMARY KEY,
        Name      VARCHAR(50)
      );

      CREATE TABLE Course (
        CourseID INT PRIMARY KEY,
        Title    VARCHAR(50)
      );

      -- Junction table for the M:N relationship
      CREATE TABLE Enrolls (
        StudentID INT,
        CourseID  INT,
        Grade     CHAR(2),
        PRIMARY KEY (StudentID, CourseID),
        FOREIGN KEY (StudentID) REFERENCES Student(StudentID),
        FOREIGN KEY (CourseID)  REFERENCES Course(CourseID)
      );
      ```

      The composite primary key `(StudentID, CourseID)` also stops a student
      enrolling in the same course twice, and the relationship attribute
      `Grade` lives in the junction table — not in either entity table.

      ## Keys

      - **Super key** — any set of attributes that uniquely identifies a row
        (may contain redundant attributes): `{StudentID}` and also
        `{StudentID, Name}`.
      - **Candidate key** — a *minimal* super key: remove any attribute and it
        stops being unique: `{StudentID}` (and `{Email}` if emails are
        unique).
      - **Primary key** — the candidate key chosen to identify rows.
      - **Alternate key** — a candidate key not chosen as the primary key.
      - **Composite key** — a key made of two or more columns
        (`(StudentID, CourseID)` in Enrolls).
      - **Foreign key** — a column referencing another table's primary key,
        enforcing referential integrity.

      **Use case:** `Enrolls` uses a composite primary key of two foreign keys
      — this is the standard relational answer to M:N relationships and the
      most common schema question in interviews.
  - type: markdown
    content: |
      ## Interview questions

      :::tip
      **Interview question:** Super key vs candidate key vs primary key? — A
      super key is any unique-identifying attribute set (it may be redundant);
      a candidate key is a minimal super key (no proper subset is unique); the
      primary key is the one candidate key chosen for row identity. A table can
      have many super keys and several candidate keys, but exactly one primary
      key.
      :::

      :::tip
      **Interview question:** How do you model an M:N relationship in
      relational tables? — With a junction table whose primary key is the
      composite of both foreign keys (e.g. `Enrolls(StudentID, CourseID)`),
      plus any relationship attributes such as `Grade`. The composite key also
      enforces that each pair appears only once.
      :::
