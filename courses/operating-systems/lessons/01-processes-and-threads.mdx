      ### Program vs Process vs Thread

      - **Program** — a passive file on disk (source or binary). It does nothing by itself.
      - **Process** — an active instance of a program in execution, with its own resources (address space, open files, registers, PID).
      - **Thread** — the unit of execution *inside* a process; threads of one process share code, data and open files, but keep their own stack and registers.

      | | Program | Process | Thread |
      |---|---|---|---|
      | Nature | passive | active | active |
      | Own address space | — | yes | no (shared) |
      | Scheduled by OS | no | via its threads | yes (kernel threads) |

      **Use case:** a web server spawns a **thread per request** (cheap, shared state), while Chrome runs each browser tab as a separate **process** so one crashing tab cannot take down the browser. Processes give isolation; threads give cheap concurrency.
  - type: markdown
    content: |
      ### Process lifecycle & states

      A process moves through five states. Only **Running** actually executes on a CPU.

      - **New** — being created.
      - **Ready** — loaded in memory, waiting for the CPU.
      - **Running** — instructions executing on the CPU.
      - **Blocked / Waiting** — waiting for I/O or an event (disk, keyboard, a lock).
      - **Terminated** — finished; the OS reclaims its resources.

      **Use case:** `ps` / Task Manager shows every running process in one of
      these states — a process in **Blocked** (uninterruptible sleep, `D`
      state) is why a hung disk can freeze an app; **Ready** is why your CPU
      stays busy even while one process waits for input.

      :::tip
      Remember: a process can only go **Blocked → Ready → Running**. It can never jump directly from Blocked to Running.
      :::

      ### PCB — Process Control Block

      One PCB per process — the kernel's bookkeeping structure for that process.

      - PID and parent PID
      - Process state (new / ready / running / blocked / terminated)
      - Program counter + CPU registers (saved on every switch)
      - Memory limits and page tables
      - Open file list
      - Scheduling info (priority, queue pointers)
      - I/O status (pending requests, devices)

      **Use case:** when a process is suspended, the PCB is exactly what lets the OS resume it later — like a saved game slot holding the full game state.

      :::tip
      Interview answer: "The PCB is the data structure the kernel uses to track every process — everything needed to suspend it and resume it later."
      :::
  - type: markdown
    content: |
      ### Context switching

      - To switch processes, the kernel **saves** the running process's state (PC, registers, stack pointer) into its PCB and **loads** the next process's saved state from its PCB.
      - It is pure **overhead** — the CPU does no useful work during the switch.
      - Cost components: saving/restoring registers, kernel-mode entry/exit, and **cache/TLB misses** because the new process's data is cold.

      **Use case:** with thousands of switches per second in a thread-per-request server, TLB/cache flushes — not register saves — dominate the cost.
  - type: markdown
    content: |
      ### User threads vs kernel threads

      - **User threads** — managed in user space by a thread library. Fast to create and switch (no syscall), but the kernel sees only the process.
      - **Kernel threads** — created and scheduled by the OS directly. Slower to create, but the kernel can run them in parallel on different cores, and one blocked kernel thread does not stall the whole process.

      **Multithreading models:**
      - **Many-to-one** — many user threads mapped to one kernel thread. Cheap, but one blocking syscall blocks *all* threads (classic Java green threads).
      - **One-to-one** — each user thread has its own kernel thread (Linux `clone`, modern Java). True parallelism, more overhead per thread.
      - **Many-to-many** — N user threads multiplexed onto M kernel threads. Best of both, complex to implement.

      **Use case:** Go and Rust use kernel threads (one-to-one) for true
      parallelism; language runtimes like Java historically started with
      many-to-one green threads and moved to one-to-one as cores multiplied.
      A database connection pool is a user-space construct riding on kernel
      threads underneath.
