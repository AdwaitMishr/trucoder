      ## Contiguous allocation

      Each process occupies one continuous block of physical memory.

      - **Fixed partitioning** — fixed-size partitions; a process smaller than
        its partition wastes space inside it (**internal fragmentation**).
      - **Dynamic partitioning** — partitions match process size; many small
        holes appear between processes (**external fragmentation**), fixed by
        **compaction** (moving processes together — costly).

      Placement policies:
      - **First fit** — first hole big enough (fast).
      - **Best fit** — smallest hole that fits (leaves tiny holes).
      - **Worst fit** — largest hole (leaves big usable holes).

      **Use case:** early batch systems and bare-metal embedded OSes; today it
      survives under paging (page frames) and in allocators like the kernel's
      buddy allocator.

      ## Paging

      Physical memory is cut into fixed-size **frames**, logical memory into
      equal-sized **pages**; a per-process **page table** maps page → frame.

      - Logical address = **page number (p) + offset (d)**.
      - Offset uses log₂(page_size) bits (4 KiB ⇒ 12 bits).
      - Physical address = frame(p) × page_size + offset.

      **Worked example:** page size 4 KiB, page table says `page 3 → frame 7`,
      logical address `0x3A2C`:

      - `0x3A2C` → page **0x3** (3), offset **0xA2C** (2604)
      - Physical = 7 × 4096 + 2604 = **31276 = 0x7A2C** — the frame number
        simply replaces the page number.

      Only **internal** fragmentation (last page partially used); no external
      fragmentation. Cost: one page-table entry per page.

      **Use case:** every modern OS pages (Linux/Windows/macOS); 4 KiB pages
      with 2 MiB large pages on x86-64.

      ## Segmentation

      Memory is divided into variable-sized **segments** (code, data, stack).
      A segment table holds **base + limit** per segment; address = base +
      offset, checked against the limit.

      - No internal fragmentation; **external** fragmentation possible.
      - Segments are programmer-visible and **shareable** (one code segment,
        many processes).

      **Use case:** x86's legacy segment registers; shared libraries mapped as
      a shared segment; the JVM's heap / code cache / stack regions.

      ## Virtual memory & demand paging

      Pages are loaded only when touched (**demand paging**). On a reference
      to a page not in memory, a **page fault** occurs:

      1. Trap to kernel (invalid PTE).
      2. Find a free frame, or evict a victim page.
      3. Swap the page in from disk.
      4. Update the page table and TLB.
      5. Restart the faulting instruction.

      **Effective access time:** EAT = (1 − p) × ma + p × fault_time, with
      p = page-fault rate and ma = memory-access time.

      **Worked example:** ma = 200 ns, fault service = 8 ms = 8×10⁶ ns,
      p = 10⁻⁴:

      EAT = (1 − 0.0001) × 200 + 0.0001 × 8×10⁶ = 199.98 + 800 =
      **999.98 ns ≈ 1 µs** — one fault in 10 000 accesses quintuples the
      effective access time.

      **Use case:** a laptop runs a browser + IDE + Docker by keeping rarely
      used pages on disk; SSDs (~50 µs random reads) make demand paging
      tolerable, HDDs (~8 ms) made it painful. The JVM heap is OS pages under
      the hood — swap pressure shows up as page-fault stalls.

      ## Page replacement

      No free frame ⇒ evict a **victim page** (write back first if dirty).

      - **FIFO** — evict the oldest loaded page. Simple; suffers **Belady's
        anomaly** (more frames can mean more faults).
      - **LRU** — evict the least-recently-used page. Good, but expensive to
        track exactly.
      - **OPTIMAL** — evict the page whose next use is farthest in the
        future. Best possible, needs the future — used as a yardstick.

      **Classic worked example** — reference string
      `7,0,1,2,0,3,0,4,2,3,0,3,2,1,2,0,1,7,0,1`, 3 frames:

      | Algorithm | Page faults |
      |---|---|
      | FIFO | 15 |
      | LRU | 12 |
      | OPTIMAL | 9 |

      **Belady's anomaly in miniature** — `1,2,3,4,1,2,5,1,2,3,4,5`:
      with 3 frames FIFO gives 9 faults (LRU gives 10); with 4 frames FIFO
      gives 10 — *more* frames, *more* faults. FIFO is not monotonic.

      **Use case:** every OS page-replacement path (Linux clock/LRU-like
      approximations), browser tab discarding, database buffer caches.

  - type: markdown
    content: |
      ## Thrashing

      When the **sum of working sets** (pages each process touched in its last
      Δ references — its **locality**) exceeds available frames, every process
      faults constantly and CPU utilization collapses.

      - Cause: too many processes for the memory, or too small a working-set
        window.
      - Fix: **reduce multiprogramming** (swap processes out) or give the
        process more frames.

      **Use case:** a dev machine with 40 browser tabs pages itself into a
      stall; closing tabs shrinks the total working set. CI runners
      over-provisioned with parallel builds thrash the same way.

      def solve(reference: list[int], frames: int) -> int:
          memory = []
          faults = 0
          for page in reference:
              if page not in memory:
                  faults += 1
                  if len(memory) == frames:
                      memory.pop(0)
                  memory.append(page)
          return faults
