      ### Race conditions & the critical section problem

      - **Race condition** — two or more threads read-modify-write a shared variable concurrently; the final value depends on the interleaving. Example: `counter++` compiles to load / add / store, and two interleaved increments can lose an update.
      - **Critical section** — the code that touches shared data; only one process may be inside it at a time.

      A correct solution needs three properties:
      1. **Mutual exclusion** — at most one process inside the critical section.
      2. **Progress** — if the CS is free and some process wants in, only processes outside their remainder section may take part in the decision; the choice must not be postponed forever.
      3. **Bounded waiting** — a bound on how many times other processes may enter before a waiting process gets in.

      **Use case:** database **row-level locks** — two transactions updating the same bank balance must not interleave, or money silently disappears.

      ### Peterson's solution (two processes)

      - Classic software-only algorithm using `turn` and a `flag[]` array; it satisfies all three requirements for exactly **2** processes.
      - `flag[i] = true` means Pi wants in; `turn = j` hands priority to the other process, so the two can never both enter.

      ```c
      // process i (0 or 1), j = the other process
      flag[i] = true;
      turn = j;
      while (flag[j] && turn == j);   // busy wait
      // critical section
      flag[i] = false;                // exit section
      ```
      **Use case:** mostly theoretical today — CPUs reorder instructions, so real code needs hardware primitives (atomic instructions, locks).

      ### Mutex vs semaphore

      - **Mutex** — a binary lock (locked / unlocked); only the process that locked it may unlock it. Built for **protection** of a critical section.
      - **Semaphore** — an integer S with atomic `wait(S)` (decrement; block if it would go negative) and `signal(S)` (increment; wake a waiter). **Counting** semaphore = resource counter; **binary** semaphore ≈ mutex.
      - Both may **busy-wait** (spin) and waste CPU; real implementations block the thread and park it on a queue.
      - A counting semaphore with value N admits at most N processes.

      **Use case:** a **connection pool** (say 10 JDBC connections) is a counting semaphore — `wait` when all 10 are busy, `signal` when one is returned.

      ### Producer–Consumer (bounded buffer)

      A buffer of size n is protected by three semaphores:
      - `mutex = 1` — guards the buffer itself.
      - `empty = n` — number of free slots.
      - `full = 0` — number of filled slots.

      Producer: `wait(empty); wait(mutex); add item; signal(mutex); signal(full);`
      Consumer: `wait(full); wait(mutex); remove item; signal(mutex); signal(empty);`

      :::warning
      Order matters: `wait(empty)` / `wait(full)` MUST come before `wait(mutex)`. Swapping them can deadlock — see the quiz.
      :::

      **Use case:** Kafka partitions — producers append to a partition while consumers read from it; the partition is the bounded buffer, and the semaphores keep producer/consumer rates in sync.

      ### Readers–Writers

      - Shared database: **readers** may read concurrently; **writers** need exclusive access.
      - **Readers-preference** — the first reader locks, the last reader unlocks; writers may starve.
      - **Writers-preference** — new readers wait once a writer is waiting; readers may starve.
      - Fair solutions use extra counters/semaphores or a monitor.

      **Use case:** an editor on a shared document — many viewers can read at once, but saving (writing) needs exclusive access.
  - type: markdown
    content: |
      ### Dining Philosophers

      Five philosophers sit at a round table with five chopsticks (one between each pair); each needs **both** chopsticks to eat. Naive 'pick left, then right' can deadlock when all five hold their left chopstick and wait for the right one.

      Fixes:
      - Allow at most **4 philosophers** at the table (one always finds both chopsticks free).
      - Pick up **both chopsticks atomically** (under a mutex).
      - **Odd/even ordering** — odd philosophers pick left first, even pick right first (breaks the cycle).

      **Use case:** the standard analogy for resource allocation — processes holding one resource while waiting for another, the exact setup that produces deadlocks.

      ### Monitors

      - High-level construct: a module whose methods are **automatically mutually exclusive** — the compiler inserts the lock for you.
      - **Condition variables** (`wait(c)`, `signal(c)`) let a thread sleep inside the monitor and be woken later.
      - vs semaphores: monitors are structured and harder to misuse (no scattered wait/signal pairs), but semaphores are more flexible and work in interrupt handlers.

      **Use case:** Java's `synchronized` / `ReentrantLock` + `Condition` implement a monitor — the basis of thread-safe task queues, connection pools, and message queues.
