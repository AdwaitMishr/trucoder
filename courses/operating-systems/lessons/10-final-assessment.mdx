  - type: mcq
    prompt: "Which statement about a process and its threads is TRUE?"
    options: ["A thread of a process has its own separate address space", "Threads of one process share the code, data and heap, but each thread has its own stack and register set", "A program stored on disk is already a process", "A process has no PCB until it has been scheduled at least once"]
    answer: 1
    explanation: "A program is a passive file on disk; a process is a program in execution, with its own address space, open files and a PCB (process control block). Threads are the unit of execution *inside* a process: they share the process's code, data and heap, but each thread gets its own stack, program counter and register set so it can run independently. Because the address space is shared, switching between threads of one process is cheaper than a full process context switch."
  - type: mcq
    prompt: "Which of the following state transitions is NOT valid for a process?"
    options: ["running → ready", "running → waiting", "waiting → ready", "ready → waiting"]
    answer: 3
    explanation: "Valid transitions: ready → running (scheduler dispatches), running → ready (preempted, e.g. the time slice expires), running → waiting (blocked on I/O or a semaphore), waiting → ready (I/O completed), new → ready and running → terminated. A process sitting in the ready queue has not been given the CPU yet, so it cannot start waiting for I/O — ready → waiting is impossible. Whenever a process leaves the CPU, the kernel saves its PCB (program counter, registers, stack pointer, state) and restores the next process's — that is a context switch."
  - type: mcq
    prompt: "In the many-to-one threading model (many user threads mapped onto a single kernel thread), what happens when one thread makes a blocking system call?"
    options: ["Only that thread blocks; the other threads of the process keep running", "The kernel moves the blocked thread onto another core", "The entire process blocks, because the kernel sees only one thread", "The process is terminated immediately"]
    answer: 2
    explanation: "In many-to-one, the kernel is aware of only one thread, so a blocking system call from any thread blocks the whole process — the siblings cannot run either. This model is cheap (thread management happens in user space) but offers no parallelism. One-to-one (each user thread maps to a kernel thread — the model used by Linux and Windows) lets one thread block without stopping the others, at higher kernel overhead; many-to-many is a compromise."
  - type: mcq
    prompt: "Four processes arrive at time 0 with CPU bursts: P1 = 4 ms, P2 = 3 ms, P3 = 1 ms, P4 = 2 ms. Under FCFS, what is the average waiting time?"
    options: ["3.50 ms", "4.25 ms", "4.75 ms", "5.50 ms"]
    answer: 2
    explanation: "FCFS runs in arrival order: P1 → P2 → P3 → P4. Completion times: P1 = 4, P2 = 4+3 = 7, P3 = 7+1 = 8, P4 = 8+2 = 10. Waiting = completion − burst: P1 = 0, P2 = 7−3 = 4, P3 = 8−1 = 7, P4 = 10−2 = 8. Total = 0+4+7+8 = 19, average = 19/4 = 4.75 ms. Notice how P3 and P4 wait behind P1's long burst — the convoy effect, which makes FCFS poor for interactive workloads."
  - type: mcq
    prompt: "The same four processes (bursts 4, 3, 1, 2, all arriving at time 0) are scheduled with Round Robin, quantum = 2 ms. In what order do they COMPLETE?"
    options: ["P1, P2, P3, P4", "P3, P4, P1, P2", "P4, P3, P2, P1", "P1, P4, P3, P2"]
    answer: 1
    explanation: "With quantum 2, each process gets at most 2 ms per turn, in ready-queue order: t=0–2 P1 (2 left), t=2–4 P2 (1 left), t=4–5 P3 finishes (burst 1 ≤ quantum), t=5–7 P4 finishes, t=7–9 P1 finishes, t=9–10 P2 finishes. Completion order: P3, P4, P1, P2. Round Robin is starvation-free and gives good response time, but its average turnaround is worse than SJF because long jobs are chopped into many slices."
  - type: mcq
    prompt: "With the same bursts (P1 = 4, P2 = 3, P3 = 1, P4 = 2) under non-preemptive SJF, what is the execution order and the total waiting time?"
    options: ["P1, P2, P3, P4 — total 19 ms", "P3, P4, P2, P1 — total 10 ms", "P3, P4, P2, P1 — total 4 ms", "P4, P2, P3, P1 — total 8 ms"]
    answer: 1
    explanation: "SJF sorts by burst length: P3(1) → P4(2) → P2(3) → P1(4). Completion times: P3 = 1, P4 = 1+2 = 3, P2 = 3+3 = 6, P1 = 6+4 = 10. Waiting = completion − burst: P3 = 0, P4 = 1, P2 = 3, P1 = 6. Total = 0+1+3+6 = 10 ms (average 2.5 ms — the minimum possible for this set). The catch: SJF (and its preemptive cousin SRTF) can starve long jobs; the standard remedy is aging — a waiting process's priority rises over time."
  - type: mcq
    prompt: "Two threads both execute `x = x + 1` on a shared variable x (initially 0) with no synchronization. Which outcome is possible?"
    options: ["x is always 2", "x is always 1", "x can be 1 or 2 depending on the interleaving", "x can never be read safely"]
    answer: 2
    explanation: "`x = x + 1` is three machine operations: read x, add 1, write back. If both threads read 0 before either writes, both write 1 — a lost update, so x ends at 1. If one thread's read–add–write completes before the other starts, x ends at 2. This nondeterminism is a race condition. The fix is a critical section protected by mutual exclusion (at most one thread inside), plus progress (a thread wanting in is not postponed forever while the section is free) and bounded waiting (a thread waits only a bounded number of entries by others)."
  - type: mcq
    prompt: "A bounded buffer of size N is shared by producers and consumers using three semaphores: mutex, empty, full. Which initial values are correct?"
    options: ["mutex = 0, empty = N, full = 0", "mutex = 1, empty = N, full = 0", "mutex = 1, empty = 0, full = N", "mutex = N, empty = N, full = 1"]
    answer: 1
    explanation: "empty counts free slots → starts at N; full counts filled slots → starts at 0; mutex guards the buffer → starts at 1 (a binary lock). Producer: wait(empty) → wait(mutex) → put → signal(mutex) → signal(full). Consumer: wait(full) → wait(mutex) → take → signal(mutex) → signal(empty). Order matters: doing wait(mutex) before wait(empty) deadlocks when the buffer is full."
  - type: mscq
    prompt: "Which statements about mutexes and semaphores are TRUE?"
    options: ["A counting semaphore initialized to k lets up to k threads enter the guarded region", "A mutex has ownership: only the thread that locked it may unlock it", "A semaphore's wait() never blocks a thread", "A binary semaphore and a mutex behave identically in every situation"]
    answer: [0, 1]
    explanation: "[0] Correct — wait() decrements the count and blocks only when it hits 0, so an initial value of k admits k threads. [1] Correct — mutexes are ownership-based; any thread can signal a semaphore. [2] Wrong — wait() blocks the caller when the count is 0; that blocking is exactly what provides synchronization. [3] Wrong — a mutex is a locking primitive with ownership, while a binary semaphore is a signaling primitive (e.g. 'task done' notifications); they are not interchangeable in general."
  - type: mcq
    prompt: "Which of the following is NOT one of Coffman's four necessary conditions for deadlock?"
    options: ["Mutual exclusion", "Hold and wait", "No preemption", "Priority scheduling"]
    answer: 3
    explanation: "The four necessary conditions are: mutual exclusion (resources are not shareable), hold and wait (a process holds resources while waiting for more), no preemption (resources cannot be forcibly taken away), and circular wait (a cycle of processes, each waiting on a resource held by the next). Priority scheduling is a CPU-scheduling policy from lesson 2 — it can cause starvation but is not a deadlock condition. To prevent deadlock you break any one of the four, e.g. a global resource ordering breaks circular wait."

    prompt: "Banker's algorithm: resources A = 10, B = 5, C = 7. Allocation — P0(0,1,0) P1(2,0,0) P2(3,0,2) P3(2,1,1) P4(0,0,2); Max — P0(7,5,3) P1(3,2,2) P2(9,0,2) P3(2,2,2) P4(4,3,3). Is the state safe, and what is a safe sequence?"
    options: ["Not safe — no process can finish", "Safe — P1, P3, P0, P2, P4", "Safe — P0, P2, P4, P1, P3", "Safe — P4, P2, P0, P3, P1"]
    answer: 1
    explanation: "Need = Max − Allocation: P0(7,4,3) P1(1,2,2) P2(6,0,0) P3(0,1,1) P4(4,3,1). Total allocated = (7,2,5), so Available = (10,5,7) − (7,2,5) = (3,3,2). Walk: P1 needs (1,2,2) ≤ (3,3,2) → finishes, Available = (5,3,2). P3 needs (0,1,1) ≤ (5,3,2) → Available = (7,4,3). P0 needs (7,4,3) ≤ (7,4,3) → Available = (7,5,3). P2 needs (6,0,0) ≤ (7,5,3) → Available = (10,5,5). P4 needs (4,3,1) ≤ (10,5,5) → Available = (10,5,7), the full total. Every step has a process whose need fits, so the state is safe; one safe sequence is P1 → P3 → P0 → P2 → P4."
  - type: mscq
    prompt: "Which statements about the resource-allocation graph (RAG) and deadlock are TRUE?"
    options: ["A cycle in the RAG is necessary for deadlock", "If every resource type has a single instance, a cycle in the RAG implies deadlock", "If a resource type has several instances, a cycle in the RAG always implies deadlock", "If the RAG has no cycle, the system cannot be deadlocked"]
    answer: [0, 1, 3]
    explanation: "[0] Correct — circular wait is one of the four necessary conditions, so no cycle ⇒ no deadlock. [1] Correct — with single-instance resource types, every process on the cycle is blocked on a resource held by another, so the cycle means deadlock. [3] Correct — since a cycle is necessary, its absence rules out deadlock. [2] Wrong — with multiple instances, a cycle can be broken because processes on it may still obtain the instances they need from the shared pool and finish; the cycle is necessary but not sufficient."
  - type: mcq
    prompt: "A system pages with a 4 KB page size. A process's page table maps: page 0 → frame 3, page 1 → frame 7, page 2 → frame 5, page 3 → frame 1. What physical address does logical address 8,692 translate to?"
    options: ["8,692", "16,884", "20,980", "29,172"]
    answer: 2
    explanation: "Page number = 8,692 ÷ 4,096 = 2 (2×4,096 = 8,192 ≤ 8,692 < 12,288). Offset = 8,692 − 8,192 = 500. Page 2 maps to frame 5, so physical = frame × page size + offset = 5 × 4,096 + 500 = 20,480 + 500 = 20,980. Distractors: 8,692 is the untranslated logical address; 16,884 would be frame 4 + offset 500 (frame 4 is not even in the table); 29,172 is frame 7 — page 1's frame, the wrong page."
  - type: mcq
    prompt: "A process references pages 1,2,3,4,1,2,5,1,2,3,4,5 with 3 frames and FIFO replacement. How many page faults occur?"
    options: ["8", "9", "10", "12"]
    answer: 1
    explanation: "FIFO evicts the oldest loaded page. Walk: 1 F, 2 F, 3 F → frames (1,2,3). 4 F evicts 1 → (2,3,4). 1 F evicts 2 → (3,4,1). 2 F evicts 3 → (4,1,2). 5 F evicts 4 → (1,2,5). 1 H, 2 H. 3 F evicts 1 → (2,5,3). 4 F evicts 2 → (5,3,4). 5 H. Total: 9 faults, 3 hits out of 12 references. Curiously, FIFO with 4 frames on this same string faults 10 times — more frames, more faults: that is Belady's anomaly, which LRU and Optimal never exhibit."
  - type: mcq
    prompt: "A system is thrashing. Which statement best describes what is happening and the right remedy?"
    options: ["The CPU is idle because all processes are deadlocked", "Processes spend more time servicing page faults than executing, because the combined working set of the running processes exceeds the available frames; reduce the degree of multiprogramming", "The disk scheduler is starving requests; increase the Round Robin quantum", "The page size is too large; halving it removes all page faults immediately"]
    answer: 1
    explanation: "Thrashing occurs when the sum of the working sets of all active processes exceeds the number of physical frames: each process keeps faulting on pages it just evicted, disk I/O explodes and CPU utilization collapses. Remedies: reduce the degree of multiprogramming (fewer processes fighting for frames), add physical memory, or use the working-set model so each process is granted enough frames for its working set. Deadlock is a different failure: processes block waiting for each other's resources, not on page faults."
  - type: mcq
    prompt: "Disk queue: 98, 183, 37, 122, 14, 124, 65, 67. The head starts at cylinder 53 and serves requests in arrival order (FCFS). What is the total head movement?"
    options: ["236", "490", "640", "708"]

  - type: mcq
    prompt: "Same queue (98, 183, 37, 122, 14, 124, 65, 67) with the head at 53, but now using SSTF (shortest seek time first). What is the total head movement and the service order?"
    options: ["236 — 65, 67, 37, 14, 98, 122, 124, 183", "640 — 98, 183, 37, 122, 14, 124, 65, 67", "236 — 37, 14, 65, 67, 98, 122, 124, 183", "182 — 65, 67, 98, 122, 124, 183, 37, 14"]
    answer: 0
    explanation: "SSTF always picks the nearest request. From 53: 65 (12) → 67 (2) → 37 (30) → 14 (23) → 98 (84) → 122 (24) → 124 (2) → 183 (59). Order: 65, 67, 37, 14, 98, 122, 124, 183.   - type: mcq
    prompt: "A parent process executes N fork() calls (and nothing else forks in the tree). How many child processes are created in total?"
    options: ["N", "N − 1", "2^N", "2^N − 1"]
    answer: 3
    explanation: "Each fork() doubles the number of processes, so after N forks there are 2^N processes in total (the original parent plus all descendants); children created = 2^N − 1. Example: N = 3 gives 8 processes and 7 children. fork() returns 0 in the child and the child's PID in the parent — the code after fork() runs in both, which is why the fork tree grows so fast."
  - type: mcq
    prompt: "A process issues a blocking read() for a file on disk. Which sequence correctly describes what the OS does? (Cross-cutting: processes + scheduling + I/O.)"
    options: ["The process busy-waits in the running state; the disk interrupt moves it to ready when done", "The process moves running → waiting, a context switch saves its PCB, the scheduler dispatches another process; on the disk interrupt it moves waiting → ready and is later dispatched", "The process is terminated and re-created when the I/O completes", "The process moves running → ready and keeps its time slice"]
    answer: 1
    explanation: "A blocking read is a system call: the process cannot proceed until the data arrives, so the kernel moves it running → waiting, performs a context switch (saving the PCB: program counter, registers, stack pointer) and lets the scheduler run the next ready process — the CPU is never idle. When the device controller finishes, it raises an interrupt; the handler moves the process waiting → ready, and the scheduler picks it up later. Device interrupts, not busy-waiting, are how the CPU learns that an I/O completed."
  - type: mcq
    prompt: "A child process exits, but its parent has not yet called wait(). Which statement is TRUE? (Cross-cutting: process lifecycle + fork/exec/wait.)"
    options: ["The child is removed from the system immediately, PCB included", "The child becomes a zombie: it is dead but keeps a PCB entry holding its exit status until the parent reaps it with wait()", "The kernel restarts the child automatically", "The child becomes an orphan and is killed by the kernel"]
    answer: 1
    explanation: "When a child exits, the kernel keeps a minimal PCB entry with the exit status so the parent can read it — that is a zombie (defunct) process: no CPU consumed, but a process-table slot held. The parent reaps it with wait()/waitpid(), freeing the entry. If the parent exits first, the child becomes an orphan and is adopted by init (PID 1), which reaps it later. A buggy parent that never calls wait() can leak zombies until the process table fills."

    prompt: "You type `ls` in a terminal and press Enter. Which sequence of steps is correct?"
    options: ["The shell forks, the child execs /bin/ls after a PATH search, ls runs via open/read/write syscalls, the shell wait()s, then prints the next prompt", "The kernel runs ls directly and only afterwards tells the shell", "ls is loaded by the boot firmware; the shell is not involved", "The shell reads the directory itself and prints it — no new process is created"]

    explanation: "The shell blocks on read() for your input, parses the line, calls fork() (a child copy of the shell), the child calls exec() — the kernel searches PATH and replaces the child's image with /bin/ls — ls issues open/read/write syscalls against the directory, then exits; the parent shell, blocked in wait(), reaps the child and prints the next prompt.   - type: mcq
    prompt: "A child process exits but its parent never calls wait(). What is the child, and how is its process-table slot eventually reclaimed?"
    options: ["It is an orphan, immediately reparented to init and reaped at once", "It is a zombie holding a PCB entry with its exit status; the slot is reclaimed only when the parent wait()s — a SIGCHLD handler reaps automatically, and if the parent dies first, init adopts and reaps it", "The kernel deletes its PCB immediately when it exits", "It keeps running in the background, consuming CPU, until killed"]
    answer: 1
    explanation: "A zombie is dead (no CPU) but its PCB entry, holding the exit status, must stay until the parent reads it with wait()/waitpid() — that is what reaps it. A SIGCHLD handler that calls waitpid() prevents zombie accumulation. If the parent dies first, the child becomes an orphan and init (PID 1) adopts and reaps it. Signals like SIGKILL do nothing to a zombie — there is nothing left to kill."
  - type: mcq
    prompt: "A web service receives 10,000 concurrent requests. Why is a thread pool usually better than creating a fresh thread per request?"
    options: ["Thread creation costs time, each thread reserves stack memory, and thousands of runnable threads oversubscribe the cores — context switches and cache/TLB misses dominate; a pool of N fixed workers processes tasks from a queue", "Threads cannot share state, so pools are the only way to make them cooperate", "A pool can only ever run one request at a time", "Thread pools automatically prevent deadlocks"]
    answer: 0
    explanation: "Thread-per-request is unbounded: per-thread creation/destruction cost, ~8 MB default stack reservation per thread, and once runnable threads far exceed cores the scheduler thrashes — switching, cache and TLB misses dominate. A pool creates N workers once and feeds them from a task queue: bounded parallelism, thread reuse, and backpressure when the queue fills. Pools don't solve sharing (threads already share the address space) or deadlock (workers can still deadlock)."
  - type: mcq
    prompt: "Reference string 2,3,2,3,4 with 2 frames under LRU page replacement. How many page faults occur?"
    options: ["2", "3", "4", "5"]
    answer: 1
    explanation: "Walk: 2 F → frames [2]. 3 F → [2,3]. 2 H (moves to most-recent end → [3,2]). 3 H (→ [2,3]). 4 F — both frames full, evict the least-recently-used: 3 was touched at step 4, 2 at step 3, so 2 is evicted → [3,4]. Faults = 2, 3, 4 = 3. LRU counts a fault only when the page is not resident, and every hit promotes the page to most-recently-used."
