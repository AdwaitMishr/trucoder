  - type: markdown
    content: |
      A **deadlock** is a state where every process in a set is waiting for an
      event that only another process in the set can cause — typically the
      release of a resource. Everyone waits, nobody progresses.

      ## Coffman's four necessary conditions

      All four must hold **simultaneously** for deadlock to occur:

      - **Mutual exclusion** — each resource is held by one process at a time.
      - **Hold and wait** — a process holding resources requests more.
      - **No preemption** — resources are released only voluntarily.
      - **Circular wait** — a closed chain P1 → R1 → P2 → R2 → … → P1 exists.

      Break any one condition and deadlock becomes impossible.

      **Use case:** database transactions use two-phase locking (2PL) — locks
      are held until commit, which *invites* deadlocks, so the DB's deadlock
      detector breaks cycles; kernels and the JVM (`synchronized`) impose a
      global lock ordering so a circular wait cannot even form.

  - type: markdown
    content: |
      ## Prevention — break one condition

      | Condition | How to break it |
      |---|---|
      | Mutual exclusion | **Spooling** (printers); atomic read-modify-write ops |
      | Hold and wait | **Request all resources at once**, or release before requesting |
      | No preemption | **Preempt** — take the resource away, roll the holder back |
      | Circular wait | **Total resource ordering** — acquire in a fixed global order |

      :::tip
      Resource ordering is the cheapest, most common fix: if every lock is
      acquired in the same global order (always `mutex_a` before `mutex_b`),
      no cycle of waiters can form.
      :::

      **Use case:** Linux kernel lock-ordering rules, Java code-review
      checklists ("never hold lock A while taking lock B out of order"), and
      database 2PL all apply these ideas.

  - type: markdown
    content: |
      ## Detection — resource allocation graph (RAG)

      A RAG has two node types: processes (circles) and resources (squares).
      Edge P → R means *P requests R*; edge R → P means *R is allocated to P*.

      - **Single-instance resources:** a cycle is **necessary AND sufficient**
        for deadlock.
      - **Multi-instance resources:** a cycle is necessary but **not
        sufficient** — a cycle can exist without deadlock.

      For multi-instance systems use a **wait-for graph**: processes as nodes,
      edge P1 → P2 means *P1 waits for a resource P2 holds*. A cycle in the
      wait-for graph means deadlock.

      **Use case:** distributed databases build wait-for graphs across nodes
      to detect global deadlocks — a cycle spanning machines is invisible to
      any single node's local check.

  - type: markdown
    content: |
      ## Avoidance — Banker's algorithm

      Prevention is too pessimistic; **avoidance** refuses only the requests
      that would lead to deadlock. A state is **safe** if some order exists in
      which every process can finish (a *safe sequence*). Banker's grants a
      request only if the *resulting* state is still safe — it needs each
      process to declare its **maximum need in advance**.

      - `Available` — free units of each resource type
      - `Allocation` — units held by each process
      - `Max` — units a process may ever need
      - `Need = Max − Allocation`; `Work` = running copy of `Available`

      **Worked example** (3 resource types, 5 processes):

      | Process | Allocation | Max | Need |
      |---|---|---|---|
      | P0 | 0 1 0 | 7 5 3 | 7 4 3 |
      | P1 | 2 0 0 | 3 2 2 | 1 2 2 |
      | P2 | 3 0 2 | 9 0 2 | 6 0 0 |
      | P3 | 2 1 1 | 2 2 2 | 0 1 1 |
      | P4 | 0 0 2 | 4 3 3 | 4 3 1 |

      `Available = [3, 3, 2]`. Safety check:

      1. P1: need [1,2,2] ≤ [3,3,2] ✓ → Work = [3,3,2] + [2,0,0] = **[5,3,2]**
      2. P3: need [0,1,1] ≤ [5,3,2] ✓ → Work = [5,3,2] + [2,1,1] = **[7,4,3]**
      3. P4: need [4,3,1] ≤ [7,4,3] ✓ → Work = [7,4,3] + [0,0,2] = **[7,4,5]**
      4. P0: need [7,4,3] ≤ [7,4,5] ✓ → Work = [7,4,5] + [0,1,0] = **[7,5,5]**
      5. P2: need [6,0,0] ≤ [7,5,5] ✓ → done.

      Safe sequence: **P1 → P3 → P4 → P0 → P2** — the state is safe.

      :::warning
      A request is granted only if the *resulting* state is still safe.
      Banker's is rarely used in real kernels — processes rarely know their
      true maximum need in advance — but it is a classic interview question.
      :::

      **Use case:** credit-based resource managers that pre-declare demand
      (memory pools, admission control) use the same "refuse if it breaks
      safety" idea.

  - type: markdown
    content: |
      ## Recovery from deadlock

      Detect first (cycle in the RAG for single-instance; cycle in the
      wait-for graph otherwise), then recover:

      - **Process termination** — abort all deadlocked processes (simple,
        drastic) or abort one at a time until the cycle breaks (each abort
        frees its resources).
      - **Resource preemption** — take a resource from a victim and give it
        to another; the victim rolls back. Risk: **starvation** if the same
        process keeps getting picked — use a cost metric (age, resources
        held).

      :::example
      A DBMS detects a lock cycle between two transactions, aborts the younger
      one and retries it — process termination plus a cost metric, exactly the
      textbook recipe.
      :::

      **Use case:** distributed deadlock detection in multi-node databases
      (wait-for graphs), lock timeouts in Java (`tryLock` with a timeout
      instead of blocking forever), watchdog timeouts in microservices.
