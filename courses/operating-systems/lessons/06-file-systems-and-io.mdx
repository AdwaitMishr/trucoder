      ## File allocation methods

      | Method | Pros | Cons |
      |---|---|---|
      | **Contiguous** | Fast random access, minimal overhead | External fragmentation; hard to grow |
      | **Linked** | No fragmentation; files grow freely | Sequential only — random access is O(n); pointer per block |
      | **Indexed** | Random access + easy growth | Index-block overhead (multi-level indexes for big files) |

      FAT (DOS/Windows) is **linked** allocation with the pointer chain kept
      in a table in memory instead of inside blocks.

      **Use case:** ISO images and swap files are contiguous; FAT/exFAT USB
      sticks are linked-via-table; ext4 and NTFS are indexed (extent-based) —
      random access without external fragmentation.

      ## Directory structures

      - **Single-level** — one directory for everyone (name collisions).
      - **Two-level** — one directory per user.
      - **Tree** — hierarchical; the standard Unix/Windows model.
      - **Acyclic graph** — tree + shared subdirectories/files (hard links,
        symlinks); **reference counting** prevents freeing shared files that
        are still referenced.
      - **General graph** — links can create **cycles**; needs garbage
        collection or cycle detection.

      **Use case:** `ln` (hard link) gives a file a second name pointing at
      the same inode — the directory tree becomes an acyclic graph and
      deleting one link just drops a reference count.

      ## Disk scheduling

      - **FCFS** — serve in arrival order; fair, poor total movement.
      - **SSTF** — always the closest request; efficient but can **starve**
        far requests.
      - **SCAN (elevator)** — sweep to one end, then reverse; no starvation,
        uneven waits at the ends.
      - **C-SCAN** — sweep one way only, then jump back to the start; uniform
        wait times.
      - **LOOK / C-LOOK** — like SCAN/C-SCAN but only travel as far as the
        last request in each direction.

      **Worked example** — queue `98, 183, 37, 122, 14, 124, 65, 67`, head
      starts at cylinder **53**:

      **FCFS** = |53−98| + |98−183| + |183−37| + |37−122| + |122−14| +
      |14−124| + |124−65| + |65−67| = 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2
      = **640**

      **SSTF** = 53→65 (12) → 67 (2) → 37 (30) → 14 (23) → 98 (84) → 122 (24)
      → 124 (2) → 183 (59) = **236**

      **SCAN** toward 199: up 53→65 (12) → 67 (2) → 98 (31) → 122 (24) →
      124 (2) → 183 (59) → 199 (16) = 146, then down 199→37 (162) → 14 (23) =
      185 → total **331**

      **C-SCAN** toward 199: same upward sweep (146), wrap to 0, then 0→14
      (14) → 37 (23): **183** after the wrap (382 if the 199→0 jump counts).

      :::tip
      Draw the cylinder axis, mark head + requests, trace the path — the
      total is the length of the path you drew.
      :::

      **Use case:** elevator algorithms are real: disk controllers and NVMe
      SSD schedulers reorder requests SSTF/SCAN-style because the bottleneck
      is head movement / command overhead.

      ## Inodes

      An **inode** stores a file's metadata: mode/type, owner, group, size,
      timestamps, and **block pointers**:

      - 12 **direct** pointers — 12 × 4 KiB = 48 KiB for small files
      - 1 **single-indirect** block — 1024 × 4 KiB = 4 MiB
      - 1 **double-indirect** — 1024² × 4 KiB = 4 GiB
      - 1 **triple-indirect** — 1024³ × 4 KiB = 4 TiB

      So the max file size is ≈ **4 TiB** (4 KiB blocks, 4-byte pointers —
      4 KiB ÷ 4 B = 1024 pointers per block) — the cap comes from pointer
      arithmetic, not from the data. Directories
      map name → inode number; the inode holds everything else.

      **Use case:** ext4 uses inodes; FAT has none (the directory entry holds
      everything — weaker metadata, no hard links). `stat` prints the inode
      metadata.

      ## fork(), exec(), wait()

      - **fork()** clones the process: returns the **child's PID to the
        parent**, **0 to the child**, −1 on failure. Memory is
        **copy-on-write** — pages are shared until someone writes.
      - **N fork() calls from one process → 2^N processes** (2^N − 1
        children).
      - **exec()** replaces the process image (code + data) with a new
        program; same PID. fork + exec = run a new program.
      - **wait()** blocks the parent until a child exits and **reaps** it.
        - **Zombie** — child exited, not yet reaped (PCB still in the table).
        - **Orphan** — parent died first; child is **reparented to init**
          (PID 1), which reaps it.

      **Use case:** every shell pipeline (`ls | grep foo`) is fork + exec
      with a pipe between the two processes; PostgreSQL's buffer manager
      batches and reorders I/O the way a disk scheduler does.
