      ### IPC mechanisms — the comparison

      Processes are isolated; **IPC (inter-process communication)** is how they
      exchange data. Know the five, one line each, plus the use case:

      - **Anonymous pipes** — an in-memory *byte stream* created by `pipe()`;
        inherited across `fork()`, so typically parent ↔ child. Use case:
        shell pipelines (`ps aux | grep chrome`).
      - **Named pipes (FIFOs)** — a pipe with a *name* in the filesystem
        (`mkfifo`); two unrelated processes open it like a file. Use case:
        a logger daemon and any process on the same host.
      - **Shared memory** — a region of memory mapped into two+ address spaces
        (`mmap` / SysV `shmget`). **Fastest**: no copy through the kernel.
        Use case: databases' buffer pools, hot IPC paths.
      - **Message queues** — the kernel delivers discrete *messages* (typed
        chunks with priority); works between unrelated processes. Use case:
        job/task dispatch between services.
      - **Sockets** — byte stream (TCP) or datagram (UDP) over a port; the only
        IPC that works **across machines** (and on localhost too). Use case:
        client-server apps, microservices.

      :::tip **Interview question: pipes vs shared memory — when do you use each?**
      "A pipe is a kernel-mediated byte stream — safe (no synchronization
      needed), but every byte is copied user → kernel → user, so it suits
      small, streaming data like shell pipelines and parent–child
      communication. Shared memory is a region both processes map into their
      address spaces: zero kernel copies, so it's the fastest IPC, but the
      processes must synchronize access themselves (mutex/semaphore) — use it
      for large, frequent, hot-path data like a database buffer pool."
      :::

      ### Thread pools — why not 1000 threads?

      Thread-per-request feels simple, but under load it collapses:

      - **Creation/destruction cost** — a thread is not free: kernel object,
        stack and TLS must be allocated and torn down,
      - **stack memory** — each thread reserves its own stack (default ~8 MB
        virtual on Linux); 1000 threads ≈ 8 GB of address space,
      - **context-switch overhead** — with far more runnable threads than
        cores, the scheduler thrashes: switches dominate useful work, cache and
        TLB are flushed constantly (oversubscription).

      A **thread pool** = a **fixed number of worker threads** + a **task
      queue**:

      1. Tasks are submitted to the queue (not to a thread).
      2. Idle workers dequeue and run them, one at a time.
      3. Workers are created once and reused — no per-request creation cost,
         bounded resource usage, parallelism capped at the pool size.

      **Async vs threads:** async I/O (event loop — Node.js) is *one* thread
      that multiplexes many in-flight I/O operations; it shines for I/O-bound
      work. Threads are for parallelism (CPU-bound work, blocking libraries).
      Pools sit in the middle: bounded parallelism with a queue.

      :::tip **Interview question: why a thread pool instead of a thread per request under load?**
      "Creating a thread per request is unbounded: each thread costs stack
      memory and, once runnable threads far exceed cores, the scheduler spends
      more time context-switching than working — latency and throughput both
      degrade, and memory can be exhausted. A pool caps the damage: N workers
      created once, a task queue between the request handler and the workers,
      so resource usage is bounded and threads are reused. It also gives you a
      natural place for backpressure — the queue grows instead of the system
      melting."
      :::

      ### Producer-consumer — the archetype

      The task queue *is* a **bounded-buffer producer-consumer** (lesson 3):
      producers `enqueue` tasks, workers `dequeue`. Same skeleton, three
      semaphores: `mutex = 1` (guard), `empty = N` (free slots), `full = 0`
      (filled slots) — or a mutex + condition variable. If the queue is empty
      workers block (`wait(full)`); if it's full producers block
      (`wait(empty)`). **Any thread-pool design is this pattern in disguise.**

      ### Deadlock in real systems

      - **Lock ordering** — if every path acquires locks in the same global
        order (A before B), circular wait is impossible (breaks Coffman's
        condition #4 — lesson 4).
      - **Timeouts** — `try_lock` with a timeout instead of blocking forever;
        a deadlocked thread backs off instead of hanging the pool.
      - Avoid nested locks; hold locks briefly; never call unknown/user code
        while holding a lock.

      ### C++ one-liners

      - **`std::thread`** — a native OS thread (one-to-one model).
      - **`std::async`** — higher-level: launch a task, get a `std::future`
        back; the runtime may run it on a pool thread — prefer it over raw
        threads for fire-and-collect work.
