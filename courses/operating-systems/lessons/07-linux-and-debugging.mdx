      ### Inspecting processes & resources

      - **`ps aux` / `ps -ef`** — one-shot snapshot of every process (PID, CPU%,
        MEM%, state, command). `ps -e -o pid,stat,cmd` picks columns.
      - **`top` / `htop`** — live, refresh-every-second view; sort by CPU or
        memory, kill from inside the UI.
      - **`free -h`** — memory in one glance: total / used / free, plus the
        **buff/cache** line (page cache — reclaimable, so "free" is low but
        memory is fine).
      - **`/proc` filesystem** — a *virtual* filesystem: the kernel exposes its
        data structures as files. `/proc/<pid>/stat`, `/proc/<pid>/status`,
        `/proc/meminfo`, `/proc/loadavg`. `ps`/`top` just read these files.
      - **grep pipeline** — `ps aux | grep chrome` pipes `ps`'s output into
        `grep` — an anonymous pipe (lesson 8) joining two processes.

      **Use case:** an interviewer asks "the box is slow — where do you start?"
      The answer is `top` (CPU/memory hogs) → `free -h` (memory pressure /
      swap) → `ps aux --sort=-%cpu` (exact culprits) → `/proc/<pid>/` for
      detail.

      :::tip **Interview question: how do you check CPU and memory usage on Linux?**
      One-liner: "`top`/`htop` for live CPU+memory per process, `free -h` for
      system memory totals, `ps aux` for a snapshot, and everything underneath
      is just reading `/proc` — virtual files the kernel generates on the fly."
      :::

      ### Signals & kill

      A **signal** is a tiny async notification the kernel delivers to a
      process. `kill` is the command that *sends* signals (the name is a
      historical accident — it doesn't only kill).

      - **SIGTERM (15)** — polite "please terminate": a handler can catch it,
        flush, clean up, then exit. The default action is termination.
      - **SIGKILL (9)** — cannot be caught, blocked or ignored; the kernel
        terminates the process directly. Last resort.
      - **SIGINT (2)** — Ctrl+C on the terminal; catchable.
      - **Default vs handled** — every signal has a default action (usually
        terminate); a process may install a handler to override it. SIGKILL and
        SIGSTOP have no handler — the kernel enforces them.
      - `kill -TERM <pid>` → give it a chance; `kill -9 <pid>` → guaranteed.

      **Use case:** graceful shutdown of a server = catch SIGTERM, drain
      in-flight requests, close the socket, exit(0) — that's how Kubernetes
      stops a pod before SIGKILL as a fallback.

      ### Zombie vs orphan — the classic question

      - **Zombie** — a child that *exited*, but the parent hasn't called
        `wait()` yet. The kernel keeps a minimal PCB entry (PID, exit status)
        so the parent can read it. `ps` shows state **`Z` / defunct**. No CPU
        is consumed, but the process-table slot is held.
      - **Orphan** — the *parent* died first. The kernel reparents the child to
        **init (PID 1)** (or a subreaper), which adopts it and reaps it on
        exit.

      **Cleaning up a zombie:** you cannot kill it — it's already dead.
      - The parent must call `wait()`/`waitpid()` (reaps the child).
      - Better: a **SIGCHLD handler** that reaps children as they exit prevents
        accumulation.
      - Blunt fix: kill the parent — init adopts the zombie and reaps it.

      :::tip **Interview question: zombie vs orphan — and how do you debug a zombie?**
      "A zombie is an exited child whose parent never called wait(): it keeps a
      PCB slot with its exit status (`ps` shows Z/defunct), it uses no CPU, and
      `kill -9` won't remove it because there is nothing to kill. Debug by
      finding the zombie's PPID with `ps -o pid,ppid,stat`, look at that parent
      — it's not reaping — and fix it to call wait()/waitpid() or install a
      SIGCHLD handler; if the parent is broken beyond repair, killing it lets
      init adopt and reap the zombie. An orphan is the opposite case: the
      parent died first, so the kernel reparents the child to init."
      :::

      ### strace — watch the syscalls

      **`strace -f ./prog`** traces every system call a program makes — the
      exact boundary between user space and the kernel: `open()`, `read()`,
      `write()`, `mmap()`, `fork()`, `execve()`… It answers "why is this
      program slow / what file is it touching / why does it fail" — you see the
      kernel calls, arguments and return values (including `ENOENT`).

      **Use case:** "the app hangs on startup" → `strace` shows it blocking on
      `read()` of a config file that doesn't exist, or retrying a socket
      connect.

      ### The viral walkthrough — "what happens when you type `ls`?"

      1. The **shell prints its prompt** and blocks on `read()` of your stdin.
      2. You type `ls` + Enter; the shell **reads the line** and parses it into
         a command + arguments.
      3. The shell calls **`fork()`** — a new child process that is a copy of
         the shell (same code, memory, open files).
      4. The child calls **`exec()`** (`execve`): the kernel **searches PATH**
         for `ls` (e.g. `/bin/ls`), then *replaces* the child's image with the
         `ls` binary — fresh address space, entry point at `main()`.
      5. `ls` executes, issuing syscalls: **`open()`** the directory,
         **`read()`** entries, **`write()`** the names to the terminal (stdout).
      6. `ls` **exits** — its exit status goes to the kernel.
      7. The parent shell (which was blocked in **`wait()`**) wakes, reaps the
         child (no zombie), and **prints the next prompt**.

      Every step crosses the user/kernel boundary through a syscall — that is
      the whole point of the exercise: fork/exec/wait (lesson 6) + syscalls +
      the shell as an ordinary program.

      :::tip **Interview answer, 30 seconds**
      "The shell forks a child, the child execs /bin/ls after a PATH search,
      ls runs via open/read/write syscalls and exits; the shell is blocked in
      wait() the whole time, reaps the child, and prints the next prompt."
      :::
