      ### Why a database?

      A **DBMS** persists data across sessions and handles organization, access, integrity, and concurrency. Plain text files fail because parsing is slow, structure can't be enforced, and concurrent writes race (two users updating a file at the same millisecond — one overwrites the other).

      - **RAM vs disk** — RAM is fast but small and expensive (Redis lives here); disk is slow but huge and cheap (Postgres lives here).
      - **Relational (SQL)** — tables/rows, strict schema, integrity enforced in the DB; ideal for financial ledgers and e-commerce. Postgres is the default choice: open source, SQL-compliant, reliable, best-in-class `jsonb`.
      - **NoSQL** — collections/documents, flexible schema, integrity at the application layer; good for CMS content and unstructured logs.

      **Use case:** checkout touches users, products, stock, and money — exactly the relational, transaction-safe workload SQL was built for.

      ### E-commerce schema — entities, keys, why

      - **users** — `id` (uuid PK), `email` (UNIQUE), `password_hash`, `role`.
      - **products** — `id`, `name`, `price` (`numeric` — exact for money), `stock_available`.
      - **carts** — `id`, `user_id` (FK → users, one cart per user).
      - **cart_items** — `cart_id` FK, `product_id` FK, `qty` (many-to-many between carts and products).
      - **orders** — `id`, `user_id` FK (one-to-many), `status` (ENUM: pending / paid / shipped / cancelled), `total`.
      - **order_items** — `order_id` FK, `product_id` FK, `qty`, `unit_price` (snapshot the price at purchase — prices change later).

      Why it's shaped this way:

      - **Foreign keys** enforce referential integrity — an `order_items` row can't point at a missing product. `ON DELETE RESTRICT` blocks deleting a user who has orders; `ON DELETE CASCADE` wipes children automatically (cart items).
      - **Enums and CHECK constraints** enforce business rules inside the DB (`status` values, `qty >= 0`).
      - **uuid** primary keys beat auto-increment `serial` ids: unguessable, generated anywhere, no enumeration.
      - **`numeric` for money, never `float`** (binary rounding errors in payments); `text` over arbitrary `varchar(255)`.

      **Use case:** the catalog service reads products while the order service writes orders — the shared schema keeps both consistent.

      ### SQL basics

      - **SELECT / JOIN** — `SELECT u.email, o.total FROM users u JOIN orders o ON o.user_id = u.id` fetches a user and their orders in one query instead of two. Use `LEFT JOIN` when you want users even without orders.
      - **INSERT / UPDATE** — `INSERT INTO products (name, price) VALUES ($1, $2)`. **Always parameterized** — `$1` treats input as data, not code. A concatenated string like `'; DROP TABLE users; --` is how databases get wiped (SQL injection).
      - **Transactions** — group statements: `BEGIN; ... COMMIT;` or `ROLLBACK` on error. Without them, a crash mid-checkout leaves half-written state.
      - **Migrations** — never hand-run `CREATE TABLE` in production; versioned `.sql` files (up/down) applied in order, tracked in a `schema_migrations` table.

      **Use case:** "add to cart" is one parameterized INSERT; "checkout" is a multi-statement transaction.

      ### ACID applied to checkout

      - **Atomicity** — order + payment + stock decrement are all-or-nothing: any failure rolls everything back — no partial order.
      - **Consistency** — constraints hold before and after: stock never goes negative, order totals match items.
      - **Isolation** — two users check out the last item in parallel: row locks serialize them — one succeeds, the other sees the updated stock and is rejected.
      - **Durability** — a committed order survives a power cut; it is on disk.

      ### Worked example — the checkout transaction

      1. `BEGIN;`
      2. `SELECT stock_available FROM products WHERE id = $1 FOR UPDATE;` — lock the stock row.
      3. If `stock < qty` → `ROLLBACK;` and return "insufficient stock".
      4. `INSERT INTO orders (user_id, status, total) VALUES ($1, 'pending', $2) RETURNING id;`
      5. `INSERT INTO order_items (order_id, product_id, qty, unit_price) VALUES (...);`
      6. `UPDATE products SET stock_available = stock_available - $qty WHERE id = $1;`
      7. `COMMIT;`

      The `FOR UPDATE` lock is the isolation trick: the second checkout of the same product blocks until the first commits, then reads the real remaining stock.

      ### Connection pooling, indexes, scale

      - **Connection pooling** — opening a Postgres connection costs a handshake, auth, and memory. A pool reuses a fixed set of connections. **Pool exhaustion = outage**: if requests grab connections and never return them (slow queries, leaks), everything else queues and times out — the DB is healthy but the app is down. Rule of thumb: tens of connections per instance (Postgres is happiest around 50–100), never thousands.
      - **ORM vs raw SQL** — ORMs (Prisma, TypeORM) give type-safe models and migrations at the cost of control; the raw `pg` driver is explicit SQL with zero magic. Hot paths get raw SQL or a query builder.
      - **Indexes** — a B-tree index turns a full sequential scan into a textbook-index lookup. Index the hot paths: `products.id` (PK — automatic), `orders.user_id` (a FK is **not** indexed automatically — add it), `orders.status` for list filters. Trade-off: every index slows INSERT/UPDATE — index only hot columns.
      - **Read replicas** — one write leader plus many read replicas: reads scale horizontally while writes stay on the leader.

      **Use case:** Black Friday traffic reads the catalog from replicas; checkout writes go through a pooled connection to the leader.

      ### Interview questions

      :::tip
      **Interview question:** Walk me through the schema for an e-commerce database.
      — users, products, carts, cart_items, orders, order_items. users has 1:N orders; orders has 1:N order_items; order_items links products (N:M) via product_id and snapshots unit_price; carts is 1:1 with users and cart_items links carts to products. Money is `numeric`, ids are `uuid`, statuses are enums, foreign keys enforce integrity, and I'd index users.email, orders.user_id, and orders.status.
      :::

      :::tip
      **Interview question:** Why do transactions matter for checkout?
      — Checkout mutates several rows: order, order_items, stock, payment. Without a transaction, a crash between statements leaves an order without items, or stock decremented without payment. BEGIN/COMMIT makes the batch atomic, ROLLBACK undoes everything on failure, `SELECT ... FOR UPDATE` gives isolation when two users buy the last item, and COMMIT makes it durable.
      :::

      :::tip
      **Interview question:** What happens when a connection pool is exhausted, and how do you avoid it?
      — Every connection is busy, so new requests block or time out — the database is fine but the app looks dead. Avoid it by sizing the pool sensibly (tens, not thousands), keeping queries fast (indexes, no N+1), setting connection timeouts, and monitoring slow queries that hog connections.
      :::
