    content: |
      A backend is a computer listening for requests — HTTP, WebSocket, gRPC,
      or similar — through an **open port** (like `80` or `443`) reachable
      over the internet. Clients and frontends connect to it to send data or
      receive data.

      It is called a **server** because it *serves* content — static images,
      JS/HTML files, JSON data — and processes the inputs clients send it.

      ## Key points

      - A backend is a **process on a machine with an open port** — that's the
        whole traditional definition.
      - It **serves content** (files, JSON) and **processes input** (orders,
        logins, likes).
      - Clients (browsers, mobile apps) initiate; the server listens and
        responds.

      **Use case:** when your browser opens `shop.example.com`, the product
      catalog, the cart badge, and the "place order" button all talk to the
      backend that serves the JSON and executes the purchase.

      ## The end-to-end request lifecycle

      A request does not teleport to your code. It crosses real infrastructure.
      Here is the full journey from a browser to an app server:

      1. **Browser** — you type `api.shop.com` and hit Enter.
      2. **DNS server** — the Domain Name System resolves the domain. An
         **A record** maps the human-readable name to the server's public IP
         address.
      3. **Firewall / security group** — before anything reaches the operating
         system, a cloud firewall checks the destination port. Only explicitly
         open ports pass: `443` (HTTPS), `80` (HTTP), `22` (SSH). Wrong port?
         The request is dropped right there.
      4. **Reverse proxy (e.g. NGINX)** — terminates TLS/SSL and routes
         traffic by domain name to the right local port (e.g.
         `localhost:3001`).
      5. **Application server** — your Node.js (or other) process, usually
         kept alive by a process manager like PM2, executes the code and sends
         the response back down the same chain.

      :::tip
      **Interview question:** Walk me through what happens when a request hits
      a backend.
      — The browser resolves the domain through a DNS A record to the server's
      public IP. The request passes a cloud firewall/security group, which
      only allows open ports (80/443). A reverse proxy like NGINX terminates
      SSL and forwards to the app server on a local port. The app server
      executes the handler, and the response travels back down the chain to
      the browser.
      :::

      ## The client-server model

      Communication is **always initiated by the client** — a browser or a
      mobile app. The server hosts resources and *passively waits* for
      requests, processes them, and responds.

      HTTP is the default protocol, but the same model holds for:

      - **WebSocket** — a long-lived, bidirectional connection (chat, live
        order tracking) over the same port.
      - **gRPC** — binary, high-performance remote procedure calls between
        services.

      Whatever the protocol, the shape is identical: a client connects to a
      listening process on a port.

      **Use case:** your storefront's live "order status" ticker uses a
      WebSocket connection to the same backend that serves the REST API — one
      server, several protocols, same machine.

      ## Why centralized state forces backend logic

      Your frontend is customized for *you*. A backend must maintain the
      global state of **all users at once** — that is why some things can
      only live server-side:

      - **The shared cart** — the same cart on your phone and laptop must be
        the same cart. It lives in the backend, not in one browser tab.
      - **Sessions & identity** — "logged in" is a server-side fact, not a UI
        flag.
      - **The database** — writes are coordinated centrally: one user's
        "like" updates the post, notifies the owner, and persists — all
        orchestrated by the backend.

      Condense the whole purpose of a backend into one word: **data**.
      Backends fetch, receive, persist, and manage data securely.

      **Use case:** adding an item to your cart on the mobile app and
      finishing the checkout on your laptop works because the cart state
      lives in the backend's database — not in either device.
  - type: markdown
    content: |
      ## Why backend logic can't just live in the frontend

      Why not connect the browser straight to the database? Because the
      browser is the runtime for frontend code, and it is a deliberately
      restricted one:

      - **Security & sandboxing** — browsers isolate untrusted remote code:
        no filesystem access, no environment variables, no writing logs. A
        backend needs system-level access to function.
      - **CORS & external APIs** — browsers block cross-origin requests
        unless the target API explicitly allows them. Backends can call
        dozens of third-party APIs (payment providers, shipping carriers)
        with no browser restrictions.
      - **Databases & connection pooling** — servers use native drivers and
        keep a *pool* of reusable connections to handle thousands of requests
        per second. If every browser opened its own database connection, the
        database would be overwhelmed instantly.
      - **Computing power** — clients range from high-end desktops to old
        smartphones. Heavy logic on weak devices means lag, battery drain,
        and crashes. A backend can be scaled vertically (more CPU/RAM) to
        serve millions.

      :::tip
      **Interview question:** Why can't backend logic just live in the
      frontend?
      — Four reasons: the browser is a sandbox (no filesystem or environment
      access); CORS blocks cross-origin API calls; browsers lack native
      database drivers and connection pooling, so direct DB access would
      crush the database; and client hardware is unpredictable, while a
      backend can be scaled vertically.
      :::

      :::example
      **Worked example — add to cart, end to end.** You tap "Add to cart" on
      `shop.example.com`. The browser sends `POST /api/cart/items`. DNS
      resolves the domain to the server's public IP; the security group lets
      the request through port 443; NGINX terminates TLS and forwards to the
      Express app on `localhost:3001`; the cart controller validates the
      payload, the cart service writes the item to PostgreSQL, and
      `201 Created` with the updated cart JSON travels back to your browser —
      which now shows the badge `1`.
      :::
