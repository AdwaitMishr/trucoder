      # Project 1: Cart Domain

      **Context.** You are building the storefront backend of a small e-commerce
      site ("Shop"). This lesson is the first of a four-lesson project arc:
      cart domain → checkout pipeline → rate limiter → Docker assembly. By the
      end of lesson 13 you will have shipped the whole API. Today you build the
      **cart domain**: the pure logic that the `CartService` runs on every
      "add to cart" request.

      **What you are building this step.** The heart of the cart is one rule:
      *an item already in the cart is merged, not duplicated*. Two requests for
      the same product must produce one cart line with summed quantity — never
      two lines. Every line carries its unit price, and the service derives the
      **line total** (`qty × price`) so the controller never does arithmetic.

      **Acceptance criteria**

      - `POST /api/cart/items` with `{itemId, qty}` adds or merges a line.
      - `GET /api/cart` returns cart rows, each with a line total.
      - `DELETE /api/cart/items/:id` removes a line.
      - Merging an existing line keeps its original unit price (the price
        snapshot from when it was first added).
      - The merge + line-total logic is a pure function — no HTTP, no SQL —
        so it is trivially unit-testable. That pure function is your graded
        exercise.

      ## Deliverables — where this logic lives in the real project

      The request flows **route → controller → service → repository**. The
      controller parses the request and formats the response; the service owns
      the domain rule; the repository owns the SQL. The graded `solve()` is the
      `mergeLine` step inside `CartService.addItem`.

      ```js
      // routes/cart.js — mounted at /api/cart
      const router = require('express').Router();
      const cartController = require('../controllers/cartController');

      router.post('/items', cartController.addItem);        // POST /api/cart/items
      router.get('/', cartController.getCart);              // GET  /api/cart
      router.delete('/items/:id', cartController.removeItem); // DELETE /api/cart/items/:id

      module.exports = router;
      ```

      ```js
      // controllers/cartController.js — thin: parse, delegate, respond
      const cartService = require('../services/cartService');

      async function addItem(req, res, next) {
        try {
          const { itemId, qty, price } = req.body; // validated by a zod schema upstream
          const rows = await cartService.addItem(req.user.id, itemId, qty, price);
          res.status(201).json({ data: rows });    // rows already carry line totals
        } catch (err) { next(err); }
      }

      async function getCart(req, res, next) {
        try {
          const rows = await cartService.getCart(req.user.id);
          res.json({ data: rows });
        } catch (err) { next(err); }
      }

      module.exports = { addItem, getCart, removeItem };
      ```

      ```js
      // services/cartService.js — the domain rule lives here
      const cartRepository = require('../repositories/cartRepository');

      async function addItem(userId, itemId, qty, price) {
        const rows = await cartRepository.getItems(userId); // rows [id, qty, price]
        const updated = mergeLine(rows, itemId, qty, price); // ← solve()'s logic
        await cartRepository.upsertItems(userId, updated);
        return updated;
      }

      function mergeLine(rows, itemId, qty, price) {
        // ── the graded exercise implements exactly this as solve() ──
        // 1. find the row with row[0] === itemId
        // 2. found  → row[1] += qty   (keep the original unit price)
        // 3. missing → append [itemId, qty, price]
        // 4. map every row to [id, qty, price, qty * price]
      }

      module.exports = { addItem, getCart, removeItem };
      ```

      Why keep this out of the controller? A controller that does arithmetic is
      a controller you cannot unit-test without spinning up HTTP. The rule
      "merge, don't duplicate" is a business rule — it belongs in the service
      layer, next to the repository, and it must be pure.

      ## The graded exercise

      Implement `solve(items, itemId, qty, price)`:

      - `items` — the current cart, rows of `[id, qty, price]` (id = product id).
      - `itemId`, `qty`, `price` — the item being added (`qty >= 1`).
      - If a row with that id already exists, **add qty to that row** and keep
        its existing unit price. Otherwise **append** a new row.
      - Return the updated rows, each with the **line total** appended as a
        4th element: `[id, qty, price, qty * price]`.

      :::example
      Cart is `[[1, 2, 100]]` — product 1, qty 2, at 100¢. You add product 1,
      qty 3, at 100¢. The id exists, so qty merges: `2 + 3 = 5`. The updated
      row is `[1, 5, 100, 5 × 100 = 500]` → `[[1, 5, 100, 500]]`.
      :::

      :::example
      Cart is `[[1, 1, 50], [2, 2, 25]]`. You add a *new* product 3, qty 1, at
      10¢. No row has id 3, so it is appended: the result is
      `[[1, 1, 50, 50], [2, 2, 25, 50], [3, 1, 10, 10]]`.
      :::

      **Private cases you should handle:** empty cart (add into `[]` → a single
      new row); merging an existing line keeps the **original** unit price even
      if the incoming price differs; large quantities and prices (the line total
      can reach billions — keep full integer precision). All quantities are
      `>= 1`, so there is no zero-qty removal to worry about.

      def solve(items: list[list[int]], item_id: int, qty: int, price: int) -> list[list[int]]:
          for row in items:
              if row[0] == item_id:
                  row[1] += qty
                  break
          else:
              items.append([item_id, qty, price])
          return [[row[0], row[1], row[2], row[1] * row[2]] for row in items]

      ## Interview questions

      :::tip
      **Interview question:** Why is the cart's add-item rule a pure function
      of `(items, itemId, qty, price)` rather than living inline in the route
      handler? Because a pure function has no hidden state — no HTTP request,
      no database connection — so you can test every branch (merge, append,
      empty cart, big numbers) in milliseconds without spinning up the app.
      That is the whole point of the service layer: business rules that are
      fast to verify and safe to reuse.
      :::

      :::tip
      **Interview question:** Why merge quantities instead of always appending
      a new line per request? Because a cart is a *set of products with
      quantities*, not a log of clicks. Two lines for the same product make
      checkout ambiguous (which line wins?), double the storage, and confuse
      the shopper. Merging also preserves the price snapshot — the price at
      which the item was first added — which is what you actually charge at
      checkout.
      :::

      **Use case.** Every "add to cart" button on the storefront fans out to
      this one function. A user who taps *Add* twice for the same product gets
      qty 2 on one line — and the cart total (`Σ qty × price`) stays correct
      because the line total is derived, never stored separately.
