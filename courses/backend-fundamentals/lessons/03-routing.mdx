  - type: markdown
    content: |
      Routing is how a server decides **what code runs** when a request
      arrives. If the HTTP method is the *what* (the client's intent — GET,
      POST), the route is the *where* (which resource). Together they map to
      a **handler**: a function that runs the business logic and returns a
      response.

      ```js
      // Express: method + path -> handler
      app.get('/products', (req, res) => {
        res.json({ products: catalog.list() });
      });
      ```

      ## Key points

      - A route matches on **method AND path**: `GET /orders` and
        `POST /orders` are different routes.
      - The handler receives the request and produces the response.
      - Routes can be static, dynamic (params), or decorated with query
        strings.
  - type: markdown
    content: |
      ## Static routes

      Static routes are literal strings with no variable parts.
      `/products` is always exactly `/products`:

      - `GET /products` — list the catalog.
      - `POST /orders` — create an order.

      Every request to a static route hits the same handler with the same
      shape.
  - type: markdown
    content: |
      ## Dynamic routes & path parameters

      Real APIs act on *specific* resources: "product 42", "order 2049".
      Dynamic routes accept that variable directly in the URL:

      - Request: `GET /products/42`
      - Route definition: `GET /products/:id` (the `:id` is a **path
        parameter**)
      - The server extracts `"42"` and hands it to the handler as
        `req.params.id`.

      ```js
      app.get('/products/:id', (req, res) => {
        const id = req.params.id;   // "42" — always a string
        const product = catalog.findById(id);
        if (!product) {
          return res.status(404).json({ error: { code: 'PRODUCT_NOT_FOUND' } });
        }
        res.json(product);
      });
      ```

      Path parameters **identify which resource** you mean.
  - type: markdown
    content: |
      ## Query strings

      Query strings carry **metadata about the request**: filters, sorting,
      and pagination — especially on GET, which has no body. They start
      after a `?` as `key=value` pairs joined by `&`:

      - `GET /products?page=2&sort=price` — second page, sorted by price.
      - `GET /products?color=red&size=large` — filter the catalog.
      - `GET /orders?status=pending` — filter by status.

      ```js
      app.get('/products', (req, res) => {
        const page = Number(req.query.page) || 1;   // "2" arrives as a string
        const sort = req.query.sort || 'popular';
        res.json(catalog.list({ page, sort }));
      });
      ```

      Why not path params for everything? Path params identify *which*
      resource, while query params are *optional modifiers* — writing
      `/api/search/javascript` technically works but breaks REST semantics.

      **Use case:** the storefront's product grid calls
      `GET /api/products?page=3&sort=price&inStock=true` — the resource is
      still "products"; the query string just shapes how they're returned.

      ## Method + path matching, ordering, and 404s

      A request only matches a route when **both** the method and the path
      match. That's why `app.get('/orders')` and `app.post('/orders')` can
      coexist.

      **Order matters.** Frameworks check routes in registration order, so
      specific routes must come before wildcards or catch-alls. A catch-all
      registered first swallows everything after it.

      When no route matches, don't leave the client hanging: define a
      **catch-all** as the *last* route. It returns a consistent JSON 404.

      ```js
      // specific routes first
      app.get('/products/:id', ...);
      app.post('/orders', ...);

      // catch-all LAST: anything unmatched -> JSON 404
      app.use((req, res) => {
        res.status(404).json({
          error: { code: 'NOT_FOUND', message: `No route for ${req.method} ${req.path}` }
        });
      });
      ```

      :::tip
      **Interview question:** How do you design a 404 in a REST API?
      — Register a catch-all route as the very last route. It returns HTTP
      404 with a JSON error envelope (a machine-readable code and a message),
      so clients get the same predictable shape whether the resource is
      missing or the URL is typo'd. Never return a bare HTML page from an
      API.
      :::

      ## Nested routes and versioning

      **Nested routes** mirror resource hierarchies in the URL — an order
      belongs to a user:

      - `GET /users/7/orders` — all orders of user 7.
      - `GET /users/7/orders/2049` — order 2049, *and it must belong to user
        7*.

      Reading the URL tells you exactly which relationship is queried.

      **Versioning** protects clients from breaking changes. Ship
      `/api/v1/products` and `/api/v2/products` side by side, announce v1
      deprecation, let clients migrate, then delete v1. A base path like
      `/api/v1` also keeps routes tidy and signals that the route surface is
      versioned.

      :::tip
      **Interview question:** Route params vs query strings — when do you use
      which?
      — Path params identify *which* resource you're addressing
      (`/products/:id`), so they're a mandatory part of the resource
      address. Query strings are optional modifiers — pagination, filtering,
      sorting (`?page=2&sort=price`). Rule of thumb: if the URL is
      meaningless without it, it's a path param; if it just shapes the
      response, it's a query parameter.
      :::

      :::example
      **Worked example — a shop's route table.** One Express app, one theme:

      | Method | Route | What it does |
      |---|---|---|
      | GET | `/api/v1/products` | list catalog (`?page`, `?sort`, `?category`) |
      | GET | `/api/v1/products/:id` | one product's detail page |
      | POST | `/api/v1/cart/items` | add to cart (body: `{productId, qty}`) |
      | GET | `/api/v1/orders/:id` | order status for the user |
      | PATCH | `/api/v1/orders/:id/status` | admin updates fulfillment |
      | * | catch-all | `404` JSON for everything else |

      `GET /api/v1/products/42?page=1` matches the `:id` route with
      `req.params.id === '42'`; the `?page=1` query is ignored by that
      handler — params and query are read independently.
      :::
