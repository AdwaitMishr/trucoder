      ### Authentication vs authorization

      - **Authentication (AuthN) — "who are you?"** — verifying a subject's identity, e.g. logging in with email and password.
      - **Authorization (AuthZ) — "what can you do?"** — verifying permissions, e.g. an admin can delete products, a regular user can only browse them.
      - Order matters: **authenticate first, then authorize** on every protected request.

      How identity checks evolved:

      - Passwords (1961, mainframes) — first multi-user login; plaintext storage sparked the invention of hashing.
      - Cryptography (1970s) — Diffie–Hellman asymmetric keys: shared secrets over untrusted networks.
      - MFA (1990s) — combine *something you know* (password), *something you have* (OTP), *something you are* (biometric).

      **Use case:** a storefront must know *who* is checking out (AuthN) before deciding *whether* they may place an order (AuthZ — admins see the admin panel, customers don't).

      ### The Big Three: sessions, JWTs, cookies

      HTTP is **stateless** — every request is an isolated event. Auth mechanisms exist to make the server remember you.

      - **Sessions (stateful memory)** — on login the server creates a random `session_id`, stores it alongside user data (role, cart) in a DB or **Redis**, and hands it to the client. Every future request carries it back and the server **looks it up**.
      - **JWTs (stateless claims)** — on login the server signs a token of the form `header.payload.signature`. The payload holds claims (`sub` = user id, `role`, `iat`). Any server that knows the **secret key verifies the signature locally — no DB lookup**. Signed, so it cannot be tampered with.
      - **Cookies (transport, not auth)** — a browser mechanism: the server sets a cookie holding a session id *or* a JWT, and the browser automatically attaches it to every request for that domain. Flags: `HttpOnly` (JavaScript can't read it — defuses XSS), `Secure` (HTTPS only), `SameSite` (mitigates CSRF).

      **Use case:** the storefront sets an `HttpOnly` session cookie for the browser checkout, while the mobile app authenticates with a JWT in the `Authorization` header.

      ### Password hashing

      - **Never store plaintext.** Store a one-way hash; on login, hash the input and compare hashes.
      - **bcrypt** — built for passwords: deliberately slow, and each hash embeds a random **salt**, so identical passwords produce different hashes and rainbow tables are useless.
      - **Why not SHA-256?** SHA-256 is *fast* — an attacker can brute-force billions of guesses per second. Password hashing needs *deliberate slowness* (bcrypt's cost factor).
      - **Timing-safe compare** — compare hashes in constant time. A fast-fail on mismatch reveals (by response time) whether the email exists — a timing attack.
      - **Generic errors** — always return the same `401 Invalid credentials` whether the email is unknown or the password is wrong, so attackers can't scrape registered addresses.

      **Use case:** the signup endpoint stores `bcrypt(password)`; the login endpoint compares with `bcrypt.compare()` — the plaintext never touches the database.

      ### Stateful vs stateless — the tradeoff

      - **Stateful (sessions)** — instant **revocation** (delete the session in Redis → user is logged out everywhere), central control, track active devices. Con: the session store must be shared or synced across servers.
      - **Stateless (JWT)** — **infinitely scalable**: any server verifies without shared state. Con: **revocation is hard** — a stolen token is valid until it expires. The hybrid fix (check a Redis blacklist of revoked tokens) sacrifices full statelessness.

      ### API keys, OAuth 2.0, RBAC

      - **API keys** — long random strings for **machine-to-machine** auth (your backend calling Stripe or OpenAI). No login forms; embed securely server-side.
      - **OAuth 2.0** — **delegated authorization**: sign in with Google and grant a third-party app a *scoped* access token (read Drive, nothing else) — never your password.
      - **OpenID Connect (OIDC)** — OAuth 2.0 plus identity: adds an `ID token` (a JWT) — the technology behind "Sign in with Google / Apple".
      - **RBAC** — assign permissions to *roles* (`user`, `admin`), not to individuals; middleware checks the role and returns `403 Forbidden` on violation.

      **Use case:** the store's admin API uses API keys for internal services, OAuth for "Continue with Google", and RBAC so only `admin` can reach `DELETE /products/:id`.

      ### E-commerce: sessions vs JWTs for a storefront

      - **Cart and login** — **session**: the cart is server-side state tied to `session_id` in Redis; logout and revocation are instant if an account is compromised.
      - **APIs for mobile apps and microservices** — **JWT** in the `Authorization` header: the catalog or order service verifies the token without touching a shared session store.
      - Typical storefront: session cookie for the browser + short-lived JWT for the API, refreshed on expiry.

      ### Worked example — a login request end-to-end

      1. `POST /login` with `email` + `password`.
      2. Server looks up the user, bcrypt-hashes the input, compares in constant time.
      3. On match: store session in Redis → set `HttpOnly; Secure; SameSite=Lax` cookie.
      4. Next request: cookie arrives → Redis lookup → role checked (RBAC) → request served.
      5. `POST /logout`: delete the Redis session → the token is dead instantly.

      ### Interview questions

      :::tip
      **Interview question:** Sessions vs JWT — which do you use and why?
      — For a browser storefront I'd start with sessions: the cart lives server-side, logout and revocation are instant, and I can track active devices. I'd move to JWTs (or a hybrid — JWT plus a Redis blacklist) when I need to scale horizontally with zero shared state, accepting that revocation becomes a blacklist problem.
      :::

      :::tip
      **Interview question:** Why hash passwords with bcrypt and not SHA-256?
      — SHA-256 is fast, which is exactly the problem: an attacker can brute-force billions of guesses per second. bcrypt is deliberately slow and salts each hash, so identical passwords differ and precomputed rainbow tables are useless.
      :::

      :::tip
      **Interview question:** What is the difference between authentication and authorization, and where do 401 and 403 come in?
      — AuthN answers "who are you?" (login); AuthZ answers "what can you do?" (permissions). A missing or invalid credential gets `401 Unauthorized`; a validly authenticated user hitting an endpoint their role lacks gets `403 Forbidden`.
      :::
