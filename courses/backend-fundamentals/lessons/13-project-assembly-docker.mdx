      # Project 4: Assembly & Docker

      **Context.** Three lessons, three pieces: the cart domain, the checkout
      pipeline, and the rate limiter. Today you **assemble the whole e-commerce
      backend** — every file, wired end to end — and **ship it in Docker**:
      an API container (Node 20 + Express) talking to a Postgres container
      and a Redis container, orchestrated by `docker-compose.yml`. One
      command, `docker compose up`, and the shop is open.

      **What you are building this step.** The complete blueprint below is the
      finished project. Read it top to bottom; every earlier lesson plugs in
      somewhere. Your graded exercise is the last util the project needs:
      **config validation** — the function that fails fast at boot when a
      required environment variable is missing, instead of crashing on the
      first request.

      **Acceptance criteria**

      - `docker compose up` starts api + postgres + redis; the API waits for
        both databases via healthchecks.
      - The full flow works over curl: register → login (JWT) → list products
        → add to cart → checkout → duplicate checkout is replayed, not
        duplicated → hammering the API eventually returns **429**.
      - The API container runs as a **non-root user** and has a **HEALTHCHECK**.
      - Missing env vars fail at boot with a clear message — that is `solve()`.

      ```js
      // utils/env.js — fail fast at boot, not on the first request.
      // The missing-vars check is exactly your graded solve(vars, required).
      const raw = { ...process.env };

      const REQUIRED = ['PORT', 'DATABASE_URL', 'REDIS_URL', 'JWT_SECRET'];

      // ── this is solve(vars, required): missing vars, in required order ──
      const missing = REQUIRED.filter((name) => {
      ```

      ## middleware/ — auth and errors (rateLimiter is in lesson 12)

      ```js
      // middleware/auth.js — JWT verify (stateless auth, lesson 6)
      const jwt = require('jsonwebtoken');

      function requireAuth(req, res, next) {
        const header = req.headers.authorization || '';
        const token = header.startsWith('Bearer ') ? header.slice(7) : null;
        if (!token) return res.status(401).json({ error: { code: 'UNAUTHORIZED' } });
        try {
          req.user = jwt.verify(token, process.env.JWT_SECRET); // { id, email }
          next();
        } catch {
          res.status(401).json({ error: { code: 'UNAUTHORIZED' } });
        }
      }

      module.exports = { requireAuth };
      ```

      ```js
      // middleware/errors.js — terminal middleware
      function notFound(req, res) {
        res.status(404).json({ error: { code: 'NOT_FOUND' } });

        if (status >= 500) console.error(err);
        res.status(status).json({ error: { code: err.code || 'INTERNAL' } });
      ```

      ## services/ — the business rules from lessons 10 and 11

      ```js
      // services/authService.js
      const bcrypt = require('bcryptjs');
      const jwt = require('jsonwebtoken');
      const { query } = require('../db/pool');

      async function register(email, password) {
        const hash = await bcrypt.hash(password, 10);
        const { rows } = await query(
          'INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email',
          [email, hash]
        );
        return rows[0];
      }

      async function login(email, password) {
        const { rows } = await query('SELECT * FROM users WHERE email = $1', [email]);
        const user = rows[0];
        if (!user || !(await bcrypt.compare(password, user.password_hash))) {
          const err = new Error('invalid credentials');
          err.status = 401;
          throw err;
        }
        return jwt.sign({ id: user.id, email: user.email }, process.env.JWT_SECRET, {
          expiresIn: '1h',
        });
      }

      module.exports = { register, login };
      ```

      ## Dockerfile

      ```dockerfile
      FROM node:20-alpine

      WORKDIR /app

      # install dependencies first so the layer cache survives code changes
      COPY package*.json ./
      RUN npm ci --omit=dev

      COPY . .

      # run as an unprivileged user — never as root in production
      RUN addgroup -S app && adduser -S app -G app
      USER app

      EXPOSE 3000

      # the platform can see when this container is actually healthy
      HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
        CMD wget -qO- http://localhost:3000/health || exit 1

      CMD ["node", "server.js"]
      ```

      ## docker-compose.yml

      ```yaml
      services:
        api:
          build: .
          ports:
            - "3000:3000"
          environment:
            PORT: "3000"
            DATABASE_URL: postgres://shop:shop@postgres:5432/shop
            REDIS_URL: redis://redis:6379
            JWT_SECRET: change-me-in-prod
          depends_on:
            postgres:
              condition: service_healthy
            redis:
              condition: service_healthy

        postgres:
          image: postgres:16-alpine
          environment:
            POSTGRES_USER: shop
            POSTGRES_PASSWORD: shop
            POSTGRES_DB: shop
          volumes:
            - pgdata:/var/lib/postgresql/data
          healthcheck:
            test: ["CMD-SHELL", "pg_isready -U shop -d shop"]
            interval: 5s
            timeout: 3s
            retries: 10

        redis:
          image: redis:7-alpine
          volumes:
            - redisdata:/data
          healthcheck:
            test: ["CMD", "redis-cli", "ping"]
            interval: 5s
            timeout: 3s
            retries: 10

      volumes:
        pgdata:
        redisdata:
      ```

      Note the service names are DNS names: the API connects to `postgres:5432`
      and `redis:6379` — not `localhost`, because each container has its own
      network namespace. Compose gives them one shared network, and the
      `depends_on.condition: service_healthy` gates the API's start on its
      databases actually accepting connections.

      ## The curl walkthrough

      ```bash
      docker compose up --build

      # 1. register a shopper
      curl -s -X POST http://localhost:3000/api/auth/register \
        -H 'Content-Type: application/json' \
        -d '{"email":"ada@example.com","password":"hunter2hunter2"}'

      # 2. login → grab the JWT
      TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
        -H 'Content-Type: application/json' \
        -d '{"email":"ada@example.com","password":"hunter2hunter2"}' \
        | jq -r .data.token)

      # 3. browse the public catalog
      curl -s http://localhost:3000/api/products

      # 4. add to cart: 2 of product 1
      curl -s -X POST http://localhost:3000/api/cart/items \
        -H "Authorization: Bearer $TOKEN" \
        -H 'Content-Type: application/json' \
        -d '{"itemId":1,"qty":2}'

      # 5. checkout with an idempotency key (controller reads req.body.items — lesson 11)
      curl -s -X POST http://localhost:3000/api/orders \
        -H "Authorization: Bearer $TOKEN" \
        -H 'Content-Type: application/json' \
        -H 'Idempotency-Key: order-ada-001' \
        -d '{"items":[{"itemId":1,"qty":2}],"shippingAddress":"1 Main St"}'

      # 6. same key again → replayed (200), no second order, no second charge
      curl -s -X POST http://localhost:3000/api/orders \
        -H "Authorization: Bearer $TOKEN" \
        -H 'Content-Type: application/json' \
        -H 'Idempotency-Key: order-ada-001' \
        -d '{"items":[{"itemId":1,"qty":2}],"shippingAddress":"1 Main St"}'

      # 7. hammer the API → eventually 429 Too Many Requests
      for i in $(seq 1 70); do
        curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/api/products
      done | sort | uniq -c
      #   60 200
      #   10 429
      ```

      cart's merge (step 4), the transaction and idempotency key (steps 5–6),
      and the sliding-window limiter (step 7).

      ## The graded exercise

      Implement `solve(vars, required)` — the config validator from
      `utils/env.js`:

      - `vars` — environment entries as strings, e.g. `"PORT=3000"`.
      - `required` — the variable names the app needs.
      - Return the names in `required` that are **missing**, in the order they
        appear in `required`. Return `[]` when all are present.
      - **Convention:** only `KEY=value` with a **non-empty** value counts as
        present. `KEY=` (empty value) and an absent key are both missing.

      :::example
      `(["PORT=3000", "JWT_SECRET=abc"], ["PORT", "DB_URL"])`: PORT is present,
      DB_URL is nowhere → `["DB_URL"]`.
      :::

      :::example
      `(["A=1", "B=2"], ["A", "B"])`: both present → `[]`.
      :::

      **Private cases you should handle:** empty `vars` → every required name
      is missing, in order; empty `required` → `[]`; an entry like `"PORT="`
      with an empty value counts as **missing**; missing names must come back
      in `required` order, not input order.

      def solve(vars: list[str], required: list[str]) -> list[str]:

          for entry in vars:
              key, sep, value = entry.partition("=")
              if sep and value != "":
                  present.add(key)
          return [name for name in required if name not in present]

      ## Interview questions

      :::tip
      **Interview question:** Why does the API container depend on Postgres's
      *healthcheck* (`condition: service_healthy`) instead of plain
      `depends_on: [postgres]`? Plain `depends_on` only waits for the
      container to *start* — Postgres boots in seconds but takes longer to
      accept connections, so the API would crash-loop on refused connections.
      `service_healthy` gates startup on `pg_isready` succeeding, so the API
      only starts when the database is actually ready. Same trick for Redis.
      :::

      :::tip
      **Interview question:** The Dockerfile runs as a non-root user *and*
      declares a HEALTHCHECK — what failure mode does each prevent? Root in a
      container is still root on the host kernel for many operations: a
      compromised app becomes a compromised host. A non-root `USER app`
      shrinks that blast radius. The HEALTHCHECK gives the orchestrator a
      truthful signal — a container whose process is alive but whose app is
      wedged (stuck at 100% CPU, deadlocked pool) is reported unhealthy and
      restarted, instead of silently serving errors.
      :::

      **Use case.** A fresh clone of the repo on a new machine — or a CI
      pipeline — runs `docker compose up --build` and gets a working shop in
      minutes, because every dependency (Postgres, Redis, env vars) is
      declared in one file. That reproducibility is the entire point of
      shipping with Docker: the production environment is a text file in git.
