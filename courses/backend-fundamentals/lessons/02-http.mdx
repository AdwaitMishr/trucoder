      HTTP (Hypertext Transfer Protocol) is how browsers and servers exchange
      data. Two ideas define it:

      **Statelessness** — the server has no memory of past interactions. Every
      request is treated as a completely new, unrelated event, so each request
      must carry everything the server needs (tokens, cookies). That buys
      *simplicity* (no per-server session memory) and *scalability* (any
      server can handle any request, so load balancing is trivial).

      **Client-server model** — communication is always initiated by the
      client. The server hosts resources and passively waits for requests,
      processes them, and responds.

      ## Key points

      - HTTP is an application-layer (OSI layer 7) protocol that runs over
        TCP.
      - Stateless requests are self-contained: headers carry identity and
        context.
      - Because of statelessness, sessions and tokens exist — more on that
        below.

      **Use case:** your storefront serves `GET /api/products` from any of
      ten load-balanced servers — statelessness makes that safe.

      ## Anatomy of an HTTP message

      A **request** has four parts:

      1. **Request line** — method + path + version: `POST /orders HTTP/1.1`
      2. **Headers** — key-value metadata: `Host: api.shop.com`
      3. **Blank line** — marks the end of the headers
      4. **Body (optional)** — the payload, e.g. a JSON order

      A **response** mirrors it:

      1. **Status line** — version + code + message: `HTTP/1.1 201 Created`
      2. **Headers** — e.g. `Content-Type: application/json`
      3. **Blank line**
      4. **Body** — the requested data or an error object

      :::example
      **Worked example — placing an order.** The checkout page sends:

      ```http
      POST /orders HTTP/1.1
      Host: api.shop.com
      Authorization: Bearer eyJhbGciOi...
      Content-Type: application/json

      {"items":[{"productId":42,"qty":2}],"addressId":7}
      ```

      The backend creates the order and replies:

      ```http
      HTTP/1.1 201 Created
      Content-Type: application/json
      Location: /orders/2049

      {"orderId":2049,"total":5998,"status":"confirmed"}
      ```

      Note the status line, the headers (`Content-Type`, `Location`), and the
      JSON body — and that the client's identity travelled in the
      `Authorization` header, not in server memory.
      :::

      ## Methods: intent, safety, idempotency

      Methods declare the **intent** of the request:

      | Method | Meaning | Example | Idempotent? |
      |---|---|---|---|
      | GET | fetch data | `GET /products/42` | yes (safe, no side effects) |
      | POST | create | `POST /orders` | **no** — twice = two orders |
      | PUT | full replace | `PUT /users/7` | yes |
      | PATCH | partial update | `PATCH /users/7` (just the name) | no |
      | DELETE | remove | `DELETE /cart/items/9` | yes |
      | OPTIONS | ask capabilities (CORS preflight) | `OPTIONS /orders` | yes |

      A method is **idempotent** when calling it N times leaves the same end
      state as calling it once. GET, PUT, and DELETE are idempotent; POST is
      not — double-clicking "Place order" must be defended server-side
      (idempotency keys, see the API design lesson).

      :::tip
      **Interview question:** What is the difference between GET and POST?
      — GET fetches a resource: it is *safe* (no side effects) and
      *idempotent* (any number of identical GETs changes nothing). POST
      creates a resource and is non-idempotent: two identical POSTs create
      two resources. That's why retrying a failed checkout needs an
      idempotency key rather than a plain POST retry.
      :::

      ## Status codes: 1xx–5xx

      Status codes standardize the *result* of a request so clients don't
      have to guess from the body:

      - **1xx Informational** — `100 Continue` (go ahead and send the body),
        `101 Switching Protocols` (WebSocket upgrade).
      - **2xx Success** — `200 OK`, `201 Created` (resource made), `204 No
        Content` (success, no body — common for DELETE).
      - **3xx Redirection** — `301 Moved Permanently`, `302 Found`, `304 Not
        Modified` (caching: use your saved copy).
      - **4xx Client errors** — *you* messed up the request: `400 Bad
        Request`, `401 Unauthorized` (missing/invalid credentials), `403
        Forbidden` (authenticated but not allowed), `404 Not Found`, `405
        Method Not Allowed`, `409 Conflict` (e.g. email already registered),
        `422 Unprocessable Entity` (valid JSON, invalid values), `429 Too
        Many Requests` (rate limited).
      - **5xx Server errors** — *the server* messed up: `500 Internal Server
        Error`, `502 Bad Gateway` / `504 Gateway Timeout` (a proxy can't
        reach the backend), `503 Service Unavailable` (overloaded or in
        maintenance).

      :::tip
      **Interview question:** What's the difference between 401 and 403?
      — 401 Unauthorized means the request lacks valid authentication: the
      server doesn't know *who you are* (missing or invalid token). 403
      Forbidden means the server knows who you are but you're not *allowed*
      to do this — a customer hitting an admin-only endpoint gets 403, not
      401.
      :::

      ## Headers: the shipping labels of HTTP

      Headers are metadata attached to requests and responses — like the
      label on a parcel: they tell the network and the server how to handle
      the package without opening it. The ones you'll meet constantly:

      - `Content-Type` — what the body is: `application/json`,
        `multipart/form-data`.
      - `Authorization` — credentials: `Bearer <jwt>` or `Basic ...`.
      - `Cache-Control` — freshness: `max-age=10` (cache for 10 seconds).
      - `Set-Cookie` — the server plants a cookie (`HttpOnly`, `Secure`
        flags).
      - `Access-Control-Allow-Origin` / `-Methods` / `-Headers` — CORS: the
        server tells the browser which origins may read the response.
      - `Content-Encoding: gzip` — the body is compressed.
      - Security: `Strict-Transport-Security` (force HTTPS),
        `Content-Security-Policy` (block XSS).

      **Use case:** the storefront's image CDN returns
      `Cache-Control: max-age=3600` and an `ETag` on product photos, so
      repeat visits reuse the cached images and only changed files are
      re-downloaded (`304 Not Modified`).

      ## Statelessness: why sessions and tokens exist

      Because HTTP has no memory, each request must prove who it is. Two
      standard solutions:

      - **Server-side sessions** — the server stores session state (often in
        Redis) keyed by a session id the client sends as a cookie.
      - **Tokens** — the client holds a signed token (e.g. JWT) and sends it
        in the `Authorization` header; the server verifies the signature
        without storing anything.

      Either way the principle is the same: **the request carries its own
      context**. Your cart API reads the user id from the token, not from
      server memory of a previous request.

      :::tip
      **Interview question:** Why does HTTP statelessness matter for scaling?
      — A stateless server holds no per-user memory, so any instance can
      serve any request. You can add servers behind a load balancer and
      spread traffic freely. The moment servers keep sessions in local
      memory, requests get stuck to one instance and scaling breaks.
      :::
