      # Project 3: Rate Limiter & Middleware

      **Context.** The shop is live and the first bot attack arrives: one IP
      hammers `POST /api/auth/login` a thousand times a minute, and a scraper
      drains the product catalog. You need a **rate limiter** — and because
      Express is a middleware chain, the limiter is just one link in it. This
      lesson builds the real **sliding-window rate limiter middleware**
      (`middleware/rateLimiter.js`) and shows where it sits in the chain:
      logger → auth → rate limit → controller.

      **What you are building this step.** A real Express middleware factory:

      - `rateLimiter({ limit, windowMs, keyFn, store? })` returns middleware
        that decides `next()` or **429** for every request. `store` is an
        optional Redis client (defaults to the shared `db/redis.js` client;
        tests inject an in-memory store so the suite runs with zero infra).
      - Sliding window `[t − windowMs, t]`, **inclusive on both edges**: a
        request is allowed when the window holds **at most `limit`** requests
        counting the current one.
      - Denied requests get **429 Too Many Requests** with a `Retry-After`
        header (seconds until the oldest request leaves the window).
      - The bucket key comes from `keyFn(req)` — `req.user.id` for protected
        routes, `req.ip` for public ones.

      This is **real backend practice, done test-first**: the middleware
      ships with a full, visible `node:test` suite (`tests/rateLimiter.test.js`)
      that boots a real Express app and drives it with `fetch`. Nothing is
      hidden — every test case is printed in this lesson.

      **Acceptance criteria**

      - `app.use('/api', limiter)` protects every API route, not just auth.
      - A request that pushes the window over `limit` → **429** +
        `Retry-After`.
      - The window slides: old requests expire out of it as time moves on.
      - The middleware chain order is fixed: logger → auth → rate limit →
        controller, so unauthenticated and rate-limited traffic never reaches
        your controllers.

      **How this lesson is graded.** The platform grades the module exercise
      below — a visible node:test suite runs your `middleware/rateLimiter.js`
      in a sandbox. The same suite is the real deliverable in the shipped
      project: run `npm test` and make `tests/rateLimiter.test.js` green.

      ## Module contract — `middleware/rateLimiter.js`

      The project and this lesson agree **exactly** on this surface.

      **Export**

      - `rateLimiter({ limit, windowMs, keyFn, store? })` — a factory
        returning Express middleware `(req, res, next)`.

      | Param | Meaning |
      |-------|---------|
      | `limit` | Max requests per window |
      | `windowMs` | Window length in ms — window `[t − windowMs, t]` **inclusive** on both edges |
      | `keyFn` | `(req) => string` — picks the bucket (`req.user.id` for protected routes, `req.ip` for public ones) |
      | `store?` | Optional Redis client. Defaults to the shared `db/redis.js` client; tests inject an in-memory store so the suite runs with zero infra |

      **Decision rule.** For the request's key at time `t`, keep every
      recorded request with timestamp `>= t − windowMs` (the left edge is
      **inclusive**). If that count is `>= limit`, the window is full — this
      request would be the `(limit + 1)`-th — so deny with **429** and
      `Retry-After`. Otherwise record `t` and call `next()`.

      **`Retry-After`.** Seconds until the oldest request in the window
      leaves it — `max(1, ceil((oldestScore + windowMs − now) / 1000))` — at
      least 1. The oldest score is read with
      `redis.zRange(key, 0, 0, { WITHSCORES: true })` (the first member of
      the zset).

      **`keyFn(req)`.** Picks the bucket: `(req) => \`user:${req.user.id}\``
      for protected routes (after auth), `(req) => \`ip:${req.ip}\`` for
      public ones. Different keys get independent budgets.

      **Store.** The default store is the shared `db/redis.js` client
      (node-redis v4): each key is a Redis sorted set whose members are
      request ids and whose scores are timestamps. The tests inject an
      in-memory store (`memRedis`) implementing the same zset commands, so
      the suite runs with zero infrastructure.

      The window check is a `multi()` pipeline — and node-redis v4 returns
      a **FLAT array** from `multi().exec()`, one result per command. With
      `zRemRangeByScore` then `zCard`, the count is `results[1]` — NOT
      `results[1][1]` (which is `undefined` under v4, so the limiter would
      silently never deny). Recording is `zAdd(key, { score: now, value:
      \`${now}:${req.id}\` })`.

      :::example
      `limit: 2, windowMs: 200`. Requests arrive at 100, 200, 300 (ms). At
      300 the window `[100, 300]` holds 100, 200, 300 — three requests, more
      than the limit of 2 → deny. At 200 the window `[0, 200]` holds exactly
      2 → allowed (at most 2). Result: `[allowed, allowed, denied]`.
      :::

      :::example
      The edge is inclusive: an earlier request at exactly `t − windowMs`
      is still inside the window, so with `limit: 2` and requests at 100 and
      300 (`windowMs: 200`), the request at 300 sees both 100 and 300 inside
      `[100, 300]` — exactly 2 → allowed.
      :::

      **Edge cases you must handle** (all covered by the visible suite): a
      burst of requests (the `limit`-th is allowed, the next is 429); the
      window sliding (after `windowMs` the budget resets); `Retry-After`
      being present and roughly `windowMs / 1000`; independent buckets per
      user and per IP; a generous limit never denying normal traffic.

      ```js
      // tests/rateLimiter.test.js — lesson 12
      // Run: node --test tests/rateLimiter.test.js   (or: npm test)
      // Integration: the limiter IS Express middleware, so the tests boot a real
      // app on an ephemeral port and drive it with the built-in fetch.
      const { test } = require('node:test');
      const assert = require('node:assert/strict');
      const express = require('express');
      const { rateLimiter } = require('../middleware/rateLimiter');

      const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

      // In-memory redis double: sliding-window zset semantics (member -> score),
      // so the middleware's real logic (multi/zRemRangeByScore/zCard/zAdd/zRange)
      // runs against a store that behaves like redis — no server required.
      function memRedis() {
        const sets = new Map();
        const zset = (key) => {
          if (!sets.has(key)) sets.set(key, new Map());
          return sets.get(key);
        };
        return {
          multi() {
            const cmds = [];
            return {
              zRemRangeByScore: (k, min, max) => cmds.push(['zrem', k, min, max]),
              zCard: (k) => cmds.push(['zcard', k]),
              async exec() {
                const out = [];
                for (const [op, k, a, b] of cmds) {
                  if (op === 'zrem') {
                    const s = zset(k);
                    let n = 0;
                    for (const [m, sc] of [...s]) {
                      if (sc >= a && sc <= b) {
                        s.delete(m);
                        n++;
                      }
                    }
                    out.push(n);
                  } else if (op === 'zcard') {
                    out.push(zset(k).size);
                  }
                }
                return out; // flat array, like node-redis v4 multi().exec()
              },
            };
          },
          async zAdd(k, { score, value }) {
            zset(k).set(value, score);
            return 1;
          },
          async zRange(k, start, stop) {
            const entries = [...zset(k).entries()].sort((x, y) => x[1] - y[1]);
            const out = [];
            for (const [m, sc] of entries.slice(start, stop + 1)) out.push(m, String(sc));
            return out; // flat [member, score, ...], like node-redis v4
          },
          async expire() {
            return 1;
          },
        };
      }

      // A tiny app with two routes: /public (keyed on the IP) and /protected
      // (keyed on req.user.id — a stub auth middleware sets req.user first).
      function buildApp({ limit, windowMs, keyFn }) {
        const app = express();
        app.set('trust proxy', true); // so X-Forwarded-For drives req.ip in tests
        const limiter = rateLimiter({ limit, windowMs, keyFn, store: memRedis() });
        app.get('/public', limiter, (req, res) => res.json({ ok: true }));
        app.get(
          '/protected',
          (req, res, next) => {
            req.user = { id: req.headers['x-user-id'] || 'anon' };
            next();
          },
          limiter,
          (req, res) => res.json({ ok: true })
        );
        return app;
      }

      // Boot a fresh app per test; the server is closed even if the test throws.
      async function withServer(options, fn) {
        const server = buildApp(options).listen(0);
        await new Promise((resolve) => server.once('listening', resolve));
        try {
          await fn(`http://127.0.0.1:${server.address().port}`);
        } finally {
          await new Promise((resolve) => server.close(resolve));
        }
      }

      test('the third request inside the window is denied with 429', async () => {
        await withServer(
          { limit: 2, windowMs: 300, keyFn: (req) => `ip:${req.ip}` },
          async (base) => {
            assert.equal((await fetch(`${base}/public`)).status, 200);
            assert.equal((await fetch(`${base}/public`)).status, 200);
            const denied = await fetch(`${base}/public`);
            assert.equal(denied.status, 429);
            const body = await denied.json();
            assert.equal(body.error.code, 'RATE_LIMITED');
          }
        );
      });

      test('the window slides: after windowMs the budget resets', async () => {
        await withServer(
          { limit: 1, windowMs: 200, keyFn: (req) => `ip:${req.ip}` },
          async (base) => {
            assert.equal((await fetch(`${base}/public`)).status, 200);
            assert.equal((await fetch(`${base}/public`)).status, 429);
            await sleep(250); // oldest request has now left the window
            assert.equal((await fetch(`${base}/public`)).status, 200);
          }
        );
      });

      test('denied responses carry Retry-After (seconds until the window frees)', async () => {
        await withServer(
          { limit: 1, windowMs: 5000, keyFn: (req) => `ip:${req.ip}` },
          async (base) => {
            assert.equal((await fetch(`${base}/public`)).status, 200);
            const denied = await fetch(`${base}/public`);
            assert.equal(denied.status, 429);
            const retryAfter = Number(denied.headers.get('retry-after'));
            // Oldest request leaves at oldest + 5000ms; we are a few ms in, so
            // ceil() lands on 5. Allow a little drift.
            assert.ok(retryAfter >= 4 && retryAfter <= 5, `retry-after was ${retryAfter}`);
          }
        );
      });

      test('protected routes are keyed on the authenticated user id', async () => {
        await withServer(
          { limit: 1, windowMs: 60_000, keyFn: (req) => `user:${req.user.id}` },
          async (base) => {
            const asUser1 = { 'x-user-id': 'u1' };
            assert.equal((await fetch(`${base}/protected`, { headers: asUser1 })).status, 200);
            assert.equal((await fetch(`${base}/protected`, { headers: asUser1 })).status, 429);
            // A different user has its own budget — the limiter is keyed on the
            // identity, not on a shared counter.
            const asUser2 = { 'x-user-id': 'u2' };
            assert.equal((await fetch(`${base}/protected`, { headers: asUser2 })).status, 200);
          }
        );
      });

      test('public routes are keyed on the client IP', async () => {
        await withServer(
          { limit: 2, windowMs: 60_000, keyFn: (req) => `ip:${req.ip}` },
          async (base) => {
            const fromIpA = { 'x-forwarded-for': '10.0.0.1' };
            const fromIpB = { 'x-forwarded-for': '10.0.0.2' };
            assert.equal((await fetch(`${base}/public`, { headers: fromIpA })).status, 200);
            assert.equal((await fetch(`${base}/public`, { headers: fromIpA })).status, 200);
            assert.equal((await fetch(`${base}/public`, { headers: fromIpA })).status, 429);
            // A second IP is untouched.
            assert.equal((await fetch(`${base}/public`, { headers: fromIpB })).status, 200);
          }
        );
      });

      test('a generous limit never denies normal traffic', async () => {
        await withServer(
          { limit: 100, windowMs: 1000, keyFn: (req) => `ip:${req.ip}` },
          async (base) => {
            for (let i = 0; i < 5; i++) {
              assert.equal((await fetch(`${base}/public`)).status, 200);
            }
          }
        );
      });
      ```

      ## Wiring — where the limiter plugs into the chain

      The limiter is mounted per-route with different parameters. Public
      routes key on the IP; protected routes key on the authenticated user.
      The chain order is fixed: **logger → auth → rate limit → controller**.

      ```js
      // app.js (excerpt)
      const { rateLimiter } = require('./middleware/rateLimiter');
      const { requireAuth } = require('./middleware/auth');
      const { requestLogger } = require('./middleware/logger');

      app.use(express.json());

      app.use('/api', requestLogger);                                    // 1 logger

      app.use('/api/auth', require('./routes/auth'));                    // public — no auth/limiter
      app.use('/api/products',                                            // public catalog
        rateLimiter({ limit: 60, windowMs: 60_000,                       // IP-keyed
          keyFn: (req) => `ip:${req.ip}` }),
        require('./routes/products'));

      app.use('/api/cart', requireAuth,                                  // 2 auth first (sets req.user)
        rateLimiter({ limit: 120, windowMs: 60_000,                      // 3 then the limiter
          keyFn: (req) => `user:${req.user.id}` }),                      //    keyed on the user
        require('./routes/cart'));                                       // 4 then the controller
      ```

      One production caveat: behind a reverse proxy, `req.ip` is the proxy's
      address unless you tell Express to trust the `X-Forwarded-For` header
      (`app.set('trust proxy', 1)`) — otherwise every client shares one
      bucket and the limiter rate-limits the whole shop as a single IP. The
      test suite simulates exactly this with `trust proxy` + spoofed headers.

      Why **sliding** rather than fixed windows? A fixed window (reset every
      minute at :00) lets a burst at :59 and another at :00 sneak through as
      ~2× the limit. The sliding window counts the *last* `window_ms` of real
      time, so a burst is a burst no matter where the clock hand is. The
      price is state: you must remember each request's timestamp, not just a
      counter. The default store is the shared Redis client; the tests
      inject an in-memory store with the same zset commands. Either way the
      pipeline is the same `multi()` shape:

      ```js
      // production note — the exact final shape (node-redis v4)
      const pipe = redis.multi();
      pipe.zRemRangeByScore(key, 0, min - 1);   // drop requests older than the left edge
      pipe.zCard(key);                          // count what is left
      const results = await pipe.exec();        // v4: FLAT array, one result per command
      const count = results[1];                 // the zCard count — NOT results[1][1]
      if (count >= limit) {
        const oldest = await redis.zRange(key, 0, 0, { WITHSCORES: true });
        const oldestScore = oldest.length >= 2 ? Number(oldest[1]) : now;
        const retryAfter = Math.max(1, Math.ceil((oldestScore + windowMs - now) / 1000));
        return res.status(429).set('Retry-After', String(retryAfter))
          .json({ error: { code: 'RATE_LIMITED', message: 'Too many requests' } });
      }
      await redis.zAdd(key, { score: now, value: `${now}:${req.id}` });
      await redis.expire(key, Math.ceil(windowMs / 1000));
      next();                                   // allowed
      ```

      ## Interview questions

      :::tip
      **Interview question:** The window is `[t − window_ms, t]` inclusive —
      why does that edge case matter? An off-by-one here is the difference
      between "exactly `limit` requests in the window" being allowed or
      denied, and it decides whether a client hovering right at the boundary
      gets 429s in a tight loop. State the convention (inclusive both edges,
      allowed at exactly `limit`) and implement it once — in production this
      is the kind of subtle bug that only shows up under load-testing.
      :::

      :::tip
      **Interview question:** Rate-limit by user id or by IP? User id is
      precise but useless for unauthenticated endpoints (login, registration)
      — that is where attackers live. IP covers everyone but punishes
      NAT/corporate users who share one address. Production answer: key on
      user id when authenticated, fall back to IP for anonymous traffic, and
      apply a *separate, stricter* limiter to auth endpoints so credential
      stuffing is throttled hard. Defend both layers.
      :::

      **Use case.** The login endpoint gets a strict limiter (5 tries/min per
      IP) to blunt credential stuffing; the catalog gets a generous one (60
      req/min) to keep scrapers polite; the checkout endpoint sits behind both
      the global limiter and the idempotency key from lesson 11. Same
      middleware, different parameters — that is why the limiter takes
      `{ limit, windowMs, keyFn, store? }` as configuration.

      // middleware/rateLimiter.js — sliding window per key (lesson 12)
      // Factory: rateLimiter({ limit, windowMs, keyFn, store? })
      //   limit     — max requests per window
      //   windowMs  — window length in ms; window [t - windowMs, t] INCLUSIVE on both edges
      //   keyFn     — (req) => string key (user id for authed routes, IP for public ones)
      //   store     — optional Redis client (defaults to the shared db/redis client).
      //               Tests inject an in-memory store so the suite runs with zero infra.
      function rateLimiter({ limit, windowMs, keyFn, store }) {
        const redis = store || require('../db/redis');

        return async function rateLimit(req, res, next) {
          const key = keyFn(req);                 // user id, or IP for anonymous
          const now = Date.now();
          const min = now - windowMs;             // left edge of the window

          const pipe = redis.multi();
          pipe.zRemRangeByScore(key, 0, min - 1);  // drop requests strictly older than the left edge (window is inclusive)
          pipe.zCard(key);                          // count what is left
          const results = await pipe.exec();        // node-redis v4: FLAT array of results, one per command
          const count = results[1];                 // zCard result

          // ── the decision: this is exactly the lesson's rule ──
          if (count >= limit) {                   // window already full
            const oldest = await redis.zRange(key, 0, 0, { WITHSCORES: true });
            const oldestScore = oldest.length >= 2 ? Number(oldest[1]) : now;
            const retryAfter = Math.max(1, Math.ceil((oldestScore + windowMs - now) / 1000));
            return res.status(429)
              .set('Retry-After', String(retryAfter))
              .json({ error: { code: 'RATE_LIMITED', message: 'Too many requests' } });
          }

          await redis.zAdd(key, { score: now, value: `${now}:${req.id}` });   // record this request
          await redis.expire(key, Math.ceil(windowMs / 1000));
          next();                                 // allowed
        };
      }
