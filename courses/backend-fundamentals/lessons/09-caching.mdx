      ### Why cache?

      A cache stores a *subset* of frequently accessed or expensive-to-compute data in a fast layer, so repeated work is skipped.

      - **Cache hit** — served instantly from the fast layer.
      - **Cache miss** — fall back to the source, then store the result for next time.
      - **Two reasons to cache** — avoid heavy computation (search rankings, trending topics) and avoid heavy data transfer (serving hot content close to users).
      - **Levels of caching** — network (CDN edge servers, DNS resolvers), hardware (CPU L1/L2/L3, RAM vs disk), software (**in-memory stores like Redis**).
      - **80/20 rule** — a small fraction of data (the popular products) serves most requests; cache that hot subset, not everything.

      **Use case:** a product catalog is read-heavy — thousands of views per product, one price change a day. Cache the product detail and the database barely gets touched.
  - type: markdown
    content: |
      ### Cache-aside vs write-through vs write-back

      - **Cache-aside (lazy)** — read: check cache → miss → fetch from DB → populate cache → return. Write: update the DB, then **invalidate** the cache key. Cache is populated on demand; a miss costs one extra read, but the DB stays the source of truth.
      - **Write-through** — every write updates the DB *and* the cache together. Cache is always fresh; writes get slower.
      - **Write-back** — writes go to the cache and are flushed to the DB later (in batches). Fastest writes, riskiest — a crash before the flush loses data.

      **Use case:** product detail pages use cache-aside with a TTL — simple, stale-tolerant, and the database remains the source of truth.

      ### Redis basics

      - **In-memory key-value store** — data lives in RAM: orders of magnitude faster than disk, with optional background snapshots for durability.
      - **Operations** — `SET product:123 '{"name": "Sneaker", "price": 99}'`, `GET product:123`, `EXPIRE` / `SET ... EX 300` (TTL), `INCR` for counters.
      - **TTL (Time To Live)** — a timer per key; expired keys are deleted automatically. Your first line of defense against stale data.
      - **Eviction when memory fills** — **LRU** (evict the least recently used: yesterday's product, keep today's) or **LFU** (evict the least frequently used: the long tail). Caches typically run `allkeys-lru`.

      **Use case:** session storage — querying a session id from Postgres on every API call adds latency; Redis answers in microseconds.
  - type: markdown
    content: |
      ### Invalidation — the hard part

      - **Delete-on-write** — when the DB changes, delete (or overwrite) the key; the next read repopulates from fresh data. Simpler and safer than trying to keep cache values in sync.
      - **Versioned keys** — `product:123:v7`; bump the version on change so old clients can never read stale cache.
      - **Cache stampede (dogpile)** — thousands of requests miss at once (a hot key's TTL expired) and all hit the DB. Fix: stale-while-revalidate (serve the old value while one background request refreshes) or a mutex so a single request repopulates.
      - **Cache penetration** — attackers request nonexistent ids (`product:999999`) that always miss and hammer the DB. Fix: cache negative results briefly, or reject ids outside the valid range.
      - **TTL as the safety net** — even if an invalidation is missed, TTL bounds how stale a value can get.

      **Use case:** the storefront caches `product:{id}` with a 300s TTL and deletes the key on every admin price edit — staleness is bounded even if a delete fails.
  - type: markdown
    content: |
      ### Worked example — caching a storefront

      - **Product detail (hot):** key `product:{id}`, value = JSON, TTL 300s. On an admin price change: update the DB, then `DEL product:{id}`. The catalog survives Black Friday because ~95% of reads hit Redis.
      - **Cart per session:** key `cart:{session_id}`, a Redis list/hash — instant reads and writes, TTL refreshed on activity.
      - **Rate limiting:** key `rl:{ip}:{minute}`, `INCR` + TTL 60s; over 50 requests → `429`. Redis handles this in microseconds where a DB would drown in writes.
      - **Third-party APIs:** fetch shipping quotes or weather once, cache for an hour — saves rate limits and money.

      ### Reading the cache, end to end

      `GET /products/123` → `GET product:123` → hit? serve. Miss? `SELECT * FROM products WHERE id = 123` → `SET product:123 <json> EX 300` → serve.

      ### Interview questions

      :::tip
      **Interview question:** Cache-aside vs write-through — when do you use which?
      — Cache-aside for almost everything: the DB stays the source of truth, writes are simple (update DB, invalidate), and TTL bounds staleness. Write-through only when reads must be instantly consistent with writes, which is rare — it adds latency to every write. Write-back only when write throughput matters more than durability.
      :::

      :::tip
      **Interview question:** How do you keep the cache consistent with the database?
      — The pragmatic pattern: update the database first, then delete the cache key — invalidate, don't update. The next read misses and repopulates from the fresh DB row. TTLs are the safety net that bounds staleness even if a delete is missed, and versioned keys (`product:123:v2`) handle coordinated changes.
      :::

      :::tip
      **Interview question:** What is a cache stampede and how do you stop it?
      — When a hot key expires, hundreds of concurrent requests all miss and hit the DB at once. Fixes: stale-while-revalidate (serve the old value while one background request refreshes), request coalescing (one request repopulates, the rest wait), or jittered TTLs so hot keys don't expire simultaneously.
      :::
