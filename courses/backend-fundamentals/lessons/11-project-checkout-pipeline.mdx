      # Project 2: Checkout Pipeline

      **Context.** The cart is done (lesson 10). Now the moment of truth: the
      shopper taps **Checkout**. One request must validate the order, check
      stock, reserve stock, and create the order — and it must survive
      retries, crashes, and double-clicks. This lesson builds the **checkout
      pipeline**: a real service (`services/orderService.js`) and the
      controller that drives it (`controllers/ordersController.js`), guarded
      by an idempotency key.

      **What you are building this step.** Two real modules: `services/orderService.js` and the controller that drives it (`controllers/ordersController.js`), guarded by an idempotency key. In the platform exercise below you write the **controller** (the service is provided, mounted read-only alongside it); in the offline project you write **both** — same contract, same tests.

      - `orderService.checkout({ userId, items, idempotencyKey })` — decides
        the outcome (confirmed / insufficient stock / insufficient funds),
        reserves stock, creates the order, and replays stored results for a
        repeated idempotency key.
      - `ordersController.checkout` — the thin HTTP mapping: reads
        `req.body.items`, `req.headers['idempotency-key']` and `req.user.id`,
        delegates to the service, and maps the result to a status code.

      This is **real backend practice, done test-first**: the two modules
      ship with a full, visible `node:test` suite (`tests/orders.test.js`)
      that boots a real Express app and drives it with `fetch` — a genuine
      integration test. Nothing is hidden — every test case is printed in
      this lesson.

      **Acceptance criteria**

      - `POST /api/orders` validates the body, checks the idempotency key,
        then runs the checkout pipeline.
      - Out-of-stock or missing product → rejected with **409 Conflict**,
        nothing reserved.
      - Insufficient balance → rejected with **402 Payment Required**,
        nothing reserved.
      - Success → order created (stock reservation + order insert commit
        together or not at all), **201 Created**.
      - Replaying the same `Idempotency-Key` returns the stored order
        (**200**) instead of charging twice.

      **How this lesson is graded.** The platform grades the module exercise
      below — a visible node:test suite runs your `controllers/ordersController.js`
      in a sandbox. The same suite is the real deliverable in the shipped
      project: run `npm test` and make `tests/orders.test.js` green.

      ## Module contract — `services/orderService.js` + `controllers/ordersController.js`

      The project and this lesson agree **exactly** on this surface.

      **`orderService.checkout({ userId, items, idempotencyKey })`**

      Returns a promise of `{ status, order, replayed }`:

      | Field | Meaning |
      |-------|---------|
      | `status` | `'confirmed'` \| `'insufficient_stock'` \| `'insufficient_funds'` |
      | `order` | The created order (`{ id, userId, items, total, status, idempotencyKey, createdAt }`) for `confirmed`; `null` for the two rejections. |
      | `replayed` | `true` when the `idempotencyKey` was already used — the `order` is the **stored** order, returned untouched. |

      **Item shape.** `items` is an array of `{ productId, qty, unitPrice }`
      — the same shape the cart service produces (lesson 10). `total` is
      `Σ qty × unitPrice`.

      **Decision order** (checked before anything is written): every item
      must exist in stock with `available >= qty` — otherwise
      `insufficient_stock`; then `balance >= total`, otherwise
      `insufficient_funds`; otherwise the order is `confirmed` and stock is
      reserved. A repeated key short-circuits everything and replays.

      **`ordersController.checkout`** — maps the service result to HTTP:

      | Service result | HTTP |
      |----------------|------|
      | `confirmed` | **201** Created |
      | `insufficient_stock` | **409** Conflict |
      | `insufficient_funds` | **402** Payment Required |
      | `replayed: true` | **200** OK (the stored order) |

      **Test seams.** The service ships an in-memory store so the suite runs
      with zero infrastructure. Three documented, test-only exports seed it
      between tests: `__setStock(productId, available)`,
      `__setBalance(userId, cents)` and `__reset()`. In production the same
      contract is implemented over Postgres (stock, balances, orders) and
      Redis (the idempotency claim via `SETNX`) inside a
      `BEGIN … COMMIT` transaction — the decision rule is identical.

      :::example
      Items `[{ productId: 1, qty: 2, unitPrice: 100 }]`, stock for product 1
      is 5, balance is 1000. Total `= 2 × 100 = 200`. Stock fine, 1000 ≥ 200
      → `{ status: 'confirmed', order: { total: 200, … }, replayed: false }`
      → **201**.
      :::

      :::example
      Same items, stock 5, but qty 10 requested — we want 10 but only 5
      exist. Stock is checked *before* money → `{ status:
      'insufficient_stock', order: null }` → **409**.
      :::

      :::example
      Balance 100 < total 200 → `{ status: 'insufficient_funds', order:
      null }` → **402**.
      :::

      :::example
      The same `Idempotency-Key` arrives a second time → `{ replayed: true,
      order: <the stored order> }` → **200** with the original order, no
      second charge, no second reservation.
      :::

      **Edge cases you must handle** (all covered by the visible suite):
      buying exactly the available stock is allowed; a product id missing
      from stock entirely is `insufficient_stock`; a replayed key does not
      reserve stock a second time; the controller must take the user from
      `req.user` (never from the request body).

      The controller is the thin status mapper from the contract. The service
      is where the pipeline runs. In production, `checkout` looks like this
      (the in-memory store of the test version is swapped for real storage,
      and the decision rule is unchanged):

      ```js
      // services/orderService.js — the production shape of checkout
      async function checkout({ userId, items, idempotencyKey }) {
        // 0. idempotency: has this key been seen? Redis SETNX with a TTL.
        const claimed = await redis.set(idempotencyKey, 'pending', 'NX', 'EX', 3600);
        if (!claimed) {
          return { replayed: true, order: await getByKey(idempotencyKey) };
        }

        // 1. decision — the same rule the tests check:
        //    confirmed | insufficient_stock | insufficient_funds
        const decision = decide(items, await stockSnapshot(), balanceFor(userId));
        if (decision.status !== 'confirmed') return decision; // 409 / 402

        const client = await pool.connect();
        try {
          await client.query('BEGIN');
          // 2. reserve stock atomically: UPDATE products SET available = available - $1
          //    WHERE id = $2 AND available >= $1  → rowCount 0 means oversold
          // 3. INSERT the order row (status 'confirmed')
          // 4. stamp the idempotency key with the order id
          await client.query('COMMIT');
          return { replayed: false, status: 'confirmed', order };
        } catch (err) {
          await client.query('ROLLBACK');
          throw err;
        } finally {
          client.release();
        }
      }
      ```

      Three things make this safe. **One transaction** — the stock decrement
      and the order insert are atomic: either both commit or both roll back,
      so a crash between them cannot leave stock reserved with no order.
      **The conditional UPDATE** — `available >= $1` turns a race into a
      rejected request instead of a negative stock count. **The idempotency
      key** — a network retry of the same checkout replays the stored order
      instead of charging the card twice.

      ## Interview questions

      :::tip
      **Interview question:** What happens if the process crashes between
      "reserve stock" and "insert order"? Without a transaction you get a
      permanent inconsistency: stock decremented, no order, money never
      charged. With `BEGIN … COMMIT/ROLLBACK`, the crash aborts the open
      transaction and Postgres rolls it back — the reservation vanishes and
      the inventory returns to its previous state. That atomicity is the `A`
      in ACID, and checkout is the canonical example.
      :::

      :::tip
      **Interview question:** Why use an idempotency key instead of just
      checking "does this order already exist"? Because two identical orders
      are indistinguishable from two legitimate purchases of the same items —
      the user might genuinely want to buy the same thing twice. The key is
      client-generated and unique per *intent*: retrying the same checkout
      sends the same key and replays the stored result, while a genuinely new
      purchase sends a new key. `SETNX` makes the claim atomic so two
      concurrent retries cannot both slip through.
      :::

      **Use case.** Payment providers and mobile clients retry aggressively —
      a dropped response on a 3G network can resend the same checkout seconds
      later. Without the key, that retry charges the shopper twice. With it,
      the second attempt returns the first order untouched: one charge, one
      order, one happy customer.

          //   status ∈ 'confirmed' | 'insufficient_stock' | 'insufficient_funds'

            for (const item of items) {
              const available = store.stock.get(item.productId) ?? -1;
              if (available < item.qty) {
                return { replayed: false, status: 'insufficient_stock', order: null };
              }
            }

            // 2. Funds check.
            const total = items.reduce((sum, item) => sum + item.qty * item.unitPrice, 0);
            const balance = store.balances.get(userId) ?? 0;
            if (balance < total) {
              return { replayed: false, status: 'insufficient_funds', order: null };
            }

            // 3. Confirmed — reserve stock and create the order atomically.
            for (const item of items) {
              store.stock.set(item.productId, store.stock.get(item.productId) - item.qty);
            }
            store.seq += 1;
            const order = {
              id: `ord_${store.seq}`,
              userId,
              items,
              total,
              status: 'confirmed',
              idempotencyKey,
              createdAt: new Date().toISOString(),
            };
            store.orders.set(idempotencyKey, order);

            return { replayed: false, status: 'confirmed', order };
          }

      // Reads req.body.items + req.headers['idempotency-key'] + req.user.id,
      // delegates to orderService.checkout, and maps the result to HTTP:
      //   confirmed           -> 201 Created
      //   insufficient_stock  -> 409 Conflict

      //   replayed            -> 200 OK (the stored order, no duplicate)
      const orderService = require('../services/orderService');

      const STATUS_TO_HTTP = {
        confirmed: 201,
        insufficient_stock: 409,
        insufficient_funds: 402,

      async function checkout(req, res, next) {
        try {
          const result = await orderService.checkout({
            userId: req.user.id,
            items: req.body.items,
            idempotencyKey: req.headers['idempotency-key'],
          });
          if (result.replayed) {
            return res.status(200).json({ data: result.order });
          }
          res.status(STATUS_TO_HTTP[result.status]).json({ data: result.order });
        } catch (err) {
          next(err);
        }
      }
