      if n <= 1:

      a, b = 0, 1
      for _ in range(2, n + 1):
          a, b = b, a + b
      return b

Fibonacci is the simplest problem that shows the two ideas every DP problem is
built on: **overlapping subproblems** and **optimal substructure**. Master this
and you have the vocabulary for everything that follows.

## The naive recursion

The definition is itself a recursion: `F(n) = F(n-1) + F(n-2)`. Write it exactly
as written and it works — but it is *slow*. Try tracing `fib(5)` on paper and
count how many times you compute `fib(2)`.

:::example
`fib(5)` needs `fib(4)` and `fib(3)`. `fib(4)` needs `fib(3)` and `fib(2)`.
`fib(3)` needs `fib(2)` and `fib(1)`. The same tiny subproblems repeat over and
over. By `fib(10)`, you are computing `fib(2)` dozens of times.
:::

The runtime explodes to **O(2^n)**. That is the problem DP solves.

## Overlapping subproblems

`fib(2)` appears many times inside `fib(10)`. You are redoing work you already
did. The insight of DP: **compute each subproblem once, remember it, reuse it.**
That single change turns an exponential problem into a linear one.

## Memoization (top-down)

Keep the recursion, add a cache. Before computing `fib(n)`, check the cache. If
it is there, return it. If not, compute it and store it. This is called
*memoization* — O(n) time, O(n) space. In Java, a `HashMap<Integer, Long>` works
well.

## Tabulation (bottom-up)

The other direction: compute the small cases first and build up. Start with
`F(0)` and `F(1)`, then fill `F(2)`, `F(3)`, ... in order. No recursion, no
stack overflow.

:::tip
You only ever need the last two values. Instead of a full table, keep two
variables (`a`, `b`) and slide them forward. That shrinks space to O(1).
:::

## Which style should I use?

For learning, try memoization first — it matches how you think about a problem
recursively. Then rewrite the same problem bottom-up. Both are valid, and
interviewers often expect you to be able to do both.
