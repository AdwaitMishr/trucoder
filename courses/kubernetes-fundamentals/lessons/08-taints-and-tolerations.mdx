Taints are how a cluster says **"keep off"** to pods. A node with
`gpu=true:NoSchedule` will not schedule ordinary pods onto itself. A pod that
*needs* the GPU opts back in with a matching **toleration** — the explicit
"yes, I accept this."

## The format

Both sides are `key=value:effect`:

- `key` — what the taint is about (`gpu`, `spot`, `db`).
- `value` — the specific value (may be **empty** on a toleration: "any value
  is fine").
- `effect` — what the taint does: `NoSchedule` (don't schedule), `NoExecute`
  (evict running pods), `PreferNoSchedule` (soft preference). May be **empty**
  on a toleration: "any effect is fine".

## The matching rules

A toleration tolerates a taint when **all three** parts line up:

| Part | Toleration matches if… |
|------|------------------------|
| key | equal to taint key, OR toleration key is `*` |
| value | equal to taint value, OR toleration value is empty |
| effect | equal to taint effect, OR toleration effect is empty |

:::example
Taint `gpu=true:NoSchedule`:

| Toleration | Tolerates? | Why |
|------------|-----------|-----|
| `gpu=true:NoSchedule` | yes | exact match |
| `gpu=:NoSchedule` | yes | value empty = any value |
| `gpu=true:` | yes | effect empty = any effect |
| `*=:NoSchedule` | yes | key `*` = any key |
| `gpu=false:NoSchedule` | no | value differs |
| `gpu=true:NoExecute` | no | effect differs |
| `db=:NoSchedule` | no | key differs |
:::

:::warning
The three conditions are ANDed — a toleration that matches the key but not the
effect does **not** tolerate the taint. It is not "any one match wins"; all
three parts must be satisfied.
:::

:::tip
`NoExecute` is the sharp one: it evicts pods that are already running without
the toleration. `NoSchedule` only blocks *new* scheduling — which is why
`NoSchedule` taints are safe to add to a live node, and `NoExecute` taints are
not.
:::
