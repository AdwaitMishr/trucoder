A Pod is not useful the instant it starts — it needs to warm up, connect to
databases, load config. Kubernetes asks the question *"are you ready to serve
yet?"* with a **readiness probe**.

## The three knobs

- `initialDelaySeconds` — how long to wait *before* the first probe. The app
  gets time to boot before anyone starts poking it.
- `periodSeconds` — how often to probe after that.
- `failureThreshold` — how many consecutive failures make the pod NotReady.

If every probe fails, the timeline looks like this:

```
t = initialDelay          probe 1 (failure 1)
t = initialDelay + period probe 2 (failure 2)
t = initialDelay + 2·period probe 3 (failure 3)  <- threshold reached: NotReady
```

:::example
`periodSeconds: 10, failureThreshold: 3, initialDelaySeconds: 5`:

probes fail at t = 5, t = 15, t = 25. The third consecutive failure is at
t = **25** → NotReady.

`periodSeconds: 5, failureThreshold: 2, initialDelaySeconds: 0`:

failures at t = 0 and t = 5 → NotReady at **5**.
:::

## The formula

`initialDelay + period × (threshold − 1)`

The `− 1` is the subtle part: the first probe *is* failure number one, so you
only wait for `threshold − 1` more periods after the initial delay.

:::warning
Do not write `period × threshold`. That would count one period *before* the
first probe ever ran — the probe at `initialDelay` is already failure 1, not
failure 0.
:::

:::tip
Readiness determines traffic, not restarts. A NotReady pod stops receiving
requests but keeps running — the *liveness* probe is the one that kills and
restarts a stuck pod. Same mechanics, different consequence.
:::
