Pods come and go; their IP addresses change every time. A **Service** is a
stable name in front of a moving set of Pods. To make that name usable, the
cluster's DNS server answers it — everywhere.

## The name

Every Service in a namespace gets an automatic DNS record:

```
<service-name>.<namespace>.svc.cluster.local
```

Walk it right to left:

- `cluster.local` — the cluster's private DNS zone (never resolves off-cluster).
- `svc` — "this is a Service", as opposed to a Pod or a headless endpoint.
- `<namespace>` — namespaces are the *scoping* layer: the same service name can
  exist in two namespaces, and the namespace part disambiguates them.
- `<service-name>` — the Service's own name.

:::example
Service `web` in the `default` namespace:

`web.default.svc.cluster.local`

A pod in the *same* namespace can skip the namespace — the short name `web`
resolves too. A pod in another namespace must use the full name.
:::

## Why namespaces matter

Two teams can both have a `payments` service if each lives in its own
namespace. The DNS name makes the address unique: `payments.team-a.svc...`
versus `payments.team-b.svc...`. Without the namespace, the name would collide.

:::warning
Do not swap the order. It is `name.namespace`, not `namespace.name`. And do not
forget the dots — the three pieces join with dots, not with nothing.
:::

:::tip
`svc.cluster.local` is a fixed tail. If you ever see it, you know the record
names a Service inside the cluster — and that the lookup will never leave it.
:::
