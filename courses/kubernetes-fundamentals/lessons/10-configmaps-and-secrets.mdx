      Hard-coding configuration into a container image is a one-way trip:
      every change means a rebuild. **ConfigMaps** and **Secrets** pull that
      data out of the image and into the cluster, where it can change without
      rebuilding anything.

      - ConfigMap — non-sensitive config: `LOG_LEVEL=info`, feature flags.
      - Secret — sensitive config: passwords, tokens, keys.

      Both are consumed the same three ways: as environment variables, as
      mounted files, or (rarely) as command arguments.

      ## ConfigMap

      ```yaml
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name: shop-config
      data:
        APP_ENV: production
        LOG_LEVEL: info
      ```

      As environment variables — every key becomes a variable:

      ```yaml
      spec:
        containers:
          - name: app
            image: ghcr.io/adith2005-20/shop-api:v1
            envFrom:
              - configMapRef:
                  name: shop-config
      ```

      Or as a mounted file — the ConfigMap appears as files in the container:

      ```yaml
          volumeMounts:
            - name: config
              mountPath: /etc/shop
      volumes:
        - name: config
          configMap:
            name: shop-config
      ```

      `kubectl get configmap shop-config -o yaml` shows the data; the keys
      become files under the mount path (`/etc/shop/APP_ENV`).

      ## Secret

      A Secret looks identical but the values are base64-encoded:

      ```yaml
      apiVersion: v1
      kind: Secret
      metadata:
        name: shop-secrets
      type: Opaque
      data:
        REDIS_PASSWORD: c3VwZXJzZWNyZXQ=    # base64 of "supersecret"
      ```

      ```bash
      # create from a literal (kubectl encodes it for you)
      kubectl create secret generic shop-secrets \
        --from-literal=REDIS_PASSWORD=supersecret \
        --from-literal=API_TOKEN=abc123
      ```

      :::warning
      base64 is **not** encryption — it is an obfuscated encoding. Anyone who
      can read the cluster (or `kubectl get secret -o yaml`) can decode it.
      Real protection needs encryption at rest (kms) and access control
      (RBAC). Treat the *text* of a Secret as already-leaked if it is
      committed to git.
      :::

      :::tip
      Prefer mounted secrets over environment variables when you can:
      mounting a Secret as files updates automatically when the Secret
      changes, and tools can watch the file. Env vars are frozen at pod
      start — the pod must restart to pick up a new value.
      :::

      ## The commands

      ```bash
      kubectl create configmap shop-config --from-literal=APP_ENV=production
      kubectl create configmap shop-config --from-file=config.properties
      kubectl create secret generic shop-secrets --from-literal=REDIS_PASSWORD=supersecret
      kubectl create secret generic shop-secrets --from-file=tls.crt --from-file=tls.key
      kubectl get configmaps,secrets
      kubectl describe pod <pod>          # shows which configmaps/secrets a pod uses
      ```

      ## Env vars vs mounts — pick by mutation

      | Need | Use |
      |------|-----|
      | one-time values at boot | env vars (`envFrom`) |
      | values that change without restart | mounted files |
      | TLS certificates | mounted files (always) |
      | command-line flags | `valueFrom.configMapKeyRef` / `secretKeyRef` |

      ## The mental model

      ```text
      image  = code, frozen
      config = behavior, changeable without rebuild
      ```

      :::example
      Your app reads `LOG_LEVEL` from `envFrom.configMapRef`. You bump it to
      `debug` in the ConfigMap and roll the deployment — no image rebuild,
      no docker push. The image never knew the value existed.
      :::
