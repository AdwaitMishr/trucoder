      A Deployment is for *long-running* services: N replicas, forever. But
      not every workload runs forever. Kubernetes has a controller for each
      job shape — and the shape is a *choice you make in the manifest*.

      ## The four controllers

      | Controller | Runs | Example |
      |------------|------|---------|
      | Deployment | N replicas, always | web API |
      | Job | once to completion | migrate the database |
      | CronJob | Job on a schedule | nightly backup |
      | DaemonSet | exactly one per node | logs agent, kube-proxy |
      | StatefulSet | N replicas with stable identity | databases, message brokers |

      ## Job — run something to completion

      ```yaml
      apiVersion: batch/v1
      kind: Job
      metadata:
        name: db-migrate
      spec:
        completions: 1
        parallelism: 1
        template:
          spec:
            restartPolicy: Never
            containers:
              - name: migrate
                image: ghcr.io/adith2005-20/shop-api:v1
                command: ["node", "migrate.js"]
      ```

      The pod runs until it exits 0. On failure it retries (or, with
      `restartPolicy: Never` + `backoffLimit`, gives up after N tries).
      `kubectl get jobs`, `kubectl logs job/db-migrate`.

      :::warning
      A Job pod must NOT use `restartPolicy: Always` — that is the
      Deployment default and Jobs reject it. `Never` or `OnFailure` only.
      :::

      ## CronJob — the scheduler

      ```yaml
      apiVersion: batch/v1
      kind: CronJob
      metadata:
        name: nightly-backup
      spec:
        schedule: "0 2 * * *"        # 2 AM every day — standard cron syntax
        concurrencyPolicy: Forbid    # don't overlap runs
        jobTemplate:
          spec:
            template:
              spec:
                restartPolicy: Never
                containers:
                  - name: backup
                    image: ghcr.io/adith2005-20/shop-api:v1
                    command: ["node", "backup.js"]
      ```

      `kubectl get cronjobs` shows the schedule; `kubectl get jobs -l
      job-name=nightly-backup` shows the runs. A missed run is gone — the
      schedule is not a backlog.

      ## DaemonSet — one pod per node

      ```yaml
      apiVersion: apps/v1
      kind: DaemonSet
      metadata:
        name: fluentd
      spec:
        selector:
          matchLabels:
            name: fluentd
        template:
          metadata:
            labels:
              name: fluentd
          spec:
            containers:
              - name: fluentd
                image: fluent/fluentd:v1.16
      ```

      New node joins the cluster → a pod appears on it automatically. That
      is how log collectors, metrics agents, and kube-proxy work.

      ## StatefulSet — stable identity for stateful apps

      ```yaml
      apiVersion: apps/v1
      kind: StatefulSet
      metadata:
        name: redis
      spec:
        serviceName: redis-headless   # a headless Service (clusterIP: None)
        replicas: 3
        selector:
          matchLabels:
            app: redis
        template:
          metadata:
            labels:
              app: redis
          spec:
            containers:
              - name: redis
                image: redis:7
        volumeClaimTemplates:
          - metadata:
              name: data
            spec:
              accessModes: ["ReadWriteOnce"]
              resources:
                requests:
                  storage: 1Gi
      ```

      Pods get *ordered, stable* names: `redis-0`, `redis-1`, `redis-2`.
      Each gets its own PVC (the `volumeClaimTemplate` makes one per pod).
      Scaling and updates happen one at a time, in order. Databases and
      message brokers need this; stateless web apps do not.

      ## The decision

      ```text
      Does it serve traffic forever?      -> Deployment
      Does it finish a task?              -> Job / CronJob
      Does every node need one?           -> DaemonSet
      Does it need stable names + disks?  -> StatefulSet
      ```

      :::example
      ShopAPI: the API itself is a Deployment, the DB migration is a Job,
      the nightly report is a CronJob, the log collector is a DaemonSet,
      and Redis is a StatefulSet. One cluster, five different controllers —
      each picked because of *how the work behaves*.
      :::
