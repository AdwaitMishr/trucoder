      ### Compile-time polymorphism

      - **Function overloading** — same name, different parameter lists (type,
        count, or order); resolved at compile time.

      ```cpp
      int add(int a, int b);
      double add(double a, double b);   // overload — different params
      ```

      - **Operator overloading** — give operators class-specific meaning:
        `a + b`, `a[i]`, `std::cout << a`.
      - Zero runtime cost — the compiler picks the exact function.

      **Use case:** `std::string` overloads `+`, `==`, `<<`; your `Matrix`
      class overloads `operator+` and `operator*`.
  - type: markdown
    content: |
      ### Runtime polymorphism — virtual functions

      - `virtual` enables **dynamic dispatch**: the call is resolved at runtime
        by the object's *actual* type, not the pointer's static type.
      - `override` — declares "I override a base virtual"; the compiler checks.
      - `final` — prevents further overriding (on a class, prevents
        inheritance).

      ```cpp
      class Shape {
      public:
          virtual double area() const { return 0; }  // virtual — dynamic dispatch
      };
      class Circle : public Shape {
      public:
          double area() const override { return pi * r * r; }
      };

      Shape* s = new Circle();
      s->area();   // Circle::area runs — decided at runtime
      ```

      **Use case:** a `std::vector<Shape*>` of mixed shapes — one loop calls
      `area()` and every object runs its own version.
  - type: markdown
    content: |
      ### vtable & vptr — how dynamic dispatch works

      - Each **polymorphic class** gets one **vtable**: an array of function
        pointers, one entry per virtual function.
      - Each **object** carries a hidden **vptr** pointing to its class's
        vtable.
      - A virtual call is: `ptr->vptr->vtable[index]` — an **indirect call**
        through two pointer hops.

      **Cost:** one vptr per object (usually 8 bytes), one vtable per class,
      and an indirect call per virtual call — no inlining, worse cache and
      branch-prediction behavior.

      :::tip
      **Interview question:** what is the cost of virtual functions? — Per
      object: one hidden vptr (~8 bytes). Per class: one vtable. Per call: an
      indirect jump through vptr → vtable instead of a direct call, which also
      defeats inlining and hurts branch prediction / cache locality.
      :::

      ### Pure virtual functions & the virtual destructor (the #1 trap)

      - `virtual void draw() = 0;` — **pure virtual**; the class becomes
        **abstract** and cannot be instantiated; derived classes must override
        it to be concrete.
      - **Virtual destructor:** if you `delete` a `Derived` through a `Base*`
        and the base destructor is NOT virtual, only the base part is
        destroyed — **undefined behavior**, and the derived resources leak.

      ```cpp
      class Base {
      public:
          virtual ~Base() = default;   // ALWAYS virtual when polymorphic
      };
      ```

      **Use case / trap:** every polymorphic base (`Shape`, `Animal`,
      `Widget`) needs a virtual destructor — the classic interview question.

      :::tip
      **Interview question:** when do you need a virtual destructor? — Whenever
      derived objects are deleted through a base-class pointer or reference.
      Without it, the destructor call is statically bound to `~Base`, the
      derived destructor never runs, and the behavior is undefined.
      :::
