      ### The 5 types of inheritance

      ```
      single        multilevel        hierarchical     multiple        hybrid
        A              A                  A             A     B         A (shared)
        |              |                 / \             \   /          / \
        B              B                B   C            \ /          B   C
                       |                                   D            \ /
                       C                                                 D
      ```

      - **Single** — one class inherits from one base.
      - **Multiple** — one class inherits from more than one base (`D : A, B`).
      - **Multilevel** — a chain: `C` inherits `B` inherits `A`.
      - **Hierarchical** — one base, several derived classes.
      - **Hybrid** — any combination (multiple + multilevel), e.g. the diamond.

      ### Access modes of inheritance

      | Base member | public inheritance | protected inheritance | private inheritance |
      |---|---|---|---|
      | public | public | protected | private |
      | protected | protected | protected | private |
      | private | (not accessible) | (not accessible) | (not accessible) |

      - **Public inheritance** models **is-a**: `class Dog : public Animal`.
      - **Private/protected inheritance** is implementation reuse — prefer
        **composition (has-a)** instead.

      **Rule of thumb:** use inheritance for *is-a*, composition for *has-a*.
      A `Car` **has-a** `Engine` (composition); a `Car` **is-a** `Vehicle`
      (inheritance).
  - type: markdown
    content: |
      ### Object slicing

      - Assigning or passing a `Derived` **by value** to a `Base` copies only
        the base part — the derived members are **sliced off**.

      ```cpp
      Derived d;
      Base b = d;          // d's derived parts are lost (sliced)
      void f(Base b);      // f(d) also slices
      void g(const Base& b); // g(d) is fine — reference, no slicing
      ```

      **Use case / trap:** storing derived objects in a `std::vector<Base>`
      slices them silently — store pointers or smart pointers instead.

      ### The diamond problem

      - `class B : public A;` and `class C : public A;`, then
        `class D : public B, public C;`
      - `D` now contains **two copies** of `A`'s sub-object, and `d.a` /
        `d.A::x` is **ambiguous** — the compiler cannot pick which copy.
      - Fix: **virtual inheritance** — `class B : virtual public A;`,
        `class C : virtual public A;` — the two `A` sub-objects collapse into
        **one shared** sub-object.

      :::tip
      **Interview question:** what is the diamond problem and how do you fix
      it? — When a class inherits from two classes that share a common base,
      the common base is duplicated in the derived object, making its members
      ambiguous. Declare the shared base `virtual` in the intermediate classes
      so the derived class gets a single shared base sub-object.
      :::

      ### **Interview questions**

      :::tip
      **Interview question:** composition over inheritance — when? — Prefer
      composition unless there is a genuine *is-a* relationship and you need
      polymorphism. Inheritance couples derived to base and can leak base
      internals; composition (`std::unique_ptr<Engine>`) is flexible and
      testable. Use inheritance when a derived object must be usable wherever a
      base reference/pointer is expected (Liskov substitutability).
      :::

      - Inherited members keep their access unless the inheritance mode lowers
        it (see the table).
      - Virtual inheritance costs a small size/indirection overhead on the
        derived objects — use it only where the diamond actually exists.
