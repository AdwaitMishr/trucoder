      ### auto type deduction

      - `auto x = expr;` — the compiler deduces the type from the initializer.
        **Top-level `const` and references are dropped** — ask for them
        explicitly: `const auto&`, `auto&`.
      - `auto` needs an initializer — there is nothing to deduce otherwise.
      - Works for variables, function return types (C++14), and parameters of
        generic lambdas (C++14).

      **Use case:** `auto it = v.begin();` — the iterator type is long and
      uninteresting; `auto` keeps the code readable and correct when the type
      changes.

      ### Range-based for + auto

      ```cpp
      for (const auto& x : v) { ... }   // read-only, NO copy
      for (auto& x : v) { ... }         // mutate in place
      for (auto x : v) { ... }          // copies each element
      ```

      **Use case:** summing a vector, printing elements — no index, no iterator
      spelling, and `const auto&` guarantees you never copy a `std::string` by
      accident.

      ### C++17 additions — one line each

      - **Structured bindings** — `auto [a, b] = std::make_pair(1, 2);`
        decomposes pairs, tuples, arrays, and structs with public members into
        named variables — no more `.first` / `.second` or `std::get<0>`.
      - **`std::optional<T>`** — a `T` that may be absent (`std::nullopt`);
        use it for *"maybe a value"* returns (a lookup that can miss, parsing)
        instead of sentinel values like `-1` or `nullptr`.
      - **`std::variant<T...>`** — a type-safe union holding *exactly one* of
        several types; use it when a value can be one of a few types (e.g. a
        parse result: `int` | error `std::string`), checked with
        `std::holds_alternative` / `std::get`.
      - **`if constexpr (cond)`** — the branch is chosen at **compile time**
        and the discarded branch is *not instantiated*; essential inside
        templates.
      - **`constexpr` vs `const`** — `const` is a *read-only promise* (the
        value may be runtime or compile-time); `constexpr` means *computable
        at compile time* and usable in constant expressions. A `constexpr`
        function may also be called at runtime (C++14+); for variables,
        `constexpr` implies `const`.
      - **`nullptr` vs `NULL`** — `NULL` is a macro (`0` / `(void*)0`) that
        can silently become an `int` and break overloads; `nullptr` is a
        `std::nullptr_t` literal that converts **only to pointer types** —
        type-safe, always prefer it.

      ### Lambdas vs function pointers vs std::function

      - **Lambda** — `[capture](params) -> ret { body }`; captures by value
        `[=]`/`[x]` or by reference `[&]`/`[&x]`. A lambda is a compiler-made
        **closure type** — direct calls are **inlinable, zero overhead**.
      - **Generic lambda** — `[](auto x) { ... }` (C++14): the parameter type
        is deduced per call, like a template.
      - **Function pointer** — `int (*f)(int)`. A *non-capturing* lambda
        converts to one implicitly; a capturing lambda **cannot**.
      - **`std::function<Ret(Args...)>`** — a **type-erased** wrapper: it can
        hold any callable (capturing lambdas, functors, member functions)
        behind one signature. Costs: an **indirect call** and, for captures, a
        **heap allocation** — the compiler cannot inline through it.
      - **When each:** use lambdas/templates by default (fast, flexible);
        reach for `std::function` only when the callable's type must be a
        **runtime value** — callback registries, containers of handlers,
        interfaces across a library boundary.

      **Use case:** `std::sort(v.begin(), v.end(), [](auto a, auto b) { return
      a > b; })` — a generic lambda comparator, no type spelling, no overhead.

      ### Concurrency — threads, mutexes, async

      - **`std::thread t(f, args);`** — runs `f` on a new OS thread. You must
        `t.join()` (wait for it) or `t.detach()` (let it run in the
        background); destroying a *joinable* thread without either calls
        `std::terminate`.
      - **`std::mutex` + `std::lock_guard<std::mutex> lock(m);`** — the
        lock_guard locks in its constructor and **unlocks in its destructor**
        (RAII for locks): even if the guarded body throws, the mutex is
        released — you can never forget an `unlock()`.
      - **`std::async(f)`** — runs a task asynchronously and returns a
        `std::future<T>`; `future.get()` blocks until the result is ready.
        Gotcha: a future from `std::async` **blocks in its destructor** until
        the task completes, so discarding it is *not* true fire-and-forget —
        use `std::thread` + `detach()` for that.
      - **Data race** — two or more threads access the *same memory location*
        concurrently, **at least one access is a write**, and there is **no
        synchronization** → **undefined behavior** in the C++ memory model.
      - **Why `std::atomic<T>` exists** — `x++` on a plain `int` is a
        *read-modify-write* (load, add, store) that can interleave between
        threads. `std::atomic` makes the operation **indivisible** (and gives
        memory-ordering guarantees) for a single variable — no mutex needed.

      ### Quick answers: virtual + inline / static / private

      - **Virtual + inline: possible.** `inline` is a hint — it matters for
        *non-virtual* (direct) calls. A virtual call through the vtable is an
        indirect call and is normally not inlined (the compiler may
        devirtualize `final` classes and inline those).
      - **Virtual + static: impossible.** A static member function has no
        `this` and is bound to the class; a virtual function needs an object
        for dynamic dispatch. Declaring both is ill-formed.
      - **Virtual + private: possible.** A private virtual can be overridden
        in derived classes but invoked only from the base's own member
        functions — the Non-Virtual Interface (NVI) idiom: public non-virtual
        wrapper, private virtual hook.

      **Use case:** NVI — `void draw() { pre(); do_draw(); post(); }` where
      `do_draw()` is a private virtual each derived class overrides.

      ### **Interview questions**

      :::tip
      **Interview question:** what does `auto` actually deduce? — The type of
      the initializer with **top-level const and references stripped**:
      `auto x = s;` copies, `auto& x = s;` binds a reference, `const auto& x =
      s;` is a read-only reference. In range-based for, `const auto&` is the
      default choice because `auto x` copies every element.
      :::

      :::tip
      **Interview question:** lambdas vs `std::function` — when does the
      overhead matter? — A lambda is a concrete closure type: direct calls are
      inlined and cost nothing. `std::function` type-erases (it can hold
      capturing lambdas and functors) but dispatches through an indirect call
      and heap-allocates captures. Use it only where the callable's type is a
      runtime value — callback registries, containers of handlers — never on a
      hot path where a template or lambda would do.
      :::

      :::tip
      **Interview question:** how do you avoid a data race in C++? — Ensure
      concurrent access to shared memory is synchronized: `std::mutex` +
      `std::lock_guard` (RAII — unlock guaranteed even on exceptions), or
      `std::atomic` for a single variable, or design so data is not shared at
      all (thread-local, message passing). A data race is **undefined
      behavior**, not merely a logic bug — it can corrupt the program in
      unpredictable ways.
      :::
