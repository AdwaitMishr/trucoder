      ### Copy constructor vs copy assignment

      - **Copy constructor** — builds a *new* object from an existing one; runs
        at *declaration/initialization*:
        ```cpp
        MyString b = a;   // copy ctor — b does not exist yet
        MyString c(a);    // copy ctor, direct form
        ```
      - **Copy assignment operator** — copies into an *already-existing* object;
        runs when you *assign*, not when you declare:
        ```cpp
        MyString b;       // default ctor
        b = a;            // copy assignment — b already exists
        ```
      - Both are auto-generated (member-wise) unless you declare them, and both
        take `const MyString&`:
        - `MyString(const MyString& other);`
        - `MyString& operator=(const MyString& other);` — returns `*this` for
          chaining, and must handle self-assignment (`a = a;`).
      - Passing by value / returning by value invoke the copy ctor (copy elision
        aside); passing by `const&` avoids copies entirely.

      **Use case:** `Student s2 = s1;` makes a fresh copy of a record; `s2 = s1;`
      overwrites an existing record — different operations, different functions.
  - type: markdown
    content: |
      ### Deep vs shallow copy

      - Default copies are **member-wise = shallow**: for a pointer member only
        the pointer *value* is copied — both objects point to the **same** heap
        block.
      - **Aliasing** — mutating through one object changes the other.
      - **Double free** — both destructors `delete` the same block → undefined
        behavior / heap corruption.
      - **Deep copy** — allocate a *new* block and copy the pointee contents;
        the objects become fully independent.
      - Plain value members (`int`, `double`, `char`) need no deep copy — only
        *owning* pointer / resource members do.

      **Use case:** a `StringBuffer` owning `char* data_` — a shallow copy shares
      the buffer between two objects; a deep copy gives each instance its own
      buffer.

    content: |
      ### Rule of Three & Rule of Five

      - If you wrote the **destructor**, you manage a resource — and the default
        copies will *shallow-copy* it. So if you need the destructor, the copy
        constructor, or the copy assignment, you almost certainly need **all
        three** — that is the **Rule of Three**.
      - C++11 adds **move constructor** and **move assignment** → the **Rule of
        Five**: destructor, copy ctor, copy assignment, move ctor, move
        assignment.
      - A **move** *transfers ownership* (steals the pointer) instead of
        deep-copying — cheaper, and leaves the source empty.
      - Modern advice: prefer smart pointers so the defaults are correct
        (Rule of Zero) — only write the five when you genuinely own a resource.
  - type: markdown
    content: |
      ### Stack vs heap, new/delete vs malloc/free

      - **Stack** — automatic lifetime: the object dies at scope exit; allocation
        is nearly free (a stack-pointer bump); size is small (typically ~1–8 MB);
        LIFO order.
      - **Heap** — manual lifetime: `new`/`delete`; allocation is slower (allocator
        bookkeeping); large; survives the creating scope.
      - `new` / `delete` — allocate **and run the constructor** / run the
        **destructor** and free.
      - `malloc` / `free` — raw bytes only: **no constructor or destructor runs**.
      - Arrays pair up as `new T[n]` with `delete[]`.

      **Use case:** objects that must outlive their scope (a buffer built in a
      factory and returned) live on the heap; short-lived locals live on the
      stack.
  - type: markdown
    content: |
      ### Memory leaks, dangling pointers, double free

      - **Memory leak** — allocated with `new`, never `delete`d (the pointer is
        lost), so the block is unreachable until the program exits.
      - **Dangling pointer** — points to memory already freed; dereferencing it
        is undefined behavior.
      - **Double free** — freeing the same block twice (the classic shallow-copy
        bug) — heap corruption, undefined behavior.
      - Avoid all three with **RAII**: bind the resource to an object's lifetime
        (constructor acquires, destructor releases) or use smart pointers.

      **Use case:** a `FileGuard` opens the file in its constructor and closes it
      in its destructor — no matter how the scope exits (even via an exception),
      the file is closed.
  - type: markdown
    content: |
      ### **Interview questions**

      :::tip
      **Interview question:** shallow copy — when does it bite you (double
      free)? — Whenever a class with a raw *owning* pointer is copied with the
      default member-wise copy: both objects end up pointing at one heap block.
      The first destructor frees it, the second frees it *again* → double free /
      UB, and writes through either object alias the other. Fix it with a deep
      copy (Rule of Three) or by owning the memory with a smart pointer.
      :::

      :::tip
      **Interview question:** rule of three vs rule of five — when do you need
      which? — Rule of Three (C++98): if you need a destructor, copy ctor, or
      copy assignment, you need all three — you own a resource and the defaults
      would shallow-copy it. Rule of Five (C++11): also provide the move
      constructor and move assignment so resources are *transferred* instead of
      deep-copied, which is faster and enables efficient return-by-value.
      :::

      - `b2 = b1;` on an existing object is **copy assignment**, not the copy
        constructor — the #1 off-by-one of copy semantics.
      - The copy assignment operator must release its old resource *before*
        copying the new one, and guard against `a = a;`.
