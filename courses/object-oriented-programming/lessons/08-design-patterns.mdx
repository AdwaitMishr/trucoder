      ### What patterns are — and why they exist

      - A **design pattern** is a *reusable, named solution* to a recurring
        design problem — not a library or a framework, but a **template for
        structure** you adapt to your code.
      - **Why they matter in interviews:** a shared vocabulary ("this is a
        factory", "that is an observer") communicates design intent in one
        word, and the patterns encode battle-tested answers to common
        coupling / flexibility problems.
      - **Pattern vs principle:** a *principle* (SOLID) is a general rule
        about *how* to design; a *pattern* is a concrete *recipe* that applies
        one or more principles (e.g. Factory applies OCP — open/closed).
  - type: markdown
    content: |
      ### SOLID — one line each

      - **S**ingle Responsibility — a class should have *one reason to change*.
      - **O**pen/Closed — open for *extension*, closed for *modification*
        (add behavior by adding code, not editing existing code).
      - **L**iskov Substitution — a derived class must be usable *anywhere its
        base is*, without breaking behavior (no surprise contracts).
      - **I**nterface Segregation — many small, specific interfaces beat one
        fat interface (clients should not depend on methods they do not use).
      - **D**ependency Inversion — depend on *abstractions*, not concretions
        (inject dependencies; the high-level module owns the interface).

      **Use case:** when an interviewer asks "is this design good?", the
      answer is usually a SOLID analysis — name the violated letter.

      ### Singleton — and why it is often an anti-pattern

      - **Idea:** exactly one instance, reachable through a static accessor;
        constructor is private.
      - **Classic thread-safe variants:**
        - mutex + `std::lock_guard` around creation (simple, correct);
        - **Meyers singleton** — `static Singleton& get() { static Singleton
          s; return s; }` — since C++11, function-local statics are
          initialized **exactly once and thread-safely** ("magic statics"),
          so this is the idiomatic C++ way.
      - **Why it is often called an anti-pattern:** it is **global mutable
        state** with *hidden dependencies* — any code can reach it, tests
        cannot substitute a mock, and initialization/destruction order across
        translation units is fragile. Prefer **dependency injection** of a
        single instance; reach for a real singleton only when the framework
        demands one instance (e.g. a logger, a config store).

      **Use case:** a `Logger::get()` Meyers singleton in a small tool — fine;
      a singleton `Database` threaded through business logic — a testability
      nightmare.

      ### Factory / Factory Method

      - **Idea:** *decouple creation from use*. The client asks a factory for
        an object and gets it through the **abstract interface** — it never
        names the concrete class.
      - **Classic example:** `Shape* createShape(const std::string& type)` —
        `"circle"` → `new Circle`, `"rectangle"` → `new Rectangle`, returned
        as `Shape*`; adding a shape means *extending* the factory, not
        rewriting callers (**Open/Closed**).
      - **Factory Method** — the creation step is a *virtual function* in a
        base class, overridden by derived classes to decide the concrete type.
      - **When to use:** the client should not depend on concrete classes —
        libraries, plugins, and anywhere the type is chosen at runtime.

      **Use case:** a game loads enemies by name from a level file; a UI
      toolkit builds widgets from a type string.

      ### Observer — publish / subscribe

      - **Idea:** a **subject** keeps a list of **observers**; when its state
        changes it calls `update()` on every registered observer — the subject
        knows *nothing* about the observers' concrete types (loose coupling).
      - Used in **event systems, MVC (model notifies views), GUIs, pub/sub
        buses**.
      - **Gotchas:** observers must **unsubscribe before destruction** or the
        subject notifies a dangling object (use-after-free); notification
        *order* is not guaranteed; avoid notifying while holding a lock.

      **Use case:** a `WeatherStation` (subject) notifies `Dashboard`,
      `Logger`, and `AlertSystem` (observers) whenever readings change.

      ### Strategy

      - **Idea:** encapsulate a family of algorithms behind one interface and
        make them **swappable at runtime** — the client picks the strategy, the
        class does not hard-code the choice.
      - **Classic example:** `std::sort(v.begin(), v.end(), comparator)` —
        the comparator *is* a strategy: sorting order changes without touching
        the container or the sort call.
      - **Strategy vs switch:** a switch hard-codes the variants into the
        client (edit + retest on every addition); Strategy makes each variant
        a class you can add **without modifying existing code** (Open/Closed)
        and swap at runtime.

      **Use case:** a `PaymentProcessor` delegates to `CreditCardStrategy` /
        `PayPalStrategy`; a `TextFormatter` delegates to `JSONFormatter` /
        `XMLFormatter`.
  - type: markdown
    content: |
      ### Three more — one line each

      - **Builder** — construct a complex object *step by step*, separating
        construction from representation (fluent `setX().setY().build()`).
      - **Decorator** — *wrap* an object to add responsibilities dynamically
        (e.g. a `BufferedStream` wrapping a raw stream, logging wrappers).
      - **Adapter** — convert one interface into another so incompatible
        classes can cooperate (e.g. wrapping a legacy `OldApi` behind a modern
        interface).
  - type: markdown
    content: |
      ### **Interview questions**

      :::tip
      **Interview question:** is Singleton an anti-pattern? — It is a pattern
      that is *often* an anti-pattern: it introduces **global mutable state**
      with hidden dependencies, makes testing hard (no way to substitute a
      mock), and has fragile lifetime/order-of-initialization issues. If you
      truly need one instance, prefer **dependency injection** of a single
      instance; if you do use a singleton in C++, the **Meyers** form
      (function-local static) is the thread-safe choice since C++11.
      :::

      :::tip
      **Interview question:** when would you pick Strategy over a switch? —
      When the algorithm varies *at runtime* or you expect new variants: each
      strategy is a class you add without editing the client (Open/Closed),
      and the client swaps behavior by swapping objects (like a comparator
      passed to `std::sort`). A switch hard-codes the choice into the client —
      every new case means editing and retesting the same function.
      :::

      :::tip
      **Interview question:** factory vs direct `new` — why bother? — `new
      Circle` in the client couples it to a concrete class. A factory gives
      the client the **abstract interface** and centralizes creation: adding a
      type extends the factory, callers never change, and tests can substitute
      fake objects behind the same interface.
      :::
