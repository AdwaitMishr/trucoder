      # Scaling Fundamentals

      The first question in every design interview: **how does this thing
      grow?** Everything else — CAP, caches, queues, sharding — exists to
      answer that question.

      ## Vertical vs horizontal scaling

      | | Vertical (scale up) | Horizontal (scale out) |
      |---|---|---|
      | What | One bigger machine: more CPU / RAM / disk | More machines behind a load balancer |
      | Ceiling | Hits hardware limits, expensive | Effectively unlimited, commodity hardware |
      | Failure | Single point of failure | N−1 machines can fail and the service survives |
      | State | Easy — one machine holds it | Hard — sessions, locks, and data must be shared |
      | When | Stateful services, DB writes, small scale | Stateless app tiers, reads, web farms |

      **Use case:** an API tier grows from 1k to 100k QPS — you scale *out*
      the stateless app servers (more replicas) and scale *up* the database
      (bigger node), then shard it when one node is not enough.

      ## CAP theorem

      A distributed system under a **network partition** must choose between
      **C** (Consistency — every read sees the latest write) and **A**
      (Availability — every request gets a non-error response). Partitions
      (P) are a fact of real networks, so "pick two" really means: *when the
      network splits, do you serve stale data or refuse to serve?*

      - **CP — banking, inventory, payments:** refuse rather than serve a
        wrong balance. A transfer must never double-spend.
      - **AP — social feed, likes, shopping cart:** serve the best-known
        state and reconcile later. A like count may be briefly stale.

      ## ACID vs BASE

      - **ACID** (SQL): Atomicity, Consistency, Isolation, Durability —
        strong guarantees; writes are the bottleneck.
      - **BASE** (NoSQL): Basically Available, Soft state, Eventually
        consistent — availability and scale over strict correctness.

      ## Latency vs throughput

      - **Latency** — time for one request (ms). Watch the **tail**: **p99**
        is the 99th percentile, "1 in 100 users waits this long". A 100 ms
        average can hide a 2 s p99 that users actually feel.
      - **Throughput** — requests per second completed. Latency caps it: one
        thread doing 100 ms requests can do at most 10 QPS.

      ## The estimation toolkit (the meat of the interview)

      Every number below is a one-line multiplication. Round aggressively —
      interviewers want the *method*, not precision.

      **QPS.** `QPS = DAU × actions per user per day ÷ 86,400`.

      ```
      1M DAU × 10 actions/day = 10M actions/day
      10M ÷ 86,400 ≈ 115.7  →  ~116 QPS average
      peak = 3–5 × average  →  ~350–580 QPS
      ```

      **Storage per day.** `records/day × bytes per record`.

      ```
      100M new URLs/day × 100 B = 10^10 B = 10 GB/day  (≈ 3.6 TB/yr)
      500M tweets/day × 1 KB     = 5 × 10^11 B = 500 GB/day
      ```

      **Cache: the 80/20 rule.** ~20% of objects serve ~80% of reads. Cache
      the hot 20% and the database read load drops ~5×.

      **Servers.** `#servers = peak QPS ÷ per-server capacity`.

      ```
      5,000 QPS ÷ 1,000 QPS/server = 5 app servers
      ```
      A single DB node handles only ~1–5k QPS — that is why reads go to
      cache/replicas before they reach the DB.

      **Bandwidth.** `bandwidth = QPS × payload size`.

      ```
      100 QPS × 100 KB = 10,000 KB/s = 10 MB/s  (≈ 864 GB/day, ≈ 26 TB/month)
      ```

      **Availability.** `downtime/yr = (1 − uptime) × 8,760 h`.

      ```
      99.9%  → 0.001 × 8,760 = 8.76 h/yr
      99.99% → 0.0001 × 8,760 = 0.876 h = 52.6 min/yr
      ```

      **Latency numbers (Jeff Dean).** L1 cache **1 ns**, RAM **100 ns**,
      SSD **100 µs**, disk seek **10 ms**, network RTT **100 ms** — five
      orders of magnitude from RAM to a disk seek. This is *why* we cache.

      :::tip
      **Interview question:** Explain CAP with a real system. — "Under a
      network partition a distributed DB must pick CP or AP. Banking is CP:
      a read that cannot see the latest balance returns an error rather than
      a stale balance. A social feed is AP: likes may be briefly stale, but
      the feed must always load."
      :::

      :::tip
      **Interview question:** How do you estimate QPS for a new product? —
      "Start from DAU and user behaviour: QPS = DAU × actions/day ÷ 86,400.
      For 1M DAU doing 10 actions/day that is ~116 QPS average and ~350–580
      QPS peak. Then size storage the same way: records/day × bytes per
      record. Round to one significant figure and show the arithmetic."
      :::
