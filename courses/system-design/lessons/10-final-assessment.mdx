      # Final Assessment — System Design

      **Exam instructions.**
      - 24 questions covering all nine lessons: 21 single-choice (MCQ) + 3 multi-select (MSQ, select **all** correct options).
      - No negative marking. Every numerical question shows full working in the explanation — read it even if you got the answer right.
      - Suggested pace: ~45 minutes (about 2 minutes per question). Answer from first principles; when stuck, recall the lesson's worked example.
      - Tip: for estimation questions, write the formula first (`QPS = DAU × actions ÷ 86,400`, `storage = records × bytes`, `downtime = (1 − uptime) × 8,760 h`) — the arithmetic is then trivial.

      Good luck!
  - type: mcq
    prompt: "For a banking transaction system, which CAP combination is the standard choice?"
    options: ["AP — availability over consistency", "CP — consistency + partition tolerance", "CA — consistency + availability", "None — banking is single-node only"]
    answer: 1
    explanation: "Partition tolerance is non-negotiable in a distributed system (networks fail), so the real choice is C vs A. Banks pick consistency: during a partition they return an error rather than a stale balance → CP. Social feeds are the AP counterpart."
  - type: mcq
    prompt: "An app has 10M DAU and each user performs 20 actions/day. What is the average QPS?"
    options: ["~230", "~2,300", "~23,000", "~864"]
    answer: 1
    explanation: "Total actions = 10M × 20 = 200M/day. QPS = 200,000,000 ÷ 86,400 s/day ≈ 2,315 ≈ ~2,300 average. Peak is 3–5× this."
  - type: mcq
    prompt: "2M users upload 10 photos/day at 200 KB each. Daily storage growth?"
    options: ["40 GB", "400 GB", "4 TB", "40 TB"]
    answer: 2
    explanation: "records/day × bytes = 2M × 10 × 200 KB = 20M × 200 KB = 4,000,000,000 KB = 4 × 10^9 KB = 4 TB/day (1 TB = 10^9 KB)."
  - type: mcq
    prompt: "A service has 100M posts; 80% of traffic hits the same 20% of them. Caching the hot set at ~1 KB per entry needs about…"
    options: ["20 GB", "80 GB", "100 GB", "200 GB"]
    answer: 0
    explanation: "80/20 rule: hot set = 20% of 100M = 20M entries. 20M × 1 KB = 20 GB — and this one cache serves ~80% of reads, cutting DB load ~5×."
  - type: mcq
    prompt: "Peak load is 50k QPS and one app server handles 10k QPS. How many servers do you need?"
    options: ["5", "50", "500", "10"]
    answer: 0
    explanation: "#servers = peak QPS ÷ per-server capacity = 50,000 ÷ 10,000 = 5. In practice add headroom (e.g. ×2 for failover/rollout)."
  - type: mcq
    prompt: "99.99% availability means roughly how much downtime per year?"
    options: ["~5 minutes", "~52 minutes", "~8.76 hours", "~3.65 days"]
    answer: 1
    explanation: "downtime = (1 − 0.9999) × 8,760 h = 0.0001 × 8,760 = 0.876 h = 52.56 ≈ 52 minutes. (8.76 h is 99.9% — three nines.)"
  - type: mcq
    prompt: "An L7 load balancer routes traffic based on…"
    options: ["TCP port only", "HTTP path, host, and headers", "MAC address", "IP + port, nothing else"]
    answer: 1
    explanation: "L7 inspects the application layer (HTTP path, Host header, cookies) — enabling path-based routing and TLS termination. L4 only sees IP + port (transport layer)."
  - type: mcq
    prompt: "On a cache-aside READ MISS, what happens?"
    options: ["Return a stale cached value", "Query the DB, populate the cache, return the value", "Write cache and DB together", "Return 404 and never cache"]
    answer: 1
    explanation: "Cache-aside: miss → query DB → write value into cache → return. Write-through instead writes cache + DB together on every write (always fresh, but write latency + cold data in cache)."
  - type: mcq
    prompt: "With a PULL CDN, content reaches the edge when…"
    options: ["The first client in that region requests it (edge fetches from origin, caches with TTL)", "An operator uploads it to the edges in advance", "It is written to the origin database", "A client opens a WebSocket to the origin"]
    answer: 0
    explanation: "Pull = edge fetches from origin on first request and serves cached copies until the TTL expires — automatic, the default. Uploading in advance is a PUSH CDN (Netflix-style)."
  - type: mscq
    prompt: "Which statements about consistent hashing are true?"
    options: ["Adding a node only remaps keys in its neighbourhood (~1/N of keys, not all)", "Keys and nodes are placed on a hash ring; a key belongs to the first node clockwise", "Virtual nodes give one physical node several ring positions for an even spread", "Every key must be rehashed when a node joins"]
    answer: [0, 1, 2]
    explanation: "Consistent hashing exists to avoid the plain mod-N problem where adding a node rehashes every key. Only neighbouring keys move; virtual nodes balance load when machines are few. Option 3 describes naive sharding, not consistent hashing."
  - type: mcq
    prompt: "Token bucket: capacity 2, refill 1/s. Requests arrive at t = 0, 0, 0, 1. Which are allowed?"
    options: ["All four", "Three — the third request (also t=0) is denied", "Only the first two", "None"]
    answer: 1
    explanation: "t=0: bucket has 2 → allow → 1 left; t=0: no refill (same second) → 1 → allow → 0; t=0: 0 tokens → deny; t=1: refill +1 → 1 → allow → 0. Result: allow, allow, deny, allow."
  - type: mscq
    prompt: "Which statements about Kafka vs SQS are true?"
    options: ["Kafka guarantees ordering per partition", "Kafka consumers can replay messages from retention", "SQS standard queues guarantee global ordering by default", "Kafka's default delivery is at-least-once — consumers should dedup"]
    answer: [0, 1, 3]
    explanation: "Kafka is a partitioned log: per-partition ordering + replay from retention, with at-least-once by default (exactly-once is opt-in). SQS standard does NOT guarantee ordering — that is the classic trade-off."
  - type: mcq
    prompt: "base62 (alphabet 0-9, a-z, A-Z): what is the decimal number 62 encoded as?"
    options: ["\"62\"", "\"10\"", "\"a0\"", "\"zz\""]
    answer: 1
    explanation: "62 = 1 × 62^1 + 0 × 62^0 → digits [1, 0] → alphabet[1] = '1', alphabet[0] = '0' → \"10\"."
  - type: mcq
    prompt: "A URL shortener that needs click analytics should redirect with…"
    options: ["301 — browsers cache it, best performance", "302 — every click hits the service and gets counted", "301 — repeat clicks reach the server", "200 — render the page inline"]
    answer: 1
    explanation: "301 is cached by browsers, so repeat clicks never reach your server — great for SEO/perf, but clicks are invisible. 302 (temporary) makes every click hit the shortener, so it can count and log before redirecting."
  - type: mcq
    prompt: "Why is WebSocket the right transport for a chat app?"

    answer: 1
    explanation: "Polling every 2 s adds latency and waste; a WebSocket keeps one full-duplex connection open so the server pushes instantly. Ordering is then handled per conversation — Kafka partition key = conversation_id plus per-conversation sequence numbers."
  - type: mcq
    prompt: "In a hybrid news feed, a celebrity with 10M followers should be handled how?"
    options: ["Push-fanned to all 10M followers at post time", "Pull-based: appended to their own feed, merged at read time", "Replicated to one read replica per follower", "Excluded from timelines entirely"]
    answer: 1
    explanation: "Push would mean 10M timeline writes per post — the hot-user problem. Hybrid: push for normal users, pull for celebrities; timelines are merged at read time and capped (~800 IDs) in Redis."
  - type: mcq
    prompt: "What is the purpose of a dead-letter queue (DLQ) in a notification pipeline?"
    options: ["To speed up normal delivery", "To park messages that exhausted retries so they can be inspected and replayed", "To replace the primary Kafka topic", "To dedupe identical notifications"]
    answer: 1
    explanation: "After N failed attempts (exponential backoff), a message moves to the DLQ — alerted on, inspected, manually replayed. It guarantees nothing is silently dropped."
  - type: mcq

      ## Revision tips before the interview

      - **Estimation is free marks.** Memorize the four formulas and always show the arithmetic: `QPS = DAU × actions ÷ 86,400`, `storage = records/day × bytes`, `#servers = peak QPS ÷ capacity`, `downtime = (1 − uptime) × 8,760 h`. Round to one significant figure.
      - **The canonical answer shape:** clarify requirements → back-of-envelope estimates → APIs → data model → scale → tradeoffs. Every design lesson in this course follows it — rehearse that skeleton, then slot the specifics in.
      - **Diagrams you should be able to draw blind:** CAP triangle, cache-aside read flow, producer → Kafka → consumers, redirect flow (LB → app → Redis → DB → 301/302), WebSocket send→deliver, push vs pull fanout, notification pipeline with DLQ, DASH segments, ride-matching geohash query.
      - **One-liners to have ready:** banking = CP; chat = WebSockets + Kafka per-conversation + Redis presence; newsfeed = hybrid fanout; notifications = queue + workers + DLQ + idempotency keys; video = CDN + DASH; rides = geohash + heartbeats; RAG = retrieve-then-generate.
      - **LLD quick recall:** SOLID one-liners (S = one reason to change, O = extend don't modify, L = subclass keeps the contract, I = small interfaces, D = depend on abstractions) and Strategy/Factory/Observer/State for pattern questions.
      - **Final tip:** if you can re-derive every worked numerical in this exam in under a minute, estimation questions in the real interview become the easiest part of the room. You've got this.
