      # Async & Scaling Tools

      Three tools make a system scale past one machine: **queues** (decouple
      work), **consistent hashing** (place data), and **rate limiters**
      (protect the system). Then you implement the core of a rate limiter.

      ## Message queues — why async

      Synchronous calls chain failures and force the slowest step onto every
      request. A queue breaks the chain: the producer drops a message and
      moves on; workers consume at their own pace.

      - **Decoupling** — the producer does not know the consumers (and vice
        versa); add consumers without touching producers.
      - **Buffering** — bursts are absorbed; workers catch up slowly.
      - **Retries / DLQ** — failed messages are retried, then moved to a
        dead-letter queue for inspection.

      | | Kafka | SQS | RabbitMQ |
      |---|---|---|---|
      | Throughput | very high (100k+/s) | high (managed) | moderate |
      | Ordering | per partition | not by default | per queue |
      | Replay | yes (retention) | no | no |
      | Model | log / stream | queue | queue + exchanges |
      | Ops | self-hosted, complex | zero ops (AWS) | self-hosted, flexible routing |

      **Delivery guarantees:** at-least-once (messages may duplicate → make
      consumers **idempotent**) vs exactly-once (dedup by message ID).
      Most systems ship at-least-once + idempotent consumers; exactly-once
      costs throughput and complexity.

      **Use case:** an order service emits `order_created` once; email,
      search index, and analytics each consume it independently — one write
      fans out to many systems.

      ## Consistent hashing

      Naive sharding — `server = hash(key) % N` — rehashes **every** key when
      a node joins or leaves. **Consistent hashing** puts nodes on a hash
      ring: `hash(key)` lands somewhere on the ring, and you walk **clockwise**
      to the first node — that node owns the key.

      - Adding/removing a node only rehashes its **neighbours'** keys
        (~1/N of keys instead of all of them).
      - **Virtual nodes:** each physical node occupies several ring
        positions, so keys spread evenly even with few machines.
      - Used by DynamoDB, Cassandra, and every cache cluster (Redis Cluster).

      ## Sharding & replication

      Shard by a **partition key** (e.g. `user_id`) so one user's data lives
      together. The key choice matters: sharding by `timestamp` makes one
      shard hot (a **hotspot**); sharding by `user_id` spreads writes evenly.
      Each shard runs **leader/follower**: writes go to the leader, **read
      replicas** serve reads, and a **quorum** (majority of nodes ack) trades
      latency for durability.

      **Use case:** a 100M-row user table — shard by `user_id`; each shard
      has a leader + 2 replicas; writes hit the leader, reads hit replicas.

      ## Rate limiting

      A rate limiter answers: *may this request pass?* — per user, per IP, or
      per API key.

      - **Token bucket:** bucket holds `capacity` tokens, refilled at
        `refill_per_sec`. Each request needs 1 token. Allows bursts up to
        capacity, smooth long-run rate. Simple and memory-light — the
        default.
      - **Sliding window:** count requests in the last window (log or
        counter) — precise, but needs timestamps (memory) or a per-window
        Redis counter (small boundary error).
      - **Distributed:** a shared **Redis** keeps one bucket per key with
        atomic check-and-consume (Lua script), so N servers agree.
      - **Over limit:** respond **429 Too Many Requests** with
        `Retry-After`.

      **Use case:** an API allows 100 req/min per user — the Redis token
      bucket lets 100 burst, then 100/min forever, across all app servers.

      - "Track two things: the current token count and the previous timestamp. The bucket starts full."
      - "Between two timestamps add (t - last) * refill_per_sec tokens, then cap the count at capacity."
      - "Consume exactly 1 token when you allow a request; deny (no consumption) when tokens < 1."
    solution: |
      def solve(timestamps: list[int], capacity: int, refill_per_sec: int) -> list[bool]:
          tokens = capacity
          last = None
          out = []
          for t in timestamps:
              if last is not None:
                  tokens = min(capacity, tokens + (t - last) * refill_per_sec)
              last = t
              if tokens >= 1:
                  out.append(True)
                  tokens -= 1
              else:
                  out.append(False)
          return out
