      # Low-Level Design: SOLID, Patterns, Parking Lot

      **Concept.** HLD is boxes and arrows; LLD is classes and methods. Interviewers test whether you can turn a requirement into clean, extensible code — that is SOLID + the right design pattern.

      ## SOLID — each letter as a smell + fix

      - **S — Single Responsibility:** smell = a god class that validates, persists, and renders. Fix: one class, one reason to change — split into Validator, Repository, Presenter.
      - **O — Open/Closed:** smell = `if (type == CAR) ... else if (type == TRUCK)` inside ParkingLot. Fix: open for extension, closed for modification — add a `Vehicle` subclass instead of editing ParkingLot.
      - **L — Liskov Substitution:** smell = Square extends Rectangle but overrides `setWidth` to break `setHeight` (square-rectangle problem). Fix: a subclass must be usable anywhere its base is — model Square as its own shape.
      - **I — Interface Segregation:** smell = one fat interface with methods most implementers don't use (a `Worker` interface forcing `fly()`). Fix: small, focused interfaces.
      - **D — Dependency Inversion:** smell = ParkingLot constructs `new Car()` internally. Fix: depend on the `Vehicle` abstraction, inject concrete types.

      :::tip
      **Interview question:** "Which SOLID principle does this violate?" — A class that does validation + DB access + rendering is an SRP violation (god class). A method that grows a new `if` branch for every vehicle type violates OCP. A subclass that breaks base-class behavior (Square/Rectangle) violates LSP. One interface with methods nobody implements violates ISP. Constructing concretes instead of depending on abstractions violates DIP. Name the smell, then name the principle.
      :::

      ## Pattern selection quick guide

      - **Strategy** — interchangeable algorithms: payment methods (UPI/Card/COD), compression, sorting.
      - **Factory** — object creation with logic: create `Vehicle` by type string, `Parser` by file extension.
      - **Observer** — pub-sub: notification subscribers, UI refreshing on data change.
      - **State** — behavior changes with internal state: vending machine, order lifecycle.
      - **Decorator** — layered behavior: pricing with add-ons, logging wrappers.
      - **Singleton** — logger/config used to be the answer; now it is an anti-pattern (hidden global state, untestable). Prefer dependency injection.

      ## Classic walkthrough: Parking Lot

      - `Vehicle` (abstract): `getSize()` → `Car`, `Bike`, `Truck` (LSP: all honor the contract).
      - `ParkingSpot`: size, `isFree`, `park(vehicle)` / `leave()`.
      - `ParkingLevel` → list of spots; `findSpot(size)`.
      - `ParkingLot` → levels; `park(vehicle)` → `Ticket`; `leave(ticket)` → fee.
      - `Ticket`: id, spotId, entryTime. Fee = `hours × rate`, rounded up.
      - Edge cases: lot full → reject; wrong size spot → reject; lost ticket → charge max day rate.

      **Use case:** parking lot is *the* service-company machine-coding prompt
      (TCS/Wipro/Infosys) — 45–60 minutes of pure OOP; snake & ladder is the
      startup favorite that pairs LLD with a BFS coding problem.

      :::tip
      **Interview question:** "Walk me through designing a parking lot." — Clarify: multiple levels, vehicle sizes, hourly fee, tickets. Define Vehicle (abstract) + Car/Bike/Truck; ParkingSpot with size and free flag; ParkingLevel finds a spot; ParkingLot orchestrates park/leave and returns a Ticket with entry time; fee = ceil(hours) × rate. Call out OCP (new vehicle types = new subclasses, ParkingLot unchanged), DIP (ParkingLot depends on Vehicle, not Car), and the edge cases (full lot, wrong size, lost ticket).
      :::

      ## Other classic LLD problems (one-line designs)

      Service-company machine-coding rounds rotate through a small set — know
      the core entities of each:

      - **Library management** — `Book` (title/author), `BookCopy` (unique
        barcode), `Member`, `Librarian`, `Loan` (copy → member, due date,
        fine = overdueDays × rate), `SearchCatalog` (by title/author/ISBN).
      - **ATM** — state machine: `cardInserted → pinValidated → transaction`;
        entities `ATM`, `Card`, `Account`, `Transaction` (Withdraw/Deposit/
        Transfer), `CashDispenser`; edge cases: insufficient funds, wrong PIN
        (max 3 tries), no cash.
      - **Elevator** — `Elevator` (state: idle/moving/doorsOpen), `Request`
        (floor, direction), `ElevatorController` schedules stops — FCFS is
        naive, **SCAN/elevator** moves one direction then the other.
      - **Vending machine** — the **State pattern** in action: `Idle →
        HasMoney → Dispensing`; entities `Machine`, `Item`, `Inventory`,
        `Coin`; edge cases: exact change, sold out, refund.

      :::tip
      **Interview question:** "Which pattern fits a vending machine?" —
      State: the machine's behavior (accept money, dispense, refund) depends
      entirely on its current state (Idle/HasMoney/Dispensing). Implement
      each state as a class so adding a state never touches the others (OCP).
      :::

      ## Code exercise: Snake & Ladder — minimum dice throws

      Classic BFS problem and a favorite interview warm-up. The board is a list where `board[i] = -1` means a normal square, and any other value is the destination you **must** teleport to when you land on `i` (snakes go down, ladders go up). Start at index 0, goal is the last index, die is 1..6.

      **Worked example.** `board = [-1, -1, 4, -1, -1, -1, -1, -1]` (8 squares). One throw can't reach index 7 (max die 6). In two: roll 2 → land on 2 → teleport to 4, then roll 3 → 7. Also roll 6 → 6, then roll 1 → 7. Minimum = **2**.

      **Why BFS?** Each square is a node; each die roll is an edge to `i+1..i+6` (then follow any teleport). BFS from 0 explores in order of throw-count, so the first time the goal is popped, the distance is the minimum.

    hints:
      - "Model the board as a graph: each square is a node; a die roll is an edge to i+1..i+6, then follow any teleport."
      - "BFS from index 0 gives the minimum number of throws — the first time you pop the goal, return its distance."
      - "Landing on a teleport square is mandatory: the square you actually occupy is board[j], not j. Watch for teleports that land on already-visited squares."
    solution: |
      from collections import deque

      def solve(board: list[int]) -> int:
          n = len(board)
          goal = n - 1
          dist = [-1] * n
          dist[0] = 0
          q = deque([0])
          while q:
              i = q.popleft()
              if i == goal:
                  return dist[i]
              for die in range(1, 7):
                  j = i + die
                  if j >= n:
                      break
                  if board[j] != -1:
                      j = board[j]
                  if dist[j] == -1:
                      dist[j] = dist[i] + 1
                      q.append(j)
          return -1
