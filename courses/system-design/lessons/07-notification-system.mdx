      # Design: Notification System (Meta / Uber / Swiggy)

      **Concept.** One event must reach a user across many channels (push, email, SMS) reliably, within seconds, without spamming. The design is: **API → queue → workers → provider gateways**, with retries and dedup bolted on.

      **Requirements (clarify first).**
      - Multi-channel: iOS push (APNs), Android push (FCM), email, SMS.
      - Scale: ~10M notifications/day, delivered within seconds.
      - A user may have many devices (fanout to a device-token list).
      - Users can opt out per channel; providers have rate limits.

      **Key points.**
      - Notification service (API) validates + dedups → Kafka → fanout workers → provider gateways.
      - Workers batch by provider (APNs/FCM accept batches; email/SMS via 3rd-party APIs).
      - Retries with exponential backoff (1s → 2s → 4s → 8s), then **dead-letter queue (DLQ)**.
      - Dedup: idempotency key per event, so retries don't double-send.
      - Templates + preference filter (opt-out, quiet hours) before enqueue.
      - Observability: delivery rate, click rate, provider error rates.

      **Use case:** "Design a system that delivers 10M push/email/SMS notifications a day."

      **Estimate (back of the envelope).**
      - 10M / 86,400 ≈ **116 notifications/sec avg**; campaign peaks ~10× → **~1,160/sec**.
      - Worker capacity ~100 sends/sec each → 1,160 / 100 ≈ **12 workers** at peak.

  - type: markdown
    content: |
      **Why Kafka in the middle.** The API never talks to providers directly: Kafka buffers bursts (campaigns), lets workers retry independently, and gives replay for audits. Trade-off vs SQS: Kafka keeps per-partition ordering and replay; SQS is simpler but unordered.

      **Retries + DLQ.** A provider can fail (rate-limited, APNs down, invalid token). Workers retry with backoff and jitter; after N attempts the message moves to the DLQ — parked, alerted, manually inspected and replayed. Nothing is silently dropped.

      **Dedup.** At-least-once delivery means duplicates happen. Each event carries an **idempotency key** (e.g. `userId:eventType:refId`); the service checks it before enqueueing and workers dedup on send, so retries are safe.

      :::tip
      **Interview question:** "How do you guarantee a notification is delivered at least once?" — Persist the event in Kafka; the worker acks the message only after the provider accepts the send; on failure it retries with exponential backoff and jitter, then DLQ. At-least-once means duplicates are possible, so every event gets an idempotency key and sends are deduped.
      :::

      :::tip
      **Interview question:** "How would you stop a notification storm?" — Rate-limit per user and per event type (token bucket), cap sends per campaign, enforce preference/opt-out filters before enqueue, add a circuit breaker per provider (back off when APNs/FCM start failing), and alert on DLQ growth. Batching also smooths load.
      :::

    content: |
      **Fanout to many devices.** One user → many devices: a `device_tokens` table (userId → tokens). A notification fans out to all tokens of the user, batched per provider. Deleting invalid tokens (APNs feedback) keeps the table clean.

      **Templates + preferences.** Store message templates server-side (push: title + body + deep link; email: HTML). The preference filter drops channels the user opted out of and respects quiet hours — applied **before** enqueue to save provider quota.

      **Observability.** Track per channel: sent, delivered, clicked, failed; provider latency percentiles; DLQ size. Click rate is the product metric that matters.

      **Worked numerical — capacity.** Peak 1,160 notifications/sec ÷ 100 sends/sec per worker ≈ 12 workers (round up; add headroom for retries). Retry math: waits 1 + 2 + 4 = **7 s cumulative** across 3 retries; with jitter to avoid a thundering herd at t+7s.
