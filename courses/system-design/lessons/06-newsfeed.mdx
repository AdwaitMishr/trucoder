      # Design: News Feed (Twitter / Instagram)

      **Concept.** A news feed shows a user the latest posts from everyone they follow. The hard part is not storing posts — it is **fanout**: getting each post onto every follower's timeline quickly and cheaply.

      **Requirements (clarify first).**
      - Follow graph: users follow others; the home timeline = posts from followed users, newest first.
      - Scale: ~200M DAU, read-heavy **10:1** reads to writes.
      - Latency: timeline loads in < 200 ms; a new post reaches followers within seconds.
      - Media (images/video) is served separately from text.

      **Key points.**
      - Three fanout strategies: push, pull, hybrid (below).
      - Timeline cache in Redis: one list per user, capped at ~800 post IDs.
      - Ranking: time-based (simple) or `score = recency × affinity`.
      - Shard by `user_id`; media on S3 + CDN.
      - Idempotency: dedup on post ID so retries never double-insert.

      **Use case:** "Design Twitter's home timeline for 200M DAU."

      **Estimate (back of the envelope).**
      - 200M DAU × 10 actions/day = 2B actions/day → 2B / 86,400 ≈ **23k actions/sec avg**.
      - At 10:1 read:write → ~**2.1k writes/sec** and ~**21k reads/sec**; peak 3–5×.
      - Timeline cache: 200M users × 800 post-IDs × ~8 B ≈ **1.28 TB** — easily held by a sharded Redis cluster (IDs only, never media content).

      :::tip
      **Interview question:** "Push vs pull fanout — which and why?" — Push (fanout-on-write) copies the post into every follower's timeline at publish time: reads become O(1) list lookups, but a celebrity with 10M followers triggers 10M writes per post. Pull (fanout-on-read) stores the post once and merges timelines at read time: cheap writes, slow reads over big follow graphs. Production systems use **hybrid**: push for normal users, pull for celebrities.
      :::

      :::tip
      **Interview question:** "How would you design the timeline for a user with 10M followers?" — Never push a celebrity's post into 10M Redis lists. Keep the celebrity's posts in their own feed; at read time merge that feed (pull) with the pushed timelines of normal follows, rank, and cap at 800. This bounds write amplification while reads stay fast.
      :::

      **Hybrid fanout (what Twitter actually does).** Classify at post time:
      - Normal user (followers ≤ threshold, e.g. 100k): **push** — a fanout worker writes the post ID into each follower's timeline list.
      - Celebrity (millions of followers): **pull** — append to the celebrity's own feed only; followers merge it in at read time.
      - Fanout is async: publish → queue → fanout workers fill timelines, so the author's POST returns immediately.

      **Ranking, media, sharding, idempotency.**
      - Ranking: `score = recency × affinity`, where affinity = how often you interact with that author. One line, and it beats pure time order for engagement.
      - Media: upload to S3, serve via CDN; the timeline stores only post IDs + metadata, keeping the cache small.
      - Sharding: timelines by `user_id`; posts by `author_id` (a user's own posts live together).
      - Idempotency: fanout workers can retry — dedup on post ID (Redis `SETNX` or a unique index) so a retried delivery never shows the post twice.

      **Worked numerical — write amplification.** A normal post to 200 followers = 200 timeline writes. A celebrity post to 10M followers would be 10M writes. At ~2.1k posts/sec average, if even 1% were celebrity posts: 2.1k × 0.01 × 10M ≈ **210M writes/sec** — impossible. Hence pull for celebrities: 1 write + a few thousand merges per read instead.
