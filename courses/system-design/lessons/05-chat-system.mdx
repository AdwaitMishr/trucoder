      # Design: Chat System (WhatsApp-style)

      The real-time design question. Same six-step shape — requirements →
      estimates → APIs/data → scale → tradeoffs — plus one new axis: **how do
      servers push messages to clients?**

      ## 1. Requirements

      - **Functional:** 1:1 and group chat, delivery receipts (✓✓), last
        seen, typing indicators, offline delivery.
      - **Scale:** 100M+ users × ~10 messages/user/day = 1B messages/day.

      ```
      1B ÷ 86,400 s/day ≈ 11,574 ≈ ~11.6k messages/s average
      peak: 3–5× → ~35–58k messages/s
      ```

      ## 2. Transport: polling vs long-polling vs WebSockets

      | | Polling | Long-polling | WebSocket |
      |---|---|---|---|
      | How | GET /updates every 2 s | hold the request until a message arrives | persistent full-duplex TCP |
      | Latency | up to 2 s | ~instant | instant |
      | Cost | wasteful, mostly empty responses | fewer requests, still HTTP per message | one connection, both directions |
      | Use | non-critical status | legacy chat | chat, live games, dashboards |

      **Chat ⇒ WebSockets:** one persistent connection; the server pushes the
      moment a message arrives, with no per-message HTTP overhead.

      ## 3. Connections & presence

      Chat servers hold WebSocket connections but **no chat state** — the
      mapping `user → which WS server` lives in **Redis**:

      - **Connect:** register `user_id → ws_server_id` in Redis (TTL +
        heartbeat).
      - **Reconnect:** the client can hit *any* server (they are stateless),
        which re-registers the mapping.
      - **Deliver:** the chat service looks up the receiver's server in
        Redis and pushes over that server's socket.

      ## 4. Message flow (the happy path)

      ```
      sender → chat service (via WebSocket)
        → Kafka topic, partition = conversation_id   (per-conversation ordering)
        → consumer workers
        → receiver's WS server (from Redis presence) → receiver
        → receiver offline? → push notification (APNs / FCM)
      ```

      **Ordering:** Kafka gives ordering *per partition* — use
      `conversation_id` as the partition key so all messages of one chat land
      in one partition and are consumed in order. The sender also stamps a
      **sequence number per conversation**, so clients sort correctly and
      detect gaps even across reconnects. This is why you cannot just dump
      everything into one global queue: ordering is per-conversation, not
      global.

      **Use case:** WhatsApp-style 1:1 + group chat at 100M users — WS for
      transport, Kafka per-conversation for ordering, Redis for presence,
      Cassandra for the message log, APNs/FCM for offline delivery.

      ## 5. Presence, group fanout, storage

      - **Last seen / typing:** presence *events* flow through Redis pub/sub
        (or the same Kafka pipeline) — `typing`, `online`, `last_seen_at`.
        Throttle typing events (every 2–3 s) or you flood the system.
      - **Group chat fanout:**
        - *Fanout-on-write* (small groups): on send, write a copy into each
          member's inbox. Simple reads, expensive writes.
        - *Fanout-on-read* (large groups): store once; each member's timeline
          cache references it. Cheap writes, more read work. WhatsApp uses a
          hybrid: write-once + per-recipient receipt bookkeeping.
      - **Push notifications:** when the receiver is offline, the worker
        calls **APNs (iOS) / FCM (Android)** instead of a socket.
      - **Storage:** messages are write-once, read-by-id → **NoSQL
        (Cassandra/DynamoDB)** keyed by `(conversation_id, message_id)` for
        ordered scans per conversation; recent messages also sit in Redis for
        instant history.

      :::tip
      **Interview question:** How do you guarantee message ordering in chat?
      — "Per conversation, not globally. I partition the Kafka topic by
      conversation_id so every message of one chat lands in a single
      partition and is consumed in order; the sender also stamps a sequence
      number per conversation so clients can sort and detect gaps even
      across reconnects."
      :::

      :::tip
      **Interview question:** WebSockets vs HTTP polling for chat — why? —
      "Polling asks every 2 s: up to 2 s latency and mostly empty requests.
      Long-polling improves latency but still opens an HTTP request per
      message. A WebSocket is one persistent full-duplex connection — the
      server pushes the instant a message arrives, with no per-message
      overhead. That is the right fit for chat."
      :::
