      # Core Components

      Three boxes sit in front of almost every real system: a **load
      balancer**, a **cache**, and a **CDN**. Know what each does and when it
      earns its keep.

      ## Load balancers

      A load balancer (LB) spreads requests across a pool of servers and
      hides the pool behind one address.

      | | L4 (transport) | L7 (application) |
      |---|---|---|
      | Routes on | IP + port | HTTP path, host, headers |
      | Sees | packets | full requests |
      | Extras | fast, low overhead | TLS termination, sticky sessions, path-based routing |
      | Use | TCP, databases, any protocol | web APIs, microservices |

      **Algorithms:**
      - **Round robin** — simplest, ignores current load.
      - **Least connections** — send to the least busy server (good for
        long-lived connections).
      - **IP hash** — same client IP → same server (session stickiness).
      - **Weighted** — bigger servers get proportionally more traffic.

      **Health checks:** the LB pings `/healthz`; dead nodes are removed from
      rotation. **SPOF:** the LB itself must be redundant — an active/passive
      pair sharing a virtual IP, so a failed LB fails over in seconds.

      **Use case:** front every tier — an L7 LB in front of the API (TLS
      termination + `/api/*` routing), an L4 LB in front of the DB read
      replicas.

      ## Caching

      **Redis** is the default cache: in-memory key-value, sub-millisecond
      reads, TTLs, atomic operations — sized so the hot set fits in RAM.

      **Write strategies:**

      | Strategy | Read | Write | Risk |
      |---|---|---|---|
      | **Cache-aside** | miss → DB → populate cache | write DB, invalidate cache | stale window, cold-start stampede |
      | **Write-through** | cache always fresh | write cache + DB together | write latency; cache holds cold data |
      | **Write-back** | cache always fresh | write cache, flush to DB later | data loss if the cache dies |

      **Eviction:** LRU (least recently used — the default), LFU (least
      frequently used), or TTL (expiry — simplest, most common).

      - **Cache stampede:** a hot key expires and thousands of misses hit the
        DB at once → lock/mutex around repopulation, or TTL + jitter.
      - **Cache penetration:** requests for keys that do not exist bypass the
        cache every time → cache nulls briefly, or use a Bloom filter.

      **Use case:** read-heavy hot data — a URL shortener caches the top 20%
      of codes and serves ~80% of reads from Redis.

      ## CDN (Content Delivery Network)

      A CDN caches static content (images, video, JS/CSS) at **edge servers**
      near the user, so the browser hits a nearby node instead of your origin
      data centre.

      - **Pull CDN:** the edge fetches from origin on first request and
        caches with a **TTL**. Automatic, simple — the default.
      - **Push CDN:** you upload content to the edges in advance. More
        control, more ops — for big files and planned events.
      - **Invalidation:** TTL expiry or explicit purge; best practice is
        content-addressed filenames (`app.8f3a2c.js`) so a deploy is just new
        URLs.
      - **Routing:** DNS/anycast points the client at the nearest edge, never
        your origin IP.

      **Use case:** any read-mostly static payload — cut origin load ~90% and
      latency from ~200 ms to ~20 ms for a global audience.

      ## SQL vs NoSQL — the design decision

      - **SQL (Postgres/MySQL):** joins, transactions, ACID, ad-hoc queries.
        Use for money, orders, anything relational. Scales via read replicas,
        then sharding.
      - **NoSQL:** key-value (Redis/DynamoDB), document (MongoDB),
        wide-column (Cassandra). Horizontal scale and high write throughput
        are native; you give up joins and transactions.
      - **Rule of thumb:** start SQL unless the access pattern is "read/write
        by key" or the write scale demands NoSQL. Chat messages, tweets,
        sessions → NoSQL; users, orders, payments → SQL.

      :::tip
      **Interview question:** Cache-aside vs write-through — when which? —
      "Cache-aside: write to the DB and invalidate the cache; the next read
      repopulates it. Best for read-heavy workloads — the cache only holds
      what is actually read. Write-through keeps the cache always fresh at
      the cost of write latency and caching cold data. Default to
      cache-aside; choose write-through when stale reads are unacceptable."
      :::

      :::tip
      **Interview question:** Why do we need a CDN? — "Three reasons:
      latency — an edge node 50 ms away beats an origin 300 ms away;
      origin load — edges absorb the bulk of static traffic; availability —
      edges keep serving cached content during origin outages."
      :::
