      # Design: URL Shortener (TinyURL)

      The canonical first design question — small enough to finish, rich
      enough to touch everything. Interview shape: clarify → estimate → APIs →
      data model → scale → tradeoffs.

      **Use case:** a shareable-link service — take
      `https://example.com/a/very/long/path?x=1&y=2`, return
      `https://s.ly/4c92`, and redirect anyone who opens it.

      ## 1. Requirements

      - **Functional:** shorten a long URL → short code; redirect
        `GET /:code` to the original; optional analytics (clicks per code).
      - **Non-functional:** redirect latency < 50 ms (p99), high
        availability, scale = **100M new URLs/day**, read:write = **10:1**.

      ## 2. Estimates (full working)

      ```
      writes: 100M ÷ 86,400 s/day ≈ 1,157 writes/s
      reads:  10 × 1,157 ≈ 11,570 reads/s ≈ 11.6k QPS
      storage: 100M × 100 B (code + long_url + created_at)
             = 10^10 B = 10 GB/day ≈ 3.6 TB/yr
      ```

      **Cache:** 80/20 rule — cache the top 20% of codes. At ~11.6k read QPS,
      Redis serves ~80% and the DB sees only ~2.3k QPS, within one node's
      ~1–5k range.

      ## 3. APIs

      ```
      POST /api/url      { "long_url": "https://example.com/..." }
        -> 201 { "short_code": "4c92", "short_url": "https://s.ly/4c92" }

      GET /:code
        -> 301 Location: https://example.com/...   (or 302 — see step 5)
      ```

      ## 4. Data model

      ```
      urls (
        id         BIGINT PRIMARY KEY,   -- the ID that encodes to base62
        code       VARCHAR(7) UNIQUE,    -- indexed: the lookup key
        long_url   TEXT,
        created_at TIMESTAMP
      )
      ```

      Lookup is `SELECT long_url FROM urls WHERE code = ?` — the `code`
      index makes it O(log n). Same long_url submitted twice: reuse the
      existing code or mint a new one — pick one policy and stay consistent.

      ## 5. base62, ID generation, and the redirect

      **Why base62?** The short code is the numeric ID written in base 62
      (`0-9a-zA-Z`). base62 is **URL-safe**; base64 uses `+`, `/`, `=`,
      which are not — so base62 wins. 62^7 ≈ 3.5 × 10^12: seven characters
      cover trillions of URLs.

      **ID generation:** DB auto-increment (simple, but a single point of
      failure and guessable codes) vs **Twitter Snowflake**: 41-bit timestamp
      + 10-bit machine id + 12-bit sequence = **4,096 IDs per ms per
      machine** — unique, roughly time-ordered, no central DB. Then
      `code = base62(id)`.

      **301 vs 302:** **301** (permanent) is cached by browsers — repeat
      clicks never reach your server → great for performance and SEO, but
      **you lose click analytics**. **302** (temporary) makes every click hit
      your server → count it, then redirect. Analytics ⇒ **302**.

      ## 6. Scale & tradeoffs

      - **Cache hot URLs:** Redis with TTL; on miss → DB → populate. Protects
        the DB from ~80% of reads.
      - **Read replicas:** reads spread across replicas; writes go to the
        leader.
      - **Shard by id** (or code hash): each shard owns a range; Snowflake
        ids keep inserts sequential and append-friendly.
      - **Rate limit** the POST endpoint — one account must not mint millions
        of codes.
      - **Tradeoffs:** base62 vs random strings (guessable vs unguessable —
        pick random for private links); 301 vs 302 (perf vs analytics);
        auto-increment vs Snowflake (simplicity vs scale).

      :::tip
      **Interview question:** Walk me through designing a URL shortener. —
      "Clarify scale (100M new URLs/day, 10:1 read:write), estimate (~1,157
      writes/s, ~11.6k reads/s, 10 GB/day), design POST /api/url and
      GET /:code, store id + code + long_url with an index on code, encode
      the id in base62, cache the hot 20% in Redis, and scale with read
      replicas plus sharding by id."
      :::
