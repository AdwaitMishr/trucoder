      # Palindrome Queries — hashing with point updates

      Maintain a string of lowercase letters under two operations: change a
      character, and answer whether a substring `s[a..b]` is a palindrome.
      With `n, m ≤ 2·10^5` you need `O(log n)` per operation — a direct
      left-to-right read of the range is `O(n)` per query and too slow.

      ## When you reach for it

      The moment a string has both **point updates** and **range queries**, a
      simple prefix-hash table is not enough (updates would need `O(n)` prefix
      rebuilds). The pattern is: **hashing for `O(1)` substring comparison +
      a Fenwick tree (BIT) for `O(log n)` point updates and prefix-sum queries.**

      A substring `s[a..b]` is a palindrome **iff** it equals its own reverse.
      Compare two numbers — the polynomial hash of the substring, and the
      polynomial hash of its reverse — instead of comparing characters.

      ## Why it works

      Define a polynomial hash where the substring's value is built from the
      *weights* bounding each character:

      - forward hash of `[a,b]`: `F = Σ val(s[i]) · B^(i-a)` (weight `B^0` at `a`),
      - reverse hash of `[a,b]`: characters read `b → a` — equivalently
        `R = Σ val(s[i]) · B^(b-i)`.

      Storing these with *global* weights (`B^i` and `B^(n-1-i)` inside two BITs)
      lets any range sum be read in `O(log n)`, then normalized so the two values
      are directly comparable. If `F == R`, the substring reads the same forward
      as backward — palindrome.

      :::tip
      **Interview tip:** Hashing randomizes correctness (theoretical collision
      chance with a fixed base); interviewers expect you to *mention* using a
      large base / double hashing / random base, but for a coding round a single
      64-bit hash or a big-prime polynomial hash is the accepted answer. The
      deeper point they probe: updates move you from prefix-hash (static) to a
      Fenwick/segment tree that keeps the hash valid under point changes — that's
      the whole design decision.
      :::

      **Complexities:** build `O(n)`, each update and each query `O(log n)`
      (two BITs), space `O(n)`.

      # The Problem

      You are given a string that consists of `n` characters between `a–z`. The
      positions of the string are indexed `1, 2, …, n`.

      Your task is to process `m` operations of the following types:

      1. **Change the character at position `k` to `x`.**
      2. **Check if the substring from position `a` to position `b` is a
         palindrome.**

      ## Input

      The first input line has two integers `n` and `m`: the length of the string
      and the number of operations.

      The next line has a string that consists of `n` characters.

      Finally, there are `m` lines that describe the operations. Each line is of
      the form `1 k x` or `2 a b`.

      ## Output

      For each operation `2`, print `YES` if the substring is a palindrome and
      `NO` otherwise.

      **Constraints:** `1 ≤ n, m ≤ 2·10^5`

      ## Sample

      **Input:**

      ```
      7 5
      aybabtu
      2 3 5
      1 3 x
      2 3 5
      1 5 x
      2 3 5
      ```

      **Output:**

      ```
      YES
      NO
      YES
      ```

      ### Solution — progressive tiers

      **① Brute force — O(n) per query**

      Keep the plain string; each `2 a b` walks `s[a..b]` inward to test the
      palindrome, each `1 k x` is an `O(1)` edit. With `m ≤ 2·10^5` queries over
      `n ≤ 2·10^5`, that's `O(n·m)` in the worst case — too slow.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;

      int main() {
          ios::sync_with_stdio(false); cin.tie(0);
          int n, m; cin >> n >> m;
          string s; cin >> s;
          while (m--) {
              int t; cin >> t;
              if (t == 1) { int k; char x; cin >> k >> x; s[k - 1] = x; }
              else {
                  int a, b; cin >> a >> b; --a; --b;
                  bool ok = true;
                  for (int l = a, r = b; l < r; l++, r--)
                      if (s[l] != s[r]) { ok = false; break; }
                  cout << (ok ? "YES" : "NO") << "\n";
              }
          }
          return 0;
      }
      ```

      *Correct — the update is cheap but every palindrome check walks the whole
      range.*

      **② Optimization — polynomial hash in two Fenwick trees, O(log n) per op**

      Keep a forward BIT storing `val(s[i])·B^(i-1)` and a reverse BIT storing
      `val(s[i])·B^(n-i)`. A range's two hashes are prefix sums (BIT `sum`);
      normalize and compare. Updates add the difference at position `k` to both
      trees. This is the optimal tier — compiled and run against the sample, its
      output is `YES / NO / YES`.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      typedef long long ll;
      const ll MOD = 1000000007LL;
      const ll B = 911382323LL;

      struct BIT {
          int n; vector<ll> bit;
          BIT(int n) : n(n), bit(n + 2, 0) {}
          void add(int i, ll v) { v %= MOD; if (v < 0) v += MOD; for (; i <= n; i += i & -i) bit[i] = (bit[i] + v) % MOD; }
          ll sum(int i) { ll s = 0; for (; i > 0; i -= i & -i) s = (s + bit[i]) % MOD; return s; }
      };

      int main() {
          ios::sync_with_stdio(false); cin.tie(0);
          int n, m; cin >> n >> m;
          string s; cin >> s;
          vector<ll> pw(n + 1); pw[0] = 1;
          for (int i = 1; i <= n; i++) pw[i] = pw[i - 1] * B % MOD;
          BIT fw(n), rv(n);                     // forward and reverse hash trees
          auto val = [](char c) { return (ll)(c - 'a' + 1); };
          for (int i = 1; i <= n; i++) {
              fw.add(i, val(s[i - 1]) * pw[i - 1] % MOD);   // weight B^(i-1)
              rv.add(i, val(s[i - 1]) * pw[n - i] % MOD);   // weight B^(n-i)
          }
          while (m--) {
              int t; cin >> t;
              if (t == 1) {
                  int k; char x; cin >> k >> x;
                  ll delta = (val(x) - val(s[k - 1])) % MOD; if (delta < 0) delta += MOD;
                  fw.add(k, delta * pw[k - 1] % MOD);
                  rv.add(k, delta * pw[n - k] % MOD);
                  s[k - 1] = x;
              } else {
                  int a, b; cin >> a >> b;
                  ll fH = (fw.sum(b) - fw.sum(a - 1) + MOD) % MOD;   // forward hash
                  ll rH = (rv.sum(b) - rv.sum(a - 1) + MOD) % MOD;   // reverse hash
                  ll L = fH * pw[n - b] % MOD;     // normalize forward
                  ll R = rH * pw[a - 1] % MOD;     // normalize reverse
                  cout << (L == R ? "YES" : "NO") << "\n";
              }
          }
          return 0;
      }
      ```

      *`O(n)` build, `O(log n)` per update and query, `O(n)` memory.*

      **③ Why the normalization (and safety notes)**

      The raw BIT sums give `F' = Σ val(i)·B^(i-1)` over `[a,b]` (factor `B^(a-1)`
      too large) and `R' = Σ val(i)·B^(n-i)` (factor `B^(n-b)` too large). Equal
      means `F'/B^(a-1) = R'/B^(n-b)`, i.e. `F'·B^(n-b) = R'·B^(a-1)` — the
      comparison above, using powers instead of modular inverses. For a hard
      guarantee against the (tiny) collision chance, use **double hashing** (two
      `(base, mod)` pairs) or a **random base** chosen per run; the code logic is
      otherwise identical.

      # Code logic

      - **Two BITs = two directions.** `fw` accumulates the polynomial hash read
        left-to-right; `rv` reads right-to-left. Their internal sums use global
        weights `B^(i-1)` and `B^(n-i)`, which is what makes range sums recover
        the substring hash in `O(log n)` via `sum(r) - sum(l-1)`.
      - **Update.** Changing `s[k]` from `o` to `x` changes the two trees by
        `(val(x)-val(o))·B^(k-1)` and `(val(x)-val(o))·B^(n-k)`. A BIT point-add
        handles this in `O(log n)`; the plain string `s` is kept in sync so later
        deltas are correct.
      - **Palindrome check.** A substring is a palindrome iff forward hash equals
        reverse hash. We multiply each by the missing power (equivalent to
        dividing out the surplus weight) so both are in the same scale, then
        compare. Modular arithmetic keeps `ll` multiplication safe
        (`< MOD² ≈ 10^18 < 9.2·10^18`).

      # Walkthrough

      Trace the sample — `n = 7`, string `aybabtu`, `m = 5`.

      **Query `2 3 5`** — `s[3..5] = "bab"`. Forward and reverse hashes are
      equal → palindrome.

      ```
      Output YES
      ```

      **Query `1 3 x`** — `s[3] = 'b' → 'x'`: string becomes `ayxabtu`.

      **Query `2 3 5`** — `s[3..5] = "xab"` (positions `x,a,b`). Forward `xab`,
      reverse `bax` → not equal.

      ```
      Output NO
      ```

      **Query `1 5 x`** — `s[5] = 'b' → 'x'`: the string (now `ayxabtu`) becomes
      `ayxaxtu` (positions `a y x a x t u`).

      **Query `2 3 5`** — `s[3..5] = "xax"` → palindrome.

      ```
      Output YES
      ```

      ```
      Expected (sample):  YES, NO, YES
      Actual (two BITs):  YES, NO, YES     ← match
      ```

      Each check cost `O(log n)` (two BIT sum pairs + two multiplications), and
      each update two BIT point-adds — no range rescanning anywhere.
