      # Flight Routes — the k shortest paths

      Given a directed graph with non-negative edge weights, find the **k
      cheapest** routes from city `1` to city `n`. A route may visit the same
      city several times, and we only need the *prices* of the k smallest
      routes — not the routes themselves.

      Here `k ≤ 10`, so we can afford an algorithm that finds shortest paths
      "beyond the first one".

      ## Why plain Dijkstra is not enough

      A classic Dijkstra run finalizes each node exactly once — the moment it is
      popped with its true shortest distance — and then never revisits it. To get
      the 2nd, 3rd, …, k-th shortest distances we must let each node be
      *finalized several times*.

      ## The structural fact that makes this easy

      With non-negative weights, the (j+1)-th cheapest route to a node `v` is
      always obtained by taking some already-found route to a predecessor `p` of
      `v` and appending the single edge `p -> v`. So a min-heap that **allows a
      node to be popped up to k times**, relaxing its outgoing edges each time,
      will discover the 1st, 2nd, …, k-th cheapest distances to every node — and
      in particular to `n`.

      ## Top-k Dijkstra

      - Push `(distance, start)`.
      - Keep a counter `cnt[v]` = how many times `v` has been finalized.
      - Pop the minimum `(d, u)`. If `cnt[u] >= k`, skip it; otherwise `cnt[u]++`.
      - If `u == n`, record `d` as the next of our k answers.
      - For every edge `u -> v` of weight `w`, push `(d + w, v)`.
      - Stop once we have collected k answers for node `n`.

      **Time:** O(k·m log n) — each edge is relaxed up to k times and each heap
      insert costs O(log n). **Space:** O(n + m).

      :::tip
      **Interview tip:** "k-th shortest path" is a classic step-up from ordinary
      shortest-path questions. Interviewers cap k small (≤ 5–10) precisely so the
      top-k Dijkstra trick (reopen each vertex up to k times) works; a heavier
      algorithm like Yen's is rarely required except in the hardest rounds.
      Recognizing when a tiny k buys you k re-finalizations per node is exactly
      the insight they test.
      :::

      # Question — Flight Routes

      Your task is to find the **k shortest flight routes** from Syrjälä to
      Metsälä. A route can visit the same city several times. There can be
      several routes with the same price, and each of them should be considered.

      **Input**

      The first input line has three integers `n`, `m` and `k`: the number of
      cities, the number of flights, and the parameter `k`. The cities are
      numbered `1, 2, ..., n`. City `1` is Syrjälä, and city `n` is Metsälä.

      After this, there are `m` lines describing the flights. Each line has three
      integers `a`, `b` and `c`: a flight begins at city `a`, ends at city `b`,
      and its price is `c`. All flights are one-way. You may assume that there
      are at least `k` distinct routes from Syrjälä to Metsälä.

      **Output**

      Print `k` integers: the prices of the `k` cheapest routes, sorted by price.

      **Constraints**

      - `2 <= n <= 10^5`
      - `1 <= m <= 2*10^5`
      - `1 <= a, b <= n`
      - `1 <= c <= 10^9`
      - `1 <= k <= 10`

      **Example**

      Input:

      ```
      4 6 3
      1 2 1
      1 3 3
      2 3 2
      2 4 6
      3 2 8
      3 4 1
      ```

      Output:

      ```
      4
      4
      7
      ```

      The cheapest routes are `1 -> 3 -> 4` (price 4), `1 -> 2 -> 3 -> 4` (price
      4) and `1 -> 2 -> 4` (price 7).

      ### Solution

      **① Brute force — enumerate all routes, exponential time**

      Walk the graph from `1`, accumulating prices, and when you reach `n`
      record the total. Collect everything and sort. This is correct in spirit,
      but the number of routes grows exponentially in `n` (and, because revisits
      are allowed, even infinitely if unbounded) — with `n` up to `10^5` and
      `m` up to `2·10^5` it is hopelessly too slow. A naive DFS tracking visited
      nodes terminates but still enumerates an exponential number of distinct
      paths.

      ```cpp
      // Illustration of the naive idea only — exponential, unusable.
      void dfs(int u, long long cost, int n,
               const vector<vector<pair<int,long long>>>& g, vector<ll>& out) {
          if (u == n) { out.push_back(cost); return; }
          for (auto [v, w] : g[u]) dfs(v, cost + w, n, g, out);
      }
      ```

      **② Optimization — top-k Dijkstra, O(k·m log n) time, O(n + m) space**

      Reopen each node up to `k` times. The `k` cheapest distances to `n` are
      recorded in the order they pop.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      typedef long long ll;
      int main(){
          ios::sync_with_stdio(false); cin.tie(nullptr);
          int n, m, k; cin >> n >> m >> k;
          vector<vector<pair<int,ll>>> g(n + 1);
          for (int i = 0; i < m; ++i) {
              int a, b; ll c; cin >> a >> b >> c;
              g[a].push_back({b, c});
          }
          vector<int> cnt(n + 1, 0);
          priority_queue<pair<ll,int>, vector<pair<ll,int>>, greater<>> pq;
          pq.push({0, 1});
          vector<ll> ans;
          while (!pq.empty() && (int)ans.size() < k) {
              auto [d, u] = pq.top(); pq.pop();
              if (cnt[u] >= k) continue;          // already finalized k times
              cnt[u]++;
              if (u == n) ans.push_back(d);       // next cheapest route to n
              for (auto [v, w] : g[u]) pq.push({d + w, v});
          }
          for (ll x : ans) cout << x << "\n";
          return 0;
      }
      ```

      **③ Further optimization** — not needed: with `k <= 10` the top-k Dijkstra
      is already O(k·m log n), comfortably within the limits. There is no
      simpler faster variant.

      **④ Alternative — Yen's algorithm / Eppstein's algorithm**

      For the *k shortest simple (loopless) paths* in a general graph, Yen's
      algorithm runs in O(k·n·(m + n log n)) and is the textbook general
      method. It is overkill here both because k is tiny and because this
      problem explicitly allows revisiting cities, which the top-k Dijkstra
      handles naturally.

    content: |
      # Code logic

      Focus on the O(k·m log n) solution in **②**:

      - `cnt[v]` counts how many times node `v` has been *finalized* (popped).
        We skip any pop once `cnt[u]` reaches `k`, so a node can contribute to
        the top-k at most k times.
      - Every time we pop `u` we relax **all** its outgoing edges, pushing
        `d + w` into the heap regardless of whether `v` was reached before. That
        is what lets us find the 2nd, 3rd, … cheapest ways into `v`, not just the
        first.
      - When the popped node is `n`, its distance `d` is exactly the next
        cheapest route price, so we append it to `ans`.
      - Loop while `ans.size() < k`. Because the problem guarantees at least `k`
        distinct routes, `ans` fills up; the count guard on `n` also prevents
        overriding with a stale larger entry.

      The heap guarantees we always pop a globally smallest not-yet-finalized
      distance, so route prices come out in non-decreasing order — that is, the
      k cheapest routes first.
