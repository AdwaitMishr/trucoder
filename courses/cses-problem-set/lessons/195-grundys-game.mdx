      # Grundy's Game — a splitting game solved by Sprague-Grundy

      There is a single heap of `n` coins. On each move a player chooses a heap
      and splits it into **two non-empty heaps of different sizes**. Whoever
      makes the last move (i.e. whoever makes the position reach a state with no
      legal split) wins. With `t ≤ 10^5` queries and `n ≤ 10^6`, who wins?

      A split of `n` into `a + b` with `1 ≤ a < b` turns one heap into **two**,
      so this is genuinely a *multi-heap* game and ordinary `win/lose` DP on a
      single number cannot capture it. The right tool is the Sprague-Grundy
      (SG) value: a position (a set of heaps) has SG equal to the XOR of its
      heaps' SG values, and it is losing iff that XOR is `0`.

      ## SG recurrence for a heap of size `n`

      A heap of size `n` can split into `(a, b)` with `a < b`, `a + b = n`. Its
      SG value is the mex of the XORs of the two children:

      ```
      g(0) = g(1) = g(2) = 0            // no legal unequal split exists
      g(n) = mex{ g(a) xor g(b) : 1 <= a < b, a + b = n }
      ```

      For example `g(3) = mex{ g(1) xor g(2) } = mex{0} = 1`, and
      `g(4) = mex{ g(1) xor g(3) } = mex{1} = 0`.

      ## The crucial fact: only finitely many losing sizes

      Famously, the set of sizes with `g(n) = 0` (the "P-positions") is
      **finite**. Computing the sequence confirms it:

      ```
      0, 1, 2, 4, 7, 10, 20, 23, 26, 50, 53, 270, 273, 276, 282, 285, 288,
      316, 334, 337, 340, 346, 359, 362, 365, 386, 389, 392, 566, 630, ...,
      1222   <- the last P-position
      ```

      Every `n > 1222` has `g(n) > 0`. So we precompute `g` up to a safe bound
      `B` (much larger than `1222`, say `10000`) and for any `n > B` answer
      "first" immediately — no need to reach `10^6`.

      **Time:** O(B²) to precompute (a few tens of millions of XOR/mex steps
      with `B = 10000`) + O(1) per query. **Space:** O(B).

      :::tip
      **Interview tip:** "split a heap into two non-equal / coprime / anything
      parts" is the canonical *SG-splitting* problem. The interview-savvy
      instinct is: compute Grundy values up to a modest bound, then look for a
      pattern (here: finitely many P-positions). The `mex`, the XOR-of-children
      recurrence, and the "find the structure, never precompute to `10^6`"
      lesson are exactly what make this hard problem tractable.
      :::

      # Question — Grundy's Game

      There is a heap of `n` coins and two players who move alternately. On
      each move, a player chooses a heap and divides it into two nonempty heaps
      that have a different number of coins. The player who makes the last move
      wins the game.

      Your task is to find out who wins if both players play optimally.

      **Input**

      The first input line contains an integer `t`: the number of tests.

      After this, there are `t` lines that describe the tests. Each line has an
      integer `n`: the number of coins in the initial heap.

      **Output**

      For each test case, print "first" if the first player wins the game and
      "second" if the second player wins the game.

      **Constraints**

      - `1 <= t <= 10^5`
      - `1 <= n <= 10^6`

      **Example**

      Input:

      ```
      3
      6
      7
      8
      ```

      Output:

      ```
      first
      second
      first
      ```

      ### Solution

      **① Brute force — precompute g up to every query, O(max_n²) time**

      The direct recurrence `g(n) = mex{ g(a) xor g(b) : a<b, a+b=n }` with the
      inner loop over all `a` from `1` to `n/2` is `O(n)` per size, so filling it
      up to `10^6` costs `O(10^12)` — completely infeasible:

      ```cpp
      // too slow: O(n^2) over the whole range
      for (int n = 1; n <= maxN; n++) {
          bool seen[256] = {};
          for (int a = 1; a < n - a; a++)
              seen[g[a] ^ g[n - a]] = true;   // record reachable XORs
          int mex = 0;
          while (seen[mex]) mex++;
          g[n] = mex;
      }
      ```

      **② Optimization — precompute modestly + "first" beyond, O(B²) time**

      Exploit that the P-positions are finite (last one is `1222`). Pick a safe
      bound `B = 10000`, precompute `g[0..B]` once, then answer every query
      `n > B` as "first":

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;

      int main() {
          ios::sync_with_stdio(false);
          cin.tie(nullptr);

          const int B = 10000;
          vector<int> g(B + 1, 0);
          vector<unsigned char> seen(1024, 0);      // grundy values stay small

          for (int n = 1; n <= B; n++) {
              int maxV = 0;
              for (int a = 1; a < n - a; a++) {     // a < b, a + b = n
                  int v = g[a] ^ g[n - a];
                  if (v < (int)seen.size() && !seen[v]) {
                      seen[v] = 1;
                      if (v > maxV) maxV = v;
                  }
              }
              int mex = 0;
              while (mex < (int)seen.size() && seen[mex]) mex++;
              g[n] = mex;
              for (int v = 0; v <= maxV; v++) seen[v] = 0;
          }

          int t;
          cin >> t;
          while (t--) {
              int n;
              cin >> n;
              cout << (n > B ? "first" : (g[n] ? "first" : "second")) << "\n";
          }
      }
      ```

      **③ Further optimisation** — the query loop is already `O(1)`; the
      precompute is a fixed one-time cost. Nothing else to shave off asymptotically.

      **④ Alternative algorithm** — since the P-positions form a small finite
      set, an even faster variant hard-codes that list and answers each query in
      `O(1)` with a membership check:

      ```cpp
      // finite P-positions: 0 1 2 4 7 10 20 23 26 50 53 270 273 276 282 285 288
      //  316 334 337 340 346 359 362 365 386 389 392 566 630 633 636 639 673 676
      //  682 685 923 926 929 932 1222
      set<int> losing = {0,1,2,4,7,10,20,23,26,50,53,270,273,276,282,285,288,
                         316,334,337,340,346,359,362,365,386,389,392,566,630,
                         633,636,639,673,676,682,685,923,926,929,932,1222};
      cout << (losing.count(n) ? "second" : "first") << "\n";
      ```

      This trades the precompute for a verified constant table. Tier **②** is
      the general, self-contained submission; **④** is the practical fastest.

      # Code logic

      Walk through the `O(B²)` precompute in **②**:

      - `g[a] ^ g[n - a]` is the SG value of the two-heap position that `n`
        splits into; SG forces us to XOR, not add, the children.
      - For each `n`, the inner loop runs `a` from `1` while `a < n - a`, i.e.
        `a ≤ n/2 - 1`, guaranteeing an **unequal** split `a < b`. The `a == b`
        case (e.g. splitting an even `n` into equal halves) is correctly
        excluded, as required by the rules.
      - `seen[]` records which XOR values are reachable, then `mex` is the
        smallest non-negative integer not seen.
      - `seen` is reset to `0` only over the touched range `[0, maxV]` — cheaper
        than zeroing all 1024 slots every iteration.
      - Finally `g[n] != 0` means a winning position, and the `n > B` branch
        answers "first" for every size past the last P-position (`1222`).
