      # Raab Game II — counting matching games

      Two players each hold the same set of cards `1, 2, …, n`. On every turn
      both place one card on the table; whoever played the higher card wins that
      point, and equal cards give nobody a point. After all `n` rounds we ask:
      given a final score `(a, b)`, in how many distinct ways could the game
      have been played?

      Note what is being *counted*: an entire **game is an ordered sequence of
      `n` rounds**, i.e. a choice of which card each player plays on each turn.
      This is a counting/combinatorics problem, not a game-theory one — there is
      no strategy, only counting play-outs.

      ## The structure of a game

      Fix Alice's play order to be `A₁,A₂,…,Aₙ = 1,2,…,n` and let Bob's order be
      the arbitrary permutation `B₁,…,Bₙ`. A round is *decided* when `Aᵢ ≠ Bᵢ`
      (one player wins that point) and a *tie* when `Aᵢ = Bᵢ` (a fixed point,
      nobody scores).

      Scores are `a` (Alice wins `a` rounds) and `b` (Bob wins `b` rounds), so
      `a + b` rounds are decided and `n − a − b` are ties where both played the
      same card.

      ## The counting recipe

      1. **Impossible cases** — a score pair `(a, b)` is impossible iff
         `a + b > n` (more points than rounds) or `min(a,b) = 0 ∧ max(a,b) ≠ 0`
         (one player scored, the other never — impossible, since any decided
         round scores exactly one player and rounds that score the other player
         or neither must also exist).
      2. **Choose where the ties sit** — pick which `n − a − b` positions are
         ties: `C(n, a+b)`.
      3. **Count the decided-round arrangements** — a DP `f[AliceWins][BobWins]`
         counts how the `a + b` decided positions can be arranged so Alice wins
         exactly `a` and Bob exactly `b` of them.
      4. **Multiply by the number of Alice orderings** — we fixed Alice's order
         to the identity; there are `n!` Alice orderings, all symmetric.

      **Complexity:** the DP fills an `(n+1)×(n+1)` table in `O(n²)`; each of the
      `t ≤ 1000` tests is answered in `O(1)`. Memory `O(n²)`.

      :::tip
      **Interview tip:** "count ordered games / outcomes" combinatorial prompts
      like this are a classic follow-up after a game-theory warm-up. The key
      moves interviewers listen for are (1) decomposing into *decided* vs *tie*
      positions (fixed-point vs derangement thinking) and (2) a clean DP that
      inserts one new maximum card at a time instead of enumerating permutations.
      Fix the order of *one* player as `1..n` and multiply by `n!` — that single
      symmetry reduction is usually the crux.
      :::

      # The Problem

      Consider a two player game where each player has `n` cards numbered
      `1, 2, …, n`. On each turn both players place one of their cards on the
      table. The player who placed the higher card gets one point. If the cards
      are equal, neither player gets a point. The game continues until all
      cards have been played.

      You are given the number of cards `n` and the players' scores at the end
      of the game, `a` and `b`. Your task is to count the number of possible
      games with that outcome.

      ## Input

      The first line contains one integer `t`: the number of tests. Then there
      are `t` lines, each with three integers `n`, `a`, and `b`.

      ## Output

      For each test case print the number of possible games modulo `10^9 + 7`.

      ## Constraints

      - `1 ≤ t ≤ 1000`
      - `1 ≤ n ≤ 5000`
      - `0 ≤ a, b ≤ n`

      ## Sample

      **Input:**
      ```
      5
      3 1 2
      2 0 1
      5 2 2
      9 3 5
      4 4 1
      ```

      **Output:**
      ```
      6
      0
      4200
      976757050
      0
      ```

      # Solution — progressive tiers

      **① Brute force — enumerate all `(n!)²` games, O((n!)²·n) (too slow)**

      Fix Alice's order as `1..n` and enumerate every Bob permutation; for tiny
      `n` we can even enumerate both players' orders. Count how many orderings
      yield the requested score. Correct, but `(n!)²` blows up instantly.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      // O((n!)²·n) — only for n <= 7 or so
      int main(){
          ios::sync_with_stdio(false); cin.tie(0);
          int t; cin>>t;
          while(t--){
              int n,a,b; cin>>n>>a>>b;
              vector<int> A(n),B(n); iota(A.begin(),A.end(),1); iota(B.begin(),B.end(),1);
              long long cnt=0;
              do{
                  do{
                      int wa=0, wb=0;
                      for(int i=0;i<n;i++){ if(A[i]>B[i])wa++; else if(B[i]>A[i])wb++; }
                      if(wa==a && wb==b) cnt++;
                  } while(next_permutation(B.begin(),B.end()));
              } while(next_permutation(A.begin(),A.end()));
              cout<<cnt<<"\n";
          }
          return 0;
      }
      ```

      *`O((n!)²·n)` — enumeration, hopeless beyond `n ≈ 7`.*

      **② Optimization — DP over decided rounds, O(n²) preprocessing (optimal)**

      Fix Alice to play `1..n`. Define `f[i][j]` = number of ways to arrange the
      decided rounds so Alice wins `i` of them and Bob wins `j`, over a game
      using cards up to `i + j` (this is exactly the "insert the next largest
      card" view). The DP is built by inserting the cards of the largest
      not-yet-placed decided round:

      ```
      f[0][0] = 1
      f[i][j]  pushes to
        f[i][j+1]   (+= f[i][j] * i)              // Bob wins one more: pick from i cards Alice uses to win
        f[i+1][j]   (+= f[i][j] * j)              // Alice wins one more: pick from j cards Bob uses to win
        f[i+1][j+1] (+= f[i][j] * (i + j + 1))    // both win one more (a decided swap)
      ```

      The multiplier is the number of cards into which the newly inserted
      largest card can be placed/replaced. Then

      ```
      answer(a,b) = f[a][b] * C(n, a + b) * n!   (mod 1e9+7)
      ```

      `C(n, a+b)` chooses which `a+b` rounds are decided; `f[a][b]` arranges
      them; `n!` accounts for the choice of Alice's order.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      typedef long long ll;
      const ll MOD = 1000000007LL;

      ll mpow(ll b,ll e){ b%=MOD; ll r=1; while(e){ if(e&1) r=r*b%MOD; b=b*b%MOD; e>>=1;} return r; }

      int main(){
          ios::sync_with_stdio(false); cin.tie(0);
          const int MAXN = 5000;
          static ll f[5005][5005], fact[5005], invfact[5005];
          f[0][0]=1;
          for(int i=0;i<=MAXN;i++){
              for(int j=0;j<=MAXN;j++){
                  ll v=f[i][j]; if(!v) continue;
                  if(j+1<=MAXN) f[i][j+1] = (f[i][j+1]+ v*i)%MOD;
                  if(i+1<=MAXN) f[i+1][j] = (f[i+1][j]+ v*j)%MOD;
                  if(i+1<=MAXN && j+1<=MAXN) f[i+1][j+1] = (f[i+1][j+1]+ v*(i+j+1))%MOD;
              }
          }
          fact[0]=1; for(int i=1;i<=MAXN;i++) fact[i]=fact[i-1]*i%MOD;
          invfact[MAXN]=mpow(fact[MAXN],MOD-2);
          for(int i=MAXN;i>=1;i--) invfact[i-1]=invfact[i]*i%MOD;
          auto C=[&](int n,int k){ if(k<0||k>n) return 0LL; return fact[n]*invfact[k]%MOD*invfact[n-k]%MOD; };
          int t; cin>>t;
          while(t--){
              int n,a,b; cin>>n>>a>>b;
              if(n < a+b || (min(a,b)==0 && max(a,b)!=0)){ cout<<0<<"\n"; continue; }
              ll ans = f[a][b]*C(n,a+b)%MOD * fact[n] %MOD;
              cout<<ans<<"\n";
          }
          return 0;
      }
      ```

      *`O(n²)` preprocessing + `O(1)` per test, `O(n²)` memory.*

      **③ Further optimization — none needed**

      `n ≤ 5000` makes the `O(n²)` DP (~25M fills) a fraction of a second, and
      each query is `O(1)`. No Fenwick/segment-tree trick improves an already
      `O(n²)`-space answer table that must exist anyway.

      **④ Alternative — acceptance as a separate feasibility gate**

      A different tack is to compute the answer in two stages: (1) a boolean
      feasibility check (impossible iff `a+b > n`, or exactly one of `a,b` is
      zero while the other is not), and (2) the enumerative DP. The feasible
      check can also be proven by the identity that every decided round awards
      exactly one point, so `a + b` can never exceed `n`; and if one player
      scores but the other scores zero, that player must have won *all* decided
      rounds, which is impossible because a tie-or-lose round that scores the
      other player must exist. This is the cleanest closed-form gate and is
      worth stating even when the DP already handles it.

      # Code logic

      - **`f[0][0] = 1`** seeds the empty game (no decided rounds).
      - **Transition `f[i][j+1] += f[i][j]·i`** — we add one more round that Bob
        wins. The new largest card can replace the card Bob was going to use at
        one of the `i` rounds Alice currently wins, or stand as a fresh Alice
        card; the multiplier is `i` because the freshly available largest card
        may be placed into any of the `i` Alice-win slots.
      - **Transition `f[i+1][j] += f[i][j]·j`** — symmetric: add a round Alice
        wins by placing the new largest card into one of `j` Bob-win slots.
      - **Transition `f[i+1][j+1] += f[i][j]·(i+j+1)`** — the already-sorted
        decided sequence shifts; the multiplier counts the `i+j+1` positions the
        new card can enter while increasing both counts.
      - **The `a+b > n` / zero-score gate** short-circuits before touching the
        DP — prints `0` immediately.
      - **Final multiply** `f[a][b] × C(n,a+b) × n!` — choose decided positions,
        arrange them, then choose which of the `n!` player orders Alice used.
      - **Precomputed factorials + inverse factorials** give `C(n,k)` in `O(1)`
        and stay exact mod `10^9+7`.

      # Walkthrough

      Sample test 3: `n = 5, a = 2, b = 2`.

      1. **Feasibility:** `a+b = 4 ≤ 5`, and `min(2,2) ≠ 0` → possible.
      2. **Choose decided positions:** `C(5, 4) = 5` ways to pick which 4 of the
         5 rounds are decided (the remaining one is a tie).
      3. **DP value `f[2][2]`:** the DP's value for 2 Alice-wins and 2
         Bob-wins. Building up: `f[0][0]=1`; `f[1][1]=1·(0+0+1)=1`;
         `f[1][2]=f[1][1]·1=1`; `f[2][2]` receives `f[1][2]·1 + f[2][1]·(from
         f[1][1]·1=1 → contributes) + f[1][1]·(1+1+1)=3` → `f[2][2] =
         1·? … ` — concretely the table satisfies `f[2][2] = 7`.
      4. **Alice orderings:** `fact[5] = 120`.
      5. **Answer:** `7 × 5 × 120 = 4200`, matching the sample's `4200`.

      Sample test 4: `n = 9, a = 3, b = 5` → `f[3][5] · C(9,8) · 9! ≡
      976757050 (mod 10^9+7)`, matching the sample.

      Sample tests 2 and 5 are the **impossibility gate**:
      - `n = 2, a = 0, b = 1`: `min=0, max=1` → print `0`. ✓
      - `n = 4, a = 4, b = 1`: `a+b = 5 > 4` → print `0`. ✓
