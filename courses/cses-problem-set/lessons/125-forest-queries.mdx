      # Forest Queries — 2D prefix sums

      We have an `n x n` grid where each cell is either empty (`.`) or a tree
      (`*`). We are asked `q` rectangle queries: *how many trees are inside a
      given rectangle?* This is the two-dimensional version of the classic
      range-sum problem.

      The idea is exactly the 1D trick lifted to 2D: **precompute a 2D prefix
      sum table** so that every rectangle query becomes a constant-time,
      `O(1)` answer using inclusion–exclusion.

      ## 2D prefix sums

      Define

      ```
      pre[i][j] = number of trees in the rectangle (1,1)..(i,j)
      ```

      To fill it cell by cell, note that the rectangle `(1,1)..(i,j)` is the
      union of `(1,1)..(i-1,j)` and `(1,1)..(i,j-1)`, but the overlap
      `(1,1)..(i-1,j-1)` is counted twice — so add it back once:

      ```
      pre[i][j] = (cell (i,j) is a tree ? 1 : 0)
                  + pre[i-1][j] + pre[i][j-1] - pre[i-1][j-1]
      ```

      ## Answering a rectangle in O(1)

      A rectangle `(y1,x1)..(y2,x2)` is, by the same inclusion–exclusion,

      ```
      trees = pre[y2][x2] - pre[y1-1][x2] - pre[y2][x1-1] + pre[y1-1][x1-1]
      ```

      A small diagram: the rectangle equals the big block `pre[y2][x2]`, minus
      the strip above (`pre[y1-1][x2]`), minus the strip to the left
      (`pre[y2][x1-1]`), plus the corner we removed twice (`pre[y1-1][x1-1]`).

      **Time:** `O(n^2)` to build + `O(1)` per query. **Space:** `O(n^2)`.

      :::tip
      **Interview tip:** 2D prefix sums are the first tool to reach for on any
      "count/look things up inside rectangles" problem — matrix region sums,
      image tests, board games, counting submatrices. Lock in the two formulas
      (build from top-left, answer by inclusion–exclusion) — they recur
      everywhere, from CSES to LeetCode matrix problems like "Range Sum
      Query 2D – Immutable".
      :::

      # The Problem

      You are given an `n x n` grid representing the map of a forest. Each
      square is either empty or contains a tree. The upper-left square has
      coordinates `(1,1)`, and the lower-right square has coordinates `(n,n)`.

      Your task is to process `q` queries of the form: **how many trees are
      inside a given rectangle in the forest?**

      ## Input

      The first input line has two integers `n` and `q`: the size of the forest
      and the number of queries.

      Then, there are `n` lines describing the forest. Each line has `n`
      characters: `.` is an empty square and `*` is a tree.

      Finally, there are `q` lines describing the queries. Each line has four
      integers `y_1, x_1, y_2, x_2` corresponding to the corners of a
      rectangle.

      **Constraints**

      - `1 <= n <= 1000`
      - `1 <= q <= 2 * 10^5`
      - `1 <= y_1 <= y_2 <= n`
      - `1 <= x_1 <= x_2 <= n`

      ## Output

      Print the number of trees inside each rectangle.

      ## Example

      Input:

      ```
      4 3
      .*..
      *.** 
      **..
      ****
      2 2 3 4
      3 1 3 1
      1 1 2 2
      ```

      Output:

      ```
      3
      1
      2
      ```

      ### Solution — progressive tiers

      **① Brute force — count inside each rectangle by scanning, O(q · n^2)**

      For every query, loop over all cells in `(y1,x1)..(y2,x2)` and count the
      `*`. Correct but with `n = 1000`, `q = 2*10^5` each rectangle can be the
      whole grid (`10^6` cells) — up to `2 * 10^11` steps. Far too slow.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      int main() {
          ios::sync_with_stdio(false); cin.tie(0);
          int n, q; cin >> n >> q;
          vector<string> g(n + 1);
          for (int i = 1; i <= n; i++) cin >> g[i];
          while (q--) {
              int y1, x1, y2, x2; cin >> y1 >> x1 >> y2 >> x2;
              int cnt = 0;
              for (int i = y1; i <= y2; i++)
                  for (int j = x1; j <= x2; j++)
                      if (g[i][j - 1] == '*') cnt++;
              cout << cnt << "\n";
          }
          return 0;
      }
      ```

      *`O(q · n^2)` worst case — ~`2 * 10^11` cell visits.*

      **② Optimization — 2D prefix sums, O(n^2 + q)**

      Build `pre[i][j]` = trees in `(1,1)..(i,j)`, then answer each rectangle
      in `O(1)` by inclusion–exclusion. This is the optimal tier.

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;
      int main() {
          ios::sync_with_stdio(false); cin.tie(0);
          int n, q; cin >> n >> q;
          vector<vector<int>> pre(n + 1, vector<int>(n + 1, 0));
          for (int i = 1; i <= n; i++) {
              string s; cin >> s;
              for (int j = 1; j <= n; j++)
                  pre[i][j] = (s[j - 1] == '*') + pre[i - 1][j] + pre[i][j - 1] - pre[i - 1][j - 1];
          }
          while (q--) {
              int y1, x1, y2, x2; cin >> y1 >> x1 >> y2 >> x2;
              int ans = pre[y2][x2] - pre[y1 - 1][x2] - pre[y2][x1 - 1] + pre[y1 - 1][x1 - 1];
              cout << ans << "\n";
          }
          return 0;
      }
      ```

      *`O(n^2)` build, `O(1)` per query, `O(n^2)` space.*

      **③ Alternative — 2D Fenwick tree, O(log^2 n) per op**

      If the forest could *change* (a tree added or removed), static prefix
      sums would need to be rebuilt each time. A 2D Fenwick tree supports
      point updates and rectangle queries in `O(log^2 n)`. Not needed here —
      the input is static — but it is the natural upgrade.

      **④ Further optimization —** none needed: `O(1)` per query is optimal
      (the build reads every cell once, `Ω(n^2)`).

      # Code logic

      Focus on **②**:

      - **Build.** We iterate rows `1..n` and columns `1..n`. Each cell value
        is `1` if the character is `*`. Then `pre[i][j] = cell + pre[i-1][j] +
        pre[i][j-1] - pre[i-1][j-1]`. The `+ pre[i-1][j]` ("all trees above")
        and `+ pre[i][j-1]` ("all trees to the left") overlap in
        `pre[i-1][j-1]` (the top-left corner), which is why it is subtracted.

      - **Query.** A rectangle `(y1,x1)..(y2,x2)`:

        ```
        pre[y2][x2]                      whole block from origin
        - pre[y1-1][x2]                  strip above row y1
        - pre[y2][x1-1]                  strip left of column x1
        + pre[y1-1][x1-1]                corner removed twice, add back
        ```

      - **Coordinates.** The grid uses 1-based row/column, matching the input,
        so no indexing fiddling is needed. `y1-1` and `x1-1` are 0-safe because
        the table has a zero border (row 0 / column 0 are all 0).

      ```
      Row 1:  . * . .
      Row 2:  * . * *
      Row 3:  * * . .
      Row 4:  * * * *
      ```

      The three queries decompose as follows (using the answer formula):

      | query | rectangle | computation | result |
      |-------|-----------|-------------|--------|
      | `2 2 3 4` | rows 2–3, cols 2–4 | `pre[3][4]-pre[1][4]-pre[3][1]+pre[1][1]` | 3 |
      | `3 1 3 1` | row 3, col 1 | `pre[3][1]-pre[2][1]-pre[3][0]+pre[2][0]` | 1 |
