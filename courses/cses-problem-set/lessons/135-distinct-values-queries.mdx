      # Distinct Values Queries — offline sweep + Fenwick over last occurrence

      Given an array and `q` queries of the form "how many **distinct** values are in
      `[a, b]`?", we must count unique values per range.

      The trap: distinct-counting **cannot be merge-split** like a sum. Knowing the
      distinct count of `[l, mid]` and `[mid+1, r]` tells you nothing about `[l, r]` —
      the same value may appear in both halves and get double-counted. So neither
      prefix sums nor a plain segment tree work directly. We need a *cleaner* idea.

      ## The key idea: one "representative" per value

      Count a value only at its **last occurrence** inside the range. An element at
      position `i` with value `v` counts toward `[a, b]` exactly when `i` is the
      rightmost occurrence of `v` that is still `<= b` and `>= a`, i.e. when the
      *next* occurrence of `v` is to the right of `i` — outside the range.

      Process positions left to right and maintain, in a **Fenwick tree (BIT)**, a
      `1` at the *latest* position of each value (and a `0` at each place it used to
      be). When we reach position `b`, every value that appears in `[1..b]` has
      exactly one `1` in the BIT — at its last occurrence. Then:

      ```
      distinct in [a, b]  =  (number of 1s among positions 1..b)
                          -  (number of 1s among positions 1..a-1)
      ```

      Because a value whose last occurrence is `< a` simply never appears inside
      `[a, b]`, while a value whose last occurrence is `>= a` and `<= b` appears at
      least once. This is why *sorting queries by their right endpoint* and sweeping
      once over the array works: each query is answered in `O(log n)` when we reach
      its `b`.

      **Worked mini-example.** Array `[3, 2, 3]`. Sweep to `3`: last[3] moves from
      `1` to `3`. BIT now holds a `1` at `2` (value 2) and `3` (value 3). Range
      `[2, 3]` → `sum(3) - sum(1) = 2 - 0 = 2` (values `2, 3`) — correct.

      **Complexity.** `O((n + q) log n)` — the intended solution.

      :::tip
      **Interview tip:** "Count distinct / unique in a subarray" with all queries
      known up front is the classic trigger for **offline processing + sweep by
      right endpoint + BIT over last occurrence**. Remember you can often flip
      queries around (sort by `b`, or by `a` descending) to turn a range problem
      into a one-directional sweep. Mo's algorithm is the fallback when the sweep
      idea does not apply (e.g. a problem with online updates), but the Fenwick
      sweep is faster and simpler when it works.
      :::

      # The Problem

      You are given an array of `n` integers and `q` queries of the form: how many
      distinct values are there in a range `[a, b]`?

      ## Input

      The first input line has two integers `n` and `q`: the array size and the
      number of queries.

      The next line has `n` integers `x_1, x_2, ..., x_n`: the array values.

      Finally, there are `q` lines describing the queries. Each line has two integers
      `a` and `b`.

      **Constraints:** `1 <= n, q <= 2*10^5`, `1 <= x_i <= 10^9`,
      `1 <= a <= b <= n`.

      ## Output

      For each query, print the number of distinct values in the range.

      ## Sample

      **Input:**
      ```
      5 3
      3 2 3 1 2
      1 3
      2 4
      1 5
      ```
      **Output:**
      ```
      2
      3
      3
      ```

      ### Solution — progressive tiers

      **① Brute force — hash set per query, O(len) per query**

      For each query, scan `A[a..b]` into a `std::set`, count the elements. Correct,
      but a full-range query costs `O(n)` and `q` of them cost `O(n*q) = 4*10^10`.

      ```cpp
      int brute(int a, int b, vector<int>& A) {
          set<int> seen;
          for (int i = a; i <= b; i++) seen.insert(A[i]);
          return (int)seen.size();
      }
      ```
      *O(len log len) per query — correct, too slow.*

      **② Optimization — sort queries by right end + Fenwick over last occurrence,
      O((n + q) log n)**

      ```cpp
      #include <bits/stdc++.h>
      using namespace std;

      int main() {
          ios::sync_with_stdio(false); cin.tie(nullptr);
          int n, q; cin >> n >> q;
          vector<int> a(n + 1);
          for (int i = 1; i <= n; i++) cin >> a[i];

          // coordinate-compress the values down to 1..k
          vector<int> vals(a.begin() + 1, a.end());
          sort(vals.begin(), vals.end());
          vals.erase(unique(vals.begin(), vals.end()), vals.end());
          auto id = [&](int v) {
              return int(lower_bound(vals.begin(), vals.end(), v) - vals.begin()) + 1;
          };

          // queries stored as {b, a, original index}, sorted by right end b
          vector<array<int, 3>> qs(q);
          for (int i = 0; i < q; i++) {
              cin >> qs[i][1] >> qs[i][0];        // a, then b
              qs[i][2] = i;
          }
          sort(qs.begin(), qs.end());             // by b ascending

          // Fenwick {add(i,d), sum(i)} — 1-indexed over positions
          vector<int> bit(n + 1, 0), last(vals.size() + 1, 0);
          auto add = [&](int i, int d) { for (; i <= n; i += i & -i) bit[i] += d; };
          auto sum = [&](int i) { int s = 0; for (; i > 0; i -= i & -i) s += bit[i]; return s; };

          vector<int> ans(q);
          int ptr = 0;
          for (int i = 1; i <= n; i++) {
              int c = id(a[i]);
              if (last[c]) add(last[c], -1);      // previous occurrence stops being the last
              add(i, 1);                          // position i is now the last of value c
              last[c] = i;
              while (ptr < q && qs[ptr][0] == i) {
                  ans[qs[ptr][2]] = sum(i) - sum(qs[ptr][1] - 1);
                  ptr++;
              }
          }
          for (int x : ans) cout << x << "\n";
          return 0;
      }
      ```

      *O((n + q) log n) time, O(n) memory — the intended solution.*

      **③ Further optimization — none needed**

      `O(log n)` per query is optimal; the internal `log` is unavoidable for a Fenwick.

      **④ Alternative — Mo's algorithm, O((n + q) sqrt(n))**

      Mo sorts the queries into `sqrt(n)` buckets by their left endpoint, then
      moves two pointers `curL`, `curR` to expand/shrink the current window, keeping a
      frequency array so the distinct count updates in `O(1)` per add/remove. Each
      pointer moves `O(q * sqrt(n))` steps total. Handles updates too (then it becomes
      "Mo's with modifications").

      ```cpp
      // ④ continues the ② program: n, a, qs (as {b, a, id}) are already in scope.
      for (int i = 1; i <= n; i++) a[i] = id(a[i]);     // compress values in place for freq[]
      vector<array<int,3>> mo(q);                       // reshape queries to {id, L, R}
      for (int i = 0; i < q; i++) mo[i] = {qs[i][2], qs[i][1], qs[i][0]};
      int B = (int)sqrt(n) + 1;
      sort(mo.begin(), mo.end(), [&](const auto& x, const auto& y) {
          int bx = (x[1] - 1) / B, by = (y[1] - 1) / B;
          if (bx != by) return bx < by;
          return (bx & 1) ? x[2] > y[2] : x[2] < y[2];  // serpentine order
      });
      vector<int> freq(vals.size() + 1, 0);
      int distinct = 0, curL = 1, curR = 0;
      auto moAdd = [&](int i) { if (freq[a[i]]++ == 0) distinct++; };
      auto moRem = [&](int i) { if (--freq[a[i]] == 0) distinct--; };
      for (auto& t : mo) {
          while (curL > t[1]) moAdd(--curL);
          while (curR < t[2]) moAdd(++curR);
          while (curL < t[1]) moRem(curL++);
          while (curR > t[2]) moRem(curR--);
          ans[t[0]] = distinct;
      }
      ```
      *O((n + q) sqrt(n)) — correct and simpler to reason about, but slower.*

      # Code logic

      Walking through the Fenwick sweep:

      - **Coordinate compression.** Values go up to `10^9`; `last` must be indexed by
        value, so we map each distinct value to `1..k` with `lower_bound`.
      - **`last[c]` says which position currently owns the `1` for value `c`.** When a
        new occurrence at position `i` arrives, we delete the old `1` (`add(last[c],
        -1)`) and plant a new one (`add(i, 1)`). There is always at most one `1` per
        value.
      - **Sweep `i` from `1` to `n`; answer every query whose `b == i`.** This is why
        we sort by right endpoint — by the time the sweep reaches `b`, the BIT holds
        exactly one `1` per value appearing anywhere in `[1..b]`, at its *last*
        occurrence.
      - **`sum(b) - sum(a-1)`.** A value contributes a `1` inside `[a..b]` iff its last
        occurrence is `>= a`; values whose last occurrence is `< a` contribute only to
        the `sum(a-1)` part and cancel. So the difference is precisely the count of
        distinct values present in `[a, b]`.
      - **Correctness invariant.** Inductively, after processing position `i`, `sum(x)`
        for any `x <= i` equals the number of distinct values whose last occurrence
        is `<= x`. A direct induction shows this stays true as `last` moves.

      # Walkthrough

      Trace the sample. Array (1-indexed): `[1]=3, [2]=2, [3]=3, [4]=1, [5]=2`.
      Queries in input order: `(1,3)`, `(2,4)`, `(1,5)`.

      Sorting by `b` gives the order `(1,3)`, `(2,4)`, `(1,5)`.

      | step i | a[i] | action | BIT's 1s at | answered |
      |--------|------|--------|-------------|----------|
      | 1 | 3 | last[3]=1, `+1` at 1 | {1} | — |
      | 2 | 2 | last[2]=2, `+1` at 2 | {1,2} | — |
      | 3 | 3 | drop `1` at 1, `+1` at 3 | {2,3} | `(1,3)`: `sum(3)-sum(0)=2` → **2** |
      | 4 | 1 | last[1]=4, `+1` at 4 | {2,3,4} | `(2,4)`: `sum(4)-sum(1)=3-0=3` → **3** |
      | 5 | 2 | drop `2` at 2, `+1` at 5 | {3,4,5} | `(1,5)`: `sum(5)-sum(0)=3` → **3** |

      Output: `2 3 3`. Matches the sample. ✓

      Notice at step `3` value `3` was *moved* from position `1` to `3`: that is the
      whole trick — each value is counted at exactly its latest position, so the
      distinct count over any range is a pure window-sum of those coupon positions.
